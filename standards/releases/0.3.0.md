# Standards 0.3.0 — Design-system iteration, delivery tools and pinned skills

Reviewed 2026-11-18. Standards tag: `standards-v0.3.0`. Certified source `f87db802d0c2992d618f9ed2f887c91fa0c9634e`; evidence in [audit/certification-2026-11-18/README.md](../../audit/certification-2026-11-18/README.md).

The runtime is the 0.2.1 runtime: Astro 7.4.12, EmDash 1.5.0, Node `^22.23.4 || ^24.22.1 || >=26.12.1`. A site already on 0.2.1 needs no dependency, database or deploy step. What changes is the design system the starter ships, the delivery and audit tools, and the skills.

This is the first release that pins what it distributes. `standards/baselines/0.3.0.json` holds a content hash per skill folder, per sync and audit helper and the Impeccable version (`distribution`), and a digest of the change notes below (`changes`). `fleet:status` compares sites against them, so a site whose skills or helpers lag the release is no longer reported as current.

## Known gaps

- Skills link to Baseline documents (for example `docs/artifact-lint.md`) that EmDash sites do not carry; follow such links in a Baseline checkout.
- Workers/D1/R2 remains outside the certified profile.
- Deferred: TypeScript 7, `@types/node` 26 and `parse5` 8 (majors); the next EmDash upstream skill commit goes through the weekly reviewed proposal.

## Changes for sites

13 change notes; the largest is a minor change. Each entry says which platforms it affects and how a site takes it.

### Changes how pages look: decide per site

#### Container-query Card and Grid, opt-in section joins and CSS-first reveal

_EmDash and static · components, styles · Review and merge by hand; a decision per site · files: `src/components/Card.astro`, `src/components/Grid.astro`, `src/components/Section.astro`, `src/components/Container.astro`, `src/lib/layout-style.ts`, `src/layouts/SiteShell.astro`, `src/styles/registry-aliases.css`_

A horizontal Card switches on its own width (side by side from 32rem) instead of the viewport, with media and body in a `.card-layout` wrapper. Grid items become named `card-slot` query containers (`slots={false}` opts out). Section, Container and Grid accept token names for `gap`. Same-ground section joins are available under `SiteShell sectionJoins="shared"`, with `<Section spacing="medium">`. `data-reveal` animates with scroll-driven CSS where supported; the observer runs only as the fallback. `src/styles/registry-aliases.css` (not imported by default) maps registry component utilities onto Baseline tokens.

##### For sites

Adopt these together with the matching `global.css` rules, not file by file. Site CSS that selects `.card > .card-media` or `.card > .card-body` must drop the child combinator; a horizontal Card in a flex row and a Grid item with `justify-self` other than stretch need an explicit width. Section joins are opt-in: add the prop, then inspect each stacked join and mark sections that paint their own background with `data-ground`. Static sites receive the managed components through `sync:baseline`; their site-owned Base and `global.css` stay a manual merge.

#### Type steps, heading sizes and a resize-text rule in the starter stylesheet

_EmDash and static · styles · Review and merge by hand; a decision per site · files: `src/styles/global.css`_

The starter `global.css` gains a fluid space scale, type steps 3 to 5, a heading map and tokens for motion, layering and breakpoints. Headings h3 to h6 now have sizes (h3 step 0, h4 body size, h5/h6 step −1); before, they inherited the body size. The two text bridges are retuned to the new 2.5× resize-text rule: `--text-step-2-to-0` starts at 21px (was 16px) and `--text-step-3-to-1` at 28px (was 20px), so hero text using them is larger on phones. Three timings were rounded to tokens (180ms and 220ms to 200ms, 240ms to 250ms). Every theme token is emitted with `@theme static`.

##### For sites

`global.css` is site-owned and calibrated, so nothing changes until a site merges it. Merging the heading map and bridges changes how pages look: decide per site, capture routes before and after (`capture:routes`), and record the decision. A site that keeps its stylesheet sees a warning from `design:tokens` for the resize-text ratio, not a failure. The new tokens are optional vocabulary; an older stylesheet stays valid. Details: the design-system section at the top of `docs/baseline-updates.md`.

### Review and merge by hand

#### A guide and templates for an admin non-technical editors can use

_EmDash · components, docs, tooling · Review and merge by hand; a decision per site · files: `docs/editor-experience.md`, `src/lib/derived-order.ts`, `src/plugins/editor-ui/admin.tsx`, `src/plugins/editor-ui/config.ts`, `scripts/cms-admin-metadata.mjs`_

`docs/editor-experience.md` covers deriving display order from data instead of number fields, a drag-and-drop order page for truly editorial orders, localised select labels without a data migration, list columns, a "where this appears" panel, a help page and dashboard card, hidden navigation items, the translation-group key trap and comparing a draft with the live row before discarding it. `src/lib/derived-order.ts` adds weekday/time, list-then-title and taxonomy-rank comparators. The `editorial-order` and `editor-ui` native plugin templates ship inactive, and `cms:admin-metadata` reviews admin labels.

##### For sites

Nothing changes until a site chooses to. Read the guide when editors find the admin hard to use, and adopt the parts that fit; the plugin templates must be registered deliberately. The public site is unaffected.

### Copy into the site

#### Token guardrails, resize-text ratio and fairer rendered-UI audits

_EmDash and static · tooling · Copy the named files into the site · files: `scripts/design-system.mjs`, `scripts/css-contracts.mjs`, `scripts/check-css-contracts.mjs`, `scripts/audit-ui.mjs`, `scripts/audit-design-system.mjs`_

`check:css` prints advisory token guardrails (Tailwind default palette and type utilities, arbitrary values, raw colours, spacing and z-index outside token definitions); `--strict-guardrails` makes them fail. `design:tokens` checks that every fluid text token's maximum is at most 2.5 times its minimum (a warning on stylesheets that predate the rule), exports DTCG 2025.10 with `--format dtcg`, and applies a strict theme for new client sites (`--init-client`; existing sites opt in with `--strict-theme`). `audit:ui` measures empty bands against 1.5 times the page's own `--spacing-section` (`--band <px>` keeps a fixed limit) and measures `::before`/`::after` decorations by what their clipping ancestors let through, which removes false overlaps.

##### For sites

Static sites receive these through `sync:baseline`. EmDash sites copy the scripts whole when they carry Baseline's versions; a site that owns its own `design-system.mjs` keeps it and runs Baseline's read-only from a Baseline checkout (`node <baseline>/scripts/design-system.mjs`). `audit:ui` runs from a Baseline checkout against any origin without installing it.

#### Impeccable in a site comes only from the site skill sync

_EmDash · skills, tooling · Copy the named files into the site · files: `scripts/skill-sync.mjs`, `scripts/sync-impeccable-skill.mjs`_

In an EmDash site both `sync:site-skills` and `sync:impeccable` wrote the Impeccable folder. The second rewrote files the site-skill receipt owned, so every later site sync reported eight Impeccable files as local drift. The site skill sync now writes `.emdash/impeccable-source.json` from the applied `PROVENANCE.json`, and `sync:impeccable` refuses to apply where the site-skill receipt manages Impeccable (a read-only `--check` still reports).

##### For sites

Copy both helpers whole, then use `sync:site-skills` for Impeccable. If the next site sync lists Impeccable files as conflicts, they are this drift: review that the incoming files are the release's, and accept them.

#### Skill sync helpers list new files for static profiles and know upgrading-emdash

_EmDash and static · tooling, skills · Copy the named files into the site · files: `scripts/skill-sync.mjs`, `scripts/sync-impeccable-skill.mjs`_

`sync-impeccable-skill.mjs` now adds files new in an Impeccable release to the shared profile manifest, so static profiles ship every file the skill links to; the manifest lists the six files from 4.9.2 and `engine-checksums.txt`, which the launcher needs to verify engine downloads. `skill-sync.mjs` manages `upgrading-emdash` with the other EmDash mirrors.

##### For sites

Skill sync never replaces its own helper. Copy both scripts whole before running the skill sync; `sync:site-skills -- --check` reports `helper: differs` until `skill-sync.mjs` matches.

#### Verified D1 copies, local upgrade rehearsal and live checks for Workers sites

_EmDash · delivery, tooling, docs · Copy the named files into the site · files: `scripts/d1-export.mjs`, `scripts/d1-rehearse.mjs`, `scripts/check-live.mjs`, `scripts/workers-rules.mjs`_

Lessons from moving four live Workers sites to EmDash 1.5. `db:export-d1` now keeps the FTS5 search rows, creates every table before any row, writes to `.emdash/backups/` and refuses a destination Git would track, and writes the copy only when row counts, integrity and foreign keys match a scratch load. New `db:rehearse` loads that copy into a fresh local D1, copies active registry plugin code from R2 and prints the `wrangler dev` command, so a core upgrade runs its migrations on a copy instead of on production (a Cloudflare preview version is bound to the production database). New `check:live` requests every sitemap page on a deployed origin and checks stylesheets, scripts and status codes; it also warns on redirecting sitemap URLs, non-self canonicals, missing or repeated meta descriptions and hreflang that disagrees with the sitemap (`--strict-seo` makes those fail). `audit:site` and `fleet:status` check the Workers rules: `@astrojs/cloudflare` 14.4 or newer on EmDash 1.5, every imported `@emdash-cms/*` package declared, and HTML edge-cache keys per build.

##### For sites

Run the commands from a current Baseline checkout inside the site folder (`node <baseline>/scripts/d1-rehearse.mjs`, `node <baseline>/scripts/check-live.mjs`), or copy the four scripts and add `db:export-d1`, `db:rehearse` and `check:live` to the package scripts. Before the next deploy of a Workers site, fix any Workers rule `fleet:status` reports. After a deploy, run `check:live` against every exposed hostname.

### Arrives with the site's sync

#### Skill refresh: Impeccable 4.9.2, upgrade and delivery routing, plugin selection

_EmDash and static · skills · Arrives with the site's skill or source sync_

Impeccable moves from 4.8.1 to 4.9.2 (a critique rubric split out of `critique.md`, a motion reviewer, `foundations`, comp-led new-work references; launcher 0.1.25 with checksum-verified engine downloads). The EmDash mirrors refresh `creating-plugins` (a repeater can hold a `media_picker`), and `upgrading-emdash` becomes a built-in mirrored skill. Baseline's own skills now route upgrades and deploys through `db:rehearse` and `check:live` (`emdash-production-cutover` maintenance and launch references, `emdash-content-modeling`), add the Registry plugin selection guide where plugins are chosen (`emdash-site-setup`, `new-site-workflow`), document contact-form mail and bilingual URLs, and carry the design-system vocabulary in `astro-site-design`.

##### For sites

EmDash sites: `npm run sync:site-skills -- --stage`, review the staged diff, `--apply <id>`; then the same with `sync:emdash-skills` (add `upgrading-emdash` with `--add-skill upgrading-emdash` while the site's helper predates it). Impeccable arrives with the site skills; do not run `sync:impeccable` in a site. Adopt the updated helpers first (see the helper notes). Static sites receive the skills their profile ships through `sync:baseline`, and must copy the six new Impeccable files and `scripts/engine-checksums.txt` by hand, because bounded sync cannot add files the site did not already have.
