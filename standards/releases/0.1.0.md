Node 24 is recommended, not required. Astro remains an explicit EmDash/framework choice; new stable Astro and adapter releases trigger independent dated evaluation.

Fresh SQLite schema/seed and normal Node SSR; post/page/list/category/tag/404 routes; public native media and gallery rendering; measured 50-column budget guard; representative registered title/rich-text editing and save/reload/publish; table read-only inline placeholder and content preservation; gallery asset IDs/child keys/order/captions preserved through inline editing; fresh storage-backed media after build; existing-database upgrade/restore evidence from Phase 2.

Local Windows checks cover clean canonical goldens, no-JS, active/reduced motion, actual Chromium zoom, text spacing, keyboard/reflow and controlled visual failures. G/O/P tooling remains dev-only, local/private in memory and excluded from normal emitted client JS/CSS. Normal `/_styleguide` GET/HEAD is 404. Fixtures use a separate build profile rejected by the release guard. Screenshot tests are never Actions, pre-commit, build or deployment dependencies.

## Explicit limits

- Workers/D1/R2 parity and remote media ingestion are unverified and bounded to Phase 5 (#8/#9). Local SQLite widths do not certify remote D1 schema, quotas or expanded queries.
- Native forms remain opt-in with Phase 2 evidence. Live email/Turnstile/provider delivery, enhanced end-to-end accessibility and Worker behavior are unverified.
- This starter has no enabled multilingual routes or Astro route cache. Locale/menu/translation editing and cache-hint completeness become mandatory checks when those options are enabled; they are not certified by the single-language fixture.
- EmDash 1.3.0 regenerates a gallery block's **outer `_key`** on the exercised inline round-trip. Gallery semantics and image keys remain intact; external systems must not assume outer block-key stability. Admin table/gallery editing and every plugin block are not covered by the representative inline test.
- Browser behavior is certified only for the pinned Windows Chromium profile, not Firefox/WebKit, all operating systems, or WCAG conformance. Automated CI's Linux configuration is not a claim of an observed GitHub run.
- Existing admin bundle-size warnings, deprecated transitive packages, source-skill refresh candidates and the unknown upstream commit of the curated Impeccable snapshot remain explicit advisories. A staged refresh is not an applied synchronization. Dirty editorial skills are excluded from this release and preserved locally.
- Public packaging, license/history sanitization, visibility change and community outreach remain Issue #11. This standards release does not certify a public launch or authorize client upgrades.

## Upgrade and recovery

1. Identify the deployed runtime, starter commit and data/media ownership. Read the manifest scope before selecting this reference; unsupported target checks remain unverified. Audit diagnosis must not migrate, sync or upload.
2. Stop writers and take recoverable matching snapshots of the existing database (consistent SQLite snapshot including any WAL state), media, key/environment configuration and package files. Keep credentials/private data outside the repository. Do not copy starter sample content over a working site.
3. Review changes on a disposable copy. Use the matching npm lockfile and a supported Node version; run `npm ci`, unit/schema/design/typecheck/build, public/editor/native-media tests and the local Windows visual/HUD suites for applicable changes. Preserve dependency-local Zod bundling. Refresh visual baselines only via explicit reviewed local `--update`.
4. Exercise fresh setup and the supported existing-database migration before rollout. Check actual physical columns in the target database; a missing database is unmeasured. Verify real registration/canonical values/save/reload/publish rather than treating edit markers as proof.
5. To roll back, stop site processes and restore the **matching old package/lock + database + media + key/config set**, then npm ci/rebuild and verify public/editor behavior. Package downgrade alone does not restore a migrated database. Never remove live database sidecars or replace data while writers run. Phase 2's disposable upgrade/restore receipt is retained; production restore remains site-specific.
