## Scope and implementation choices

Use existing parsers, browser/runtime dependencies, inspection and disposable visual-test helpers where appropriate. Add no runtime dependency, new CMS platform, mandatory checkpoint, full component registry or general mutation runner. A source graph reports observations; it cannot prove live binding or effective reuse by itself. Inspect loops in source and test record-count/content changes in the browser before claiming collection-backed repetition works. Source review found the same CMS post-preview markup repeated in the home/category/tag routes; extract that item into one native component with the existing date difference exposed explicitly, preserving markup, queries, URLs and presentation. Static routes already compose their shared Card and stay unchanged.

The fictional pilot uses a direct browser proof with the existing neutral foundation and synthetic content. It exercises engineering/content ownership rather than client art direction. Keep synthetic routes, schemas, media and any calibration/exception records confined to its owned disposable fixture. Use the project's existing infrastructure-fixture pattern; never add synthetic entries, credentials or broad design exceptions to the application source. Save raw screenshots and run receipts outside distributed source. Existing production/editor databases and source seed remain untouched.

Parallel work is bounded by file ownership: source inspection, browser reporting and pilot execution have separate writers. The primary agent integrates package scripts, distribution manifests/inventory, test tiers and workflow documentation, reviews all outputs and runs release verification after source is stable. No two agents write to the same CMS instance or canvas.
