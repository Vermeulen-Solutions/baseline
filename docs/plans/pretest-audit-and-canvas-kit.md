The user approved the scoped follow-up to issues [23](https://github.com/Vermeulen-Solutions/baseline/issues/23), [25](https://github.com/Vermeulen-Solutions/baseline/issues/25) and [26](https://github.com/Vermeulen-Solutions/baseline/issues/26): explicit audit actionability, a limited source-derived bootstrap and practical testing, including the optional headless CLI. - Site audit JSON now emits v3 with per-rule `bounded_recipe`, `design_judgment`, `verification_required` or `review_required`. The current reader also validates unchanged v2 artifacts using the archived schema. Strict-exit semantics remain. - Follow-up plans group evidence, bounded recipes, design decisions and manual review. Zero primitive counts explicitly permit suitable restrained layouts. Concrete selectors, the five-point rubric and conditional alternatives remain. Known recipes still need exact eligibility/preconditions and authorized scope. Token JSON retains its fields and adds classified diagnostics for hard findings, fluid advisories, fonts and edit-proxy observations.
- The optional manual `design:canvas-kit` command samples explicitly selected CSS with existing PostCSS/TypeScript/Playwright tooling. It does not execute target JS/config, fetch imports/fonts or alter source. Ordered local CSS, explicit context classes and role maps support an existing theme without renaming it. It emits hashed source/component evidence, original expressions, independent width-specific DTCG variables and bounded scene previews at 390/1440. Missing roles withhold scenes; unsafe inputs/existing outputs/source drift refuse. It is outside verify/build/CI and adds no package dependencies.
- Bootstrap documentation and both tool skills explain manual/automatic boundaries, font requests, unresolved values, native Astro translation, optional headless inspection and old-site adoption. New files/commands are allowlisted across profiles; bounded updaters do not acquire new membership implicitly.

## Practical evidence and discovered limits

Raw captures, exported tokens/figures, CLI results, source reports and test scripts remain private under `C:/dev/baseline-design-tool-trial/pretest-2026-10-26/`; existing-site details/assets are not committed to this reusable template. The saved scratch file is `Baseline-source-kit-test-2026-10-26.fig` in the testing user's Documents directory. The prior documents were preserved. No client or global MCP settings were changed, and no issue was closed or commented on by this implementation.

1. Starter sampling produced both scenes. A private older site's global-only input correctly reported missing roles and withheld scenes. After explicitly selecting its actual global/theme CSS order, body context and source-name mapping, both scenes resolved with the existing calibrated palette, fluid expressions and custom font requests. The palette and source bytes were preserved; no neutral fallback was introduced. Root size and role meanings remain explicit assumptions, not automatic page-style fidelity. A subsequent type guard requires valid font-family syntax and the expected color/length token types before scene generation; Chromium rejected an invalid font at both widths, while the original site's samples and all source hashes remained unchanged.
2. Desktop OpenPencil/MCP 0.16.0 imported 76 variables across the two owned collections and rendered both widths. Custom display/body and local accent/mono faces reported available. A long French-title/metadata toggle remained a real instance-property change. Scoped accessibility lint returned zero issues. These synthetic previews are not a complete client layout or an accessibility certification.
3. External CLI 0.16.0 was invoked through npm's cache, without adding it to the project/global installation. Saved-file info, tokens, node inspection, advisory lint and structural file diffs worked with no editor connection. The before/after file diff isolated the requested title/visibility edit; diff exit 1 means changed. DTCG export recovered original source-name/expression metadata. Combined CSS export may disambiguate duplicate names; it is not a replacement theme.
4. Headless `eval` failed on Windows/Node 24 during CanvasKit initialization because the WASM path contained a doubled drive prefix. No installed-package patch or security workaround was applied. Desktop MCP handled authoring/raster exports. This is an observed version/environment limitation, not universal headless incompatibility.
5. The user caught a real reopened-render defect: correct text and available fonts still produced garbled glyphs inside components. A fresh export reproduced it; diagnostics alone would have missed it. Reapplying the affected uniform text nodes' existing family/style repaired rendering. Save/reopen, a second reopen and a subsequent token refresh/reopen stayed legible; both exported images and the visible editor were inspected. Bound size/color variables were retained, and native CLI structural diff reported no authored property differences for the repair. The skill records a scoped recovery and refusal to hide a recurring defect with substituted fonts. It does not promise an upstream fix or safe rewriting of arbitrary rich text.
6. An isolated native Astro proof used source-derived variables, actual self-hosted fonts and native SiteShell/Section/Container/Card/Cluster, plus semantic disclosure and action states. Real Playwright inner sizes at 390×844, 768×900 and 1440×900 passed loaded-font/indigo-action checks, equal gutters, no horizontal overflow, long-title/metadata/lower-content checks, mobile stacking, desktop unequal columns, visible focus, disabled Tab skipping, Enter/Space disclosure, destinations and reduced-motion scroll behavior. Actual gutters were 20px, 35.828125px and 80px per side; native content measures can differ from the canvas's outer padding. Renders were visually inspected. This proves source-token transfer and native behavior, not pixel-equivalent reproduction of the illustrative canvas master. The built-in browser separately inspected the route; exact dimensions come from the isolated browser test.

## Recommended next testing, ordered by impact

1. Treat the reopened glyph corruption as an upstream reliability blocker for any affected document: capture the font names, app version, file and before/after renders; repair only the owned uniform text nodes as documented, then save/reopen and inspect again. If it recurs, use the actual browser proof as the review surface while investigating; do not silently substitute the brand fonts or claim the upstream bug was fixed.
2. Test the workflow on a real, user-led design task with another model or a fresh agent session. Check that the agent identifies and reviews CSS load order, aliases and role meanings, preserves expressions and client content, responds to a small visual change without overwriting unrelated work, and translates the approved result into native Astro. Record failures and needed user interventions; this pilot cannot establish speed, token savings or weaker-model reliability.
3. Expand token coverage only after collecting real cases: exercise alternate theme contexts, intermediate widths and root sizes, container-relative values, alpha/derived colors and long or mixed-language copy. Compare recorded source expressions and sampled values with the rendered site; unresolved or unsupported contexts must remain visible rather than receiving invented defaults. Keep samples independent of production CSS and require manual approval of semantic role mappings.
4. Re-test version-matched OpenPencil CLI headless authoring on Windows when an upstream release changes the CanvasKit path behavior. Until then use its saved-file inspection and desktop MCP for authoring. Do not introduce a custom `.fig` parser, a second site token system, or a build-time dependency solely to mask this observed limitation.
