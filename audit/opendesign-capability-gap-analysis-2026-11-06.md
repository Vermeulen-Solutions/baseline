# OpenDesign catalogue compared with Baseline — 6 November 2026

For ordinary public websites, I recommend testing two small additions first: a more rigorous vector/brand-asset workflow and a consistent editorial-illustration workflow. Strengthen the existing accessibility acceptance with a reproducible screen-reader procedure. Use participant research when navigation or audience uncertainty warrants it. Layout, typography, colour, responsive composition, copy, forms and ordinary UI motion already have substantial coverage; another general frontend-design skill is unlikely to close a meaningful gap.

Charts are not a core gap for service, editorial or portfolio sites. They can be useful for a specific report, calculator or data-publishing brief, just as 3D or rendered video can serve a specific visual brief. Their presence in the catalogue is not a reason to add them to Baseline. This analysis was re-ranked explicitly around public-website work rather than catalogue breadth or application/dashboard development.

## Scope and evidence

The [catalogue](https://open-design.ai/skills/#catalog) contains 244 entries from 58 repositories in 10 task categories. I enumerated every card, screened its task/output/requirements against Baseline, and checked 25 original-source entry points. Twenty-four were available and read either completely or in relevant sections; one returned 404. Source-level review depth is recorded individually. Linked reference libraries, scripts and example projects were not comprehensively audited, installed or run. This is a capability comparison and candidate assessment, not a quality certification of all 244 skills.

The comparison uses review commit `ca69c453dcae2b1546e609abc831c653cfa71ab0` on `codex/design-review-surfaces`, including the earlier motion/routing work. The shared main checkout remains at `f5a6785`; the new capability-routing reference is not merged there. Thirteen of the eighteen coverage files checked are byte-equivalent after LF normalization in both checkouts, including discovery/content guidance, accessibility guidance, Impeccable, media preparation and support boundaries. The relevant workflow entry points differ chiefly in the newer routing/surface guidance. [Coverage hashes](opendesign-catalog-2026-11-06/baseline-coverage.json) distinguish the snapshots rather than treating an unmerged branch as released main.

Here, a **gap** means that a useful website job lacks sufficient task-specific guidance, an exercised delivery path or acceptance evidence. It does not mean an agent is technically incapable of writing the code. I distinguish specialist depth, verification and discovery gaps from genuinely different deliverables. An external library not being preinstalled is not itself a gap.

The reusable Baseline package is also distinct from this session. Image generation, conversation visualizations, presentations and PDF tools are available here through host skills. Baseline can use available tools, but generated sites cannot assume those tools exist in every agent environment. For example, the installed `visualize` skill explicitly distinguishes conversation artifacts from project website changes; it does not by itself supply a production chart integration.

## Concrete issues found in the sources

- **SVG guidance can conflict.** Impeccable's current craft floor accepts geometric SVG/diagrams but classifies shaded or perspectived illustration as a picture and restricts SVG imitating pictures. Anatomy deliberately produces detailed, shaded isometric objects. The shared capability route does not explicitly reconcile that case. For an authorized editable technical figure, resolve the scope in Baseline-owned guidance and preserve the upstream mirror. Otherwise an agent could reject a suitable vector method or silently substitute a bitmap. This is a routing/policy ambiguity, not a lack of vector tooling.
- **Generating an image is not an illustration system.** The article/infographic sources contain useful planning and consistency methods but also backend selection, preference files and confirmation conventions. Keep their useful planning ideas without importing a parallel project-context system or repeating questions already answered by the site's brief. Inspect generated text and exact factual diagrams through the existing content rules.
- **Asset lookup and asset design are separate.** [theSVG](https://github.com/glincker/thesvg/blob/0ea4d44764ab73c8500382711736f97cba50afc8/skills/thesvg/SKILL.md) retrieves existing brand/service SVGs; it does not design the client's identity or generic UI icons. Its code license and the individual assets' usage conditions are separate concerns. A lookup source can help an integrations page without making a new CDN or React package part of every site.
- **Research sources vary in depth and commercial coupling.** The generic [User Research](https://github.com/anthropics/knowledge-work-plugins/blob/main/design/skills/user-research/SKILL.md) entry is a short planning outline; Research Synthesis adds explicit participant/quote traceability. [Cookiy's entry](https://github.com/cookiy-ai/user-research-skill/blob/main/SKILL.md) routes to a provider and repeatedly suggests its service. A Baseline research route should work from supplied notes or a manual study and keep real and synthetic respondents distinct. No service was contacted or study run in this analysis.
- **Candidate testing guidance needs review too.** The screen-reader source has practical browse/focus-mode scenarios and platform references, but also market-share figures and illustrative widget code that should not become current Baseline facts or replace existing native controls. Its linked platform manuals and actual reader behavior remain untested here.
- **Hardening is substantially covered already.** [Break UI](https://github.com/emilkowalski/skills/blob/2d228630ba1446365f614a108cb8252f1feda202/skills/break-ui/SKILL.md) proposes realistic, schema-backed adverse fixtures behind a development toggle. Existing Impeccable `harden`, content-expansion checks and browser/state testing already cover the capability. Borrowing a reproducible fixture technique could improve execution; installing another general hardening skill is not necessary.

In particular, I would not add another generic frontend-design, palette, spacing, typography, responsive, copywriting or design-review skill on the evidence of this catalogue. The more useful routing improvement is to make existing guidance discoverable before proposing another installation.

## Brief-dependent extensions, not core gaps

If an actual site needs data visualisation, the source checks distinguish two different deliverables: [AntV chart-visualization](https://github.com/antvis/chart-visualization-skills/blob/master/skills/chart-visualization/SKILL.md) sends a chart specification to a hosted API and returns an image URL; [G2](https://github.com/antvis/chart-visualization-skills/blob/a105fa12a9fa41fccccc2eba7f4b34973628f5d3/skills/antv-g2-chart/SKILL.md) describes a browser library. Neither was executed. An image service is not an interactive Astro chart integration. The catalogue's [infographic-creator source](https://github.com/antvis/chart-visualization-skills/blob/master/skills/infographic-creator/SKILL.md) returned 404 in this check.

Likewise, [Three.js Interaction](https://github.com/CloudAI-X/threejs-skills/blob/b1c623076c661fc9b03dac19292e825a5d106823/skills/threejs-interaction/SKILL.md) offers library-specific picking/control recipes; it is not an already tested Baseline island. [Algorithmic Art](https://github.com/anthropics/skills/blob/main/skills/algorithmic-art/SKILL.md) has seeded p5.js methods but fixes its viewer to Anthropic branding, so its complete template is unsuitable as a neutral Baseline default. These can inform a requested experiment without expanding every site's runtime.

## Follow-up acceptance and scope decisions

1. **Existing-brand asset pilot:** start from an authorized existing mark and approved website tokens. Produce useful SVG/icon variants, inspect actual small sizes and light/dark backgrounds, then prove their use in Astro. Decide separately whether new identity creation is part of the site's commission; preservation stays the default. Compare with the current workflow before deciding whether the candidate skill adds enough value.
2. **Editorial illustration pilot:** take two or three related real page topics, explain what each image contributes, and keep one visual language across the set. Inspect final crops, text, theme behavior and production-prepared output. Use a native vector/diagram method when editability or exact structure matters, and raster generation where a picture is intended. Resolve the SVG-rule ambiguity within that scoped task.
3. **Verification depth:** exercise a representative navigation path, a form error/result and a dynamic update with an actual available screen reader. Record platform/browser, task, expected announcement and observed result. If reader execution is unavailable, retain the limit rather than treating DOM/ARIA inspection as a completed speech check.
4. **Research only where needed:** for an uncertain content structure, prepare a small findability/usability study and synthesize genuine results. Do not substitute owner approval, an agent critique or synthetic respondents for observed visitor evidence; do not impose a study on straightforward sites whose brief is already clear.

The analysis does not authorize implementing this list. No skills, providers or runtime packages were installed; no maintained skill, production code, CMS data or canvas was changed. No new runtime tests were run for the catalogue candidates. The earlier motion experiment remains separate evidence. This report and its metadata are local audit artifacts for deciding follow-up scope.
