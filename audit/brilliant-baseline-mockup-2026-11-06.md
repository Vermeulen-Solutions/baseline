# Brilliant: the actual Baseline mockup

Keep HTML/browser as the default for this workflow and keep Brilliant available when native canvas editing is worth the reconstruction work. This test supports an editable-canvas option; it does not support a clean HTML round trip or a claim of faster/cheaper design authoring. Before describing HTML recreation as a supported convenience, the follow-up scope would need font matching, source-to-native layout mapping, effect fidelity and semantic/interactive export acceptance. Those improvements need a separate implementation decision; this audit does not implement them.

Open the [desktop/mobile comparison](visual-concepts/brilliant-baseline-mockup-2026-11-06/index.html). It shows the unchanged browser source, the repaired native reconstruction and a realistic longer-copy revision. Raw browser exports and the failed initial import are available separately, so a good native PNG cannot hide a poor HTML export.

## Scope and method

The source is the user's actual [Baseline site mockup](visual-concepts/baseline-site-mockup/index.html), with its [adaptation record](visual-concepts/baseline-site-mockup/adaptation.md). Both were read before authoring and remain unchanged. [Source identity](visual-concepts/brilliant-baseline-mockup-2026-11-06/source-identity.json) records LF-normalized hashes, real platform fonts and sampling assumptions. The source has a masthead, split hero/specimen, three profiles, four-card bento, light methodology band, scope, CTA and footer. It contains 280 body descendant elements and approximately 4,122 rendered text characters at desktop width. Captures are 1440×4459 and 390×6497, with a 900px review viewport and reduced motion enabled.

This is source-driven recreation using browser measurements, followed by native editing. It establishes whether the actual composition can be represented, changed and exported; it is not a blind comparison of new designs produced from a brief. The source's historical example verification counts were copied as mockup content, not asserted as today's repository results. No Astro route, client record, global configuration, account, publication or dependency was changed.

The isolated local project is `audit/visual-concepts/brilliant-baseline-mockup-2026-11-06/project`. `Baseline mockup` contains the first sampled HTML conversion. `Native reconstruction` contains the repaired scene and final revision. Native project/catalog/cache files remain local; only `project/Exports/` is eligible for Git. Vendor knowledge/schema output is retained privately outside the repository. The earlier owner's “Owner edit kept” work is in the separate pilot project and was not edited.

## Full-page HTML conversion: visual failure

The browser resolved source custom properties, modern colours and responsive sizes at 1440 and 390. Sampled inline input kept all visible page content; system font stacks were mapped to the real family names reported by Chromium. The first preflight mistakenly copied inapplicable computed flex defaults onto block elements; that extraction mistake was corrected before canvas creation. The second input also made decorative empty elements explicit and used CSS shorthands the converter recognizes. The input is sampled geometry, not preserved fluid CSS.

One edit created **870 native objects** across the two boards. The API returned success plus real composition diagnostics, but the actual render was unsuitable: major regions overlapped, the bento/profile grids stacked incorrectly, footer content appeared beside the hero, inline treatments were lost and decorative grid gradients became broad sweeps. See the [initial desktop PNG](visual-concepts/brilliant-baseline-mockup-2026-11-06/project/Exports/initial-1440.png), [mobile PNG](visual-concepts/brilliant-baseline-mockup-2026-11-06/project/Exports/initial-390.png) and [create receipt](visual-concepts/brilliant-baseline-mockup-2026-11-06/initial-create.json). Successful object creation was not counted as successful recreation.

This trial used a locally generated computed-style input, not an official browser-extension capture. It demonstrates failure of this particular HTML/MCP path on this mockup, rather than proving every possible Brilliant import path fails.

## Native reconstruction: partial fidelity after repairs

[The reconstruction helper](visual-concepts/brilliant-baseline-mockup-2026-11-06/prepare-native.mjs) produced native DSL from the measured source hierarchy, with editable text, fills, strokes, styled ranges, glows, a native SVG grid and a project-specific token catalog. Original CSS expressions remain in the sample records. Most layout was initially fixed-position geometry; that is an explicit limitation, not a responsive layout solution. The scene initially contained **763 objects and 249 text blocks**. The current helper is the corrected reproducer; the separately retained correction batches/results show the intermediate fixes rather than claiming that its current bytes were the first submitted batch.

Several defects were in this reconstruction harness and were repaired before judging the result: CSS pixel tracking was initially bound as a native font-size-relative token; intrinsic single-line labels were constrained too tightly; and the mixed-content agent tag needed one rich-text object. The first design-system write also used unsupported `rgba()` declarations; the corrected write uses native ARGB order. These are authoring/adapter costs, not silently attributed to vendor rendering quality.

The repaired [desktop PNG](visual-concepts/brilliant-baseline-mockup-2026-11-06/project/Exports/repaired-1440.png) and [mobile PNG](visual-concepts/brilliant-baseline-mockup-2026-11-06/project/Exports/repaired-390.png) contain the full composition at exactly the source capture dimensions. Visual review finds the section topology, bento relationships, dark/light pacing and content recognizable and substantially closer than the HTML import. This is still a **partial** fidelity result: noise was not recreated; grid opacity, glow/blur, font metrics, optical variants and the headline gradient differ. The source's Display/Text font stacks were collapsed to the actual `Segoe UI Variable` family for the canvas; Chromium renders the exported family through a `Segoe UI` fallback. That mapping is part of this trial and should not be generalized into a claim that Brilliant cannot use other font families.

[Pixel measurements](visual-concepts/brilliant-baseline-mockup-2026-11-06/pixel-comparison.json) compare the full matching extents with native transparency composited on black. Approximately **5.48% desktop / 10.05% mobile** of pixels differ by more than 16 levels in at least one RGB channel. This is descriptive evidence, not an aesthetic or fidelity pass threshold. Native exports repeatedly reported provisional font measurement. One later warm export was byte-identical to its preceding PNG, but the warning persisted; stability at that checkpoint does not establish that every font resolved correctly.

## Realistic revision: fixed frames fail, native flow can repair them

One six-text-object batch changed the headline to “A foundation for / sites worth shipping.”, lengthened the supporting paragraph and replaced the hero CTA with “Build with Baseline” on both boards. These are agent-authored test drafts, not owner-approved copy. The native headline height grew from about 295px to 394px on desktop and 134px to 179px on mobile. The longer CTA text measured 138px inside a 123px original button. Fixed parent frames did not absorb those changes: [the pre-repair browser capture](visual-concepts/brilliant-baseline-mockup-2026-11-06/revision-before-flow-browser-390.png) and [readback](visual-concepts/brilliant-baseline-mockup-2026-11-06/revision-before-flow-read.json) retain the failures.

[Native flow authoring](visual-concepts/brilliant-baseline-mockup-2026-11-06/prepare-revision-flow.mjs) converted the hero, text containers, actions and surrounding page to hug/fill and wrapping, retaining the measured spacing. The first repair created 12 frames and modified 46 objects. Additional bounded edits restored explicit top/left alignment, extended the grid, set the black outer ground and reinstated clipping after frame-to-layout conversion. Cross-row gap tokens were refused by this runtime; a numeric cross-gap was accepted. The final [desktop](visual-concepts/brilliant-baseline-mockup-2026-11-06/project/Exports/aligned-1440.png) and [mobile](visual-concepts/brilliant-baseline-mockup-2026-11-06/project/Exports/aligned-390.png) canvases show the longer content without the observed collisions. Mobile actions wrap into two rows; the page grows instead of clipping later sections.

The final scene contains **769 objects**. Canvas heights read 4584.15px desktop and 6659.37px mobile; PNG heights round up to 4585 and 6660. The owned project and native canvas were inspected in the desktop editor, and the revision appeared without reloading. An initial stale accessibility index failed; a fresh screenshot-based observation recovered it. No new independent human-edit/undo test was performed on this larger scene. The earlier pilot's bounded owner-edit result remains separate.

## Raw HTML/browser acceptance

[Browser measurements](visual-concepts/brilliant-baseline-mockup-2026-11-06/browser-checks.json) cover the source and six raw export variants at 390/768/1440: **21 checks**, all with required section text present and zero page/console errors. Those checks do not imply working page behavior:

| Criterion | Observation |
| --- | --- |
| Reflow | The source passes all three widths. The 1440px HTML document overflows 390/768; the 390px document stays narrow at larger widths. Separate boards are not one responsive page. |
| Native-to-browser typography | The exported family does not select the source's exact Display/Text faces in Chromium; wrapping and metrics differ. The source and exported platform-font observations distinguish this mapping limitation from a general font-support claim. |
| Links | Raw linked text uses browser-default blue/underline styling, unlike the native canvas. Named section targets are absent: nine named links on the desktop export and five on mobile cannot resolve. The source's nine `href="#"` footer placeholders are counted separately; its named targets exist. |
| Structure | Exported content has zero heading and landmark elements, versus 19 headings and the real source landmarks. Our reconstruction/export path did not carry source semantics or fragment IDs. |
| Motion | Pulse/float animations and the source's reduced-motion branch were not recreated. A static export is not motion acceptance. |
| Flex snippet | Raw `htmlFlex` is a snippet, so opening it directly adds browser body margins. A minimal document/viewport wrapper with only `body { margin: 0 }` removes that matching-width overflow: [six wrapper checks](visual-concepts/brilliant-baseline-mockup-2026-11-06/flex-wrapper-checks.json) pass at the board's own width. The 1440px wrapped export still overflows 390/768. No export styles were patched. |

The full-document export retains useful colour variables, but it remains design handoff material. Semantic HTML, responsive composition, native font loading, links/focus, content ownership and motion still need implementation and acceptance in Astro. No representative Astro implementation was attempted in this test; the original concept remains unchanged.

The comparison page itself was checked at 390/768/1440. Both device controls work, every local link resolves, images load, and there is no document overflow or page/console error. [The review receipt](visual-concepts/brilliant-baseline-mockup-2026-11-06/review-checks.json) is separate from raw-export acceptance.

A complete normalized word-inventory check of both reconstructed exports matches the corresponding source, except for the deliberately omitted offscreen “Skip to content” link. [The inventory result](visual-concepts/brilliant-baseline-mockup-2026-11-06/text-inventory.json) supplements the section-text checks; it does not establish accessibility or correct link behavior.

## Effort and limits

At the recorded measurement checkpoint, this run used **57 MCP tool calls plus one tool-list request**, **1,038,613 HTTP request bytes**, **785,863 response bytes** and approximately **31.0 elapsed minutes**. [The summary](visual-concepts/brilliant-baseline-mockup-2026-11-06/effort-summary.json) and [per-call receipt](visual-concepts/brilliant-baseline-mockup-2026-11-06/effort.json) preserve the split. Thirty-two calls were exports, twelve were writes and five loaded focused knowledge batches. Exporting multiple intermediate states deliberately adds evaluation cost.

The transport totals exclude the contents of `textFile` inputs, model-side code/context/images, browser operations and later report/verification work. Elapsed time includes source extraction, helper development, mistakes, review and repair. Model input/output/cached tokens and cost are unavailable. The original HTML mockup's authoring time was not measured under matched conditions. Consequently this is **not a token-efficiency or speed ranking**.

This test corrects the earlier pilot's representativeness gap: the actual full mockup was now recreated and revised. It does not turn partial visual fidelity, manually repaired native flow or raw export success into production acceptance. The bounded conclusion is to retain Brilliant as an explicit native editing option while keeping browser-first concepts and native Astro proof.

## Repository verification

The audit-only follow-up was verified in an isolated worktree on `codex/design-review-surfaces`, retaining the shared checkout's `main` branch and existing database. Doctor, a clean lockfile install, helper syntax checks, documentation formatting, all 548 repository tests, the build and HTML integrity audit passed. The HTML audit captured ten public responses and checked nine HTML files. Its first run found the default `/about` link missing because this new worktree's CMS had zero page/post records. The checked-in seed was validated and applied with explicit disposable database targeting, conflict-skip and media downloads disabled; it created the two standard content entries, after which the same audit passed. No existing site database was reset or used as the fixture.

No generator, profile manifest, distributed skill, production route or runtime package was changed by this follow-up. The comparison and full-page export tests above are the acceptance evidence for the actual work; the repository checks guard the audit's integration, not Brilliant's visual quality.
