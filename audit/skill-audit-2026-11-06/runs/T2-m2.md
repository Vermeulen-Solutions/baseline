## Response and plan

### Reply to the owner (draft)

Thanks. In short, moving to Baseline is realistic for your site, but I can't give a trustworthy list of what is involved from the public URL alone. A public address lets me look at the pages and check whether an export plugin is installed. It does not let me see your drafts, event data, form settings or Elementor templates, and it does not authorise a full import. So the plan below is "audit first, then you choose". I have not changed or contacted anything.

**What I recommend (my default, to be confirmed by the audit)**

1. **Run a read-only audit of the current site.** I would look at the public pages in French and English on desktop and mobile. Then I would try the EmDash Exporter probe against your URL. To go deeper I need one thing from you: someone with plugin-install rights in WordPress installs the EmDash Exporter plugin (a ZIP I will point you to) and sends me the migration key privately, never in chat. If that can't be done, a standard WordPress export file (Tools, Export, All content) is the fallback. The audit gives you a report with counts, a list of every page type, and what to keep, improve or replace.
2. **Use Baseline's full EmDash CMS, not a static site.** Three volunteers editing in a browser, events with sessions, and venues shared across events all point to a relational CMS with browser editing. A static site would mean the volunteers edit files through Git, and it has no relationships between sessions, events and venues. I would only change this recommendation if the audit shows the content is much simpler than I expect.
3. **Rebuild the content model properly rather than copying WordPress data.**
   - Events, Sessions and Venues become separate linked record types. A session belongs to an event, and a venue is shared master data. Sessions and venues are not typed in as text inside each event.
   - French and English are stored as separate linked records per page or event, with French as the default language at plain URLs and English under `/en/`. They are not stored as duplicate "title_en" style fields. A relationship made once (for example event to venue) then works in both languages.
   - The admin screens would be labelled in the volunteers' working language, with simple folders, so they don't see WordPress leftovers.
4. **Rebuild the look, not the Elementor layouts.** Elementor layouts, widgets, forms and navigation are not converted automatically. I would use the live pages as the visual reference and rebuild them as clean reusable templates. If you want to keep your current design as a reference, you can export an Elementor "Website Template" kit from the dashboard (optional; skip it if you intend to change the look).
5. **Preserve your web addresses.** Every old address either stays the same or gets a permanent redirect, and I check this before launch.
6. **Launch with a freeze and a rollback.** There is a short editing freeze, a final comparison of what changed since the first capture, and a DNS switch with a quick way back to WordPress. WordPress stays available until you accept the result.

**Things that will take real effort, so you can weigh them**

- Events and sessions are probably buried in Elementor sections, custom fields or a plugin. They have to be extracted deliberately; the importer will not infer them.
- Anything that is not content needs a replacement: registration or contact forms, calendars, maps, search, newsletter sign-up, popups, and any events or ticketing plugin. Forms with a real cap or an inbox are the biggest question.
- Bilingual links between each French and English page must be checked after import; the language plugin (probably Polylang, which I will check) does not carry them over automatically.
- Images may need resizing and alt text before they are loaded.
- The volunteers need a short editing walkthrough, and I would test a real edit, save and publish with them.

**Decisions I need from you (nothing is needed to start the read-only audit except the first)**

1. Do you authorise the read-only audit, and can someone install the exporter plugin and share the key privately? Without it I can only audit the public surface.
2. Who will look after hosting, backups and the domain afterwards, and is there a monthly budget? This decides between the Node server option and Cloudflare, and I will explain both in plain terms when we get there.
3. Do you want to keep the current look, or are you open to a refresh? (Default: improve it while keeping your recognisable identity.)
4. Do events involve registration, limited places or payment? If so I will check whether the optional events plugin (`@vermeulen.solutions/eventual`) fits before building anything custom.
5. Which language should the volunteers work in, and who writes the English versions? A translation-dashboard plugin (LinguaDash) is optional if translation tracking matters.
6. How far should I take this after the audit? Options: (a) report only; (b) a local rebuild for your review, nothing published; (c) a full migration through launch. I will not deploy, transfer content or change DNS unless you authorise that step explicitly. If you pick (c), I would carry verified work through commit, push and the agreed deployment without asking again at each step.

### Plan behind the response (internal)

Routing used: AGENTS.md says an audit lead with an actionable plan and decisions, an audit does not authorise implementation, and release scope (commit, push, deploy, live acceptance) is settled during planning, respecting report-only scope. Task is a WordPress migration with more than one locale, a migration from an existing site, and editor roles, so it takes the **Standard** track (7 stages), not Express. Profile is chosen separately; recommended profile is `emdash`.

Scope of this turn: report-only. Nothing is implemented, no contact with the site owner's systems beyond what they authorise, no probe run (I was told not to use the web or commands).

Stage-by-stage plan if approved:

1. **Stage 1, brief and evidence** (`docs/wordpress-migration.md`, `wordpress-to-emdash-content`, `astro-site-design/references/migration-visual-audit.md`)
   - Route and page-type inventory per locale (French and English URLs, translated route pairs, missing translations, locale-specific navigation).
   - Source screenshots, desktop and mobile, including events list, event detail, session and venue displays, menus, forms and calendars.
   - Record theme, Elementor Site Settings, Theme Builder templates and display conditions, dynamic tags, popups, responsive overrides; identify Elementor Pro and third-party widgets.
   - Record language plugin and version (expect Polylang; check), language codes, default language, translation links, translatable post types and taxonomies.
   - Optional Elementor Website Template kit export, offered by default, owner may skip.
   - Media inventory (used and unused, sizes, duplicates, missing alt text) and plan for optimisation before copying.
   - Content-candidate register in `audit/content-candidate-register.md` (linked from `AGENTS.md`): events, sessions, venues, people or speakers, categories, news, testimonials, and anything repeated in Elementor sections or custom fields, each with evidence, grain, proposed model, migration method, confidence and open questions.
   - Forms inventory by tier: simple contact (native form to a form-to-email provider the client chooses) versus stateful (quotas, dedupe, inbox, export). Payment, uploads or CRM ownership are documented separately.
   - Source capture: probe, then `migration:wordpress capture` using a privately supplied migration key (or WXR fallback), then `assess` with `--kit` or `--kit-decision skipped`. Keys never go in chat, Git or command arguments. Keep the capture private.
2. **Stage 2, platform and hosting** (`emdash-site-setup`)
   - Confirm `emdash`; record editing personas (three volunteers), publishing latency, hosting (Node/SQLite with persistent media versus Workers/D1/R2), backups and costs.
   - Native Astro i18n with `defaultLocale: fr`, `locales: [fr, en]`, `prefixDefaultLocale: false`.
   - Check the plugin registry first: `@vermeulen.solutions/eventual` for events, `@swiss.ky/linguadash` for translation dashboards (optional); configure a sandbox runner if one is chosen.
   - Do the language preflight on a small disposable import: read the record by ID without a locale filter and run `migration:check-locale --expected-locale fr` (and `en`). Stop on any mismatch. Check translation groups and public routes per language. If the site lacks the checker command, adopt it through a reviewed Baseline update or do the same inspection manually and report it as manual.
3. **Stage 3, content and routes** (`emdash-content-modeling`, `building-emdash-site`, `wordpress-to-emdash-content`)
   - Model `events` (parent) to `sessions` (1:N child, `routable: false`) and `venues` as master data (reference field); people or speakers N:M if present. Enums become select fields. Fields use `translatable` appropriately; relations resolve across locales via translation groups.
   - Admin labels in the volunteers' working language, slugs in ASCII English, 2 to 4 nav groups, icons and descriptions; prune WordPress scratch fields afterwards.
   - Decide, using the composition decision tree, whether editors need blocks to add or reorder sections; do not assume.
   - Every archetype gets source, target, migration method, route, container/breakout model, owner. Gate: nothing repeated left unclassified.
4. **Stage 4 and 4.5, art direction and calibration** (`site-art-direction`, `astro-site-design`)
   - Preserve, improve, replace record; decide refine versus overhaul with the owner. If significant, present the design surface choice once (HTML/browser concepts by default; Brilliant, OpenPencil, Penpot as named options; OpenDesign optional) and compare two or three structurally distinct directions.
   - Save the Art Direction Record in `AGENTS.md` and pass `npm run check:art-direction -- --require-record` before any site-specific visual work. Calibrate on `/_styleguide` and write `audit/component-calibration.md`.
5. **Stage 5, representative pages**: shared shell plus events list, event detail with sessions and venue, a standard page, in both languages, at mobile, intermediate and wide widths; run Impeccable; compare to source screenshots.
6. **Stage 6, complete and verify**: import through the native wizard (`/_emdash/admin/import/wordpress`) after the locale proof, then media copy and URL rewrite; fill the supplemental mapping for implicit types (sessions, venues) with a custom extraction where the importer cannot infer them; forms replaced; 301 redirects; a real editor test (create, edit, translate, save, reload, publish an event with sessions and a venue, as a volunteer). Run `doctor`, `verify:fast`, `verify`, `build`, `audit:html`, `migration:verify --scope full`, content-inventory reconciliation by type, locale and status. Report only checks actually run; mark content reconciliation, editor save and design acceptance as unverified until evidenced.
7. **Stage 7, cutover** (`emdash-production-cutover`, `docs/migration-cutover.md`): recovery point first; editing freeze (24 to 48 hours); delta reconciliation (re-import is not sync; new, modified, deleted, slug-changed entries handled deliberately); lower DNS TTL; protect MX/SPF/DKIM/DMARC; DNS switch; watch for in-flight form submissions; rollback by reverting DNS; keep WordPress read-only until traffic stops.

Release completion (per AGENTS.md): to be settled with the owner at plan selection. Options are report-only (this turn), local rebuild for review, or full release. Content transfer, production writes, deployment and DNS each need authorisation covering them; a Git push does not move CMS data, and a reachable setup page is not proof of working sign-in. Once release is authorised, commit, push, deploy and live acceptance proceed without repeated prompts, and the final report states the actual commit, branch, deployed URL and what was observed.

Assumptions (labelled): the language plugin is Polylang; events, sessions and venues are likely custom post types or Elementor/ACF repeaters; the owner is not technical; admin working language is probably French. All to be confirmed in the audit.

Open risks: no exporter access means the audit is public-surface only; unknown plugins (events, forms, calendars) may need replacements; limits apply (10,000 records per collection phase, 500 URL entries per acceptance manifest, so batches if larger).
