### Reply to the owner

Short version: yes, this is a normal migration, and your site (bilingual, events with sessions and venues, three volunteer editors) maps well onto Baseline's EmDash profile. I can only see the public pages so far. To give you a firm audit I need a few things from you, listed below. Nothing will change on your live site until you approve a plan.

**What moving to Baseline would involve**

1. **Platform: I recommend the EmDash CMS profile.** Baseline offers three options: plain files (static), files edited through a browser editor that saves to Git (static + Sveltia), and a full CMS (EmDash). Your site has structured events with sessions and venues and needs two languages edited by volunteers in a browser. Static options cannot do relational data or live editing. EmDash has forms, a live editing view and relations. The cost is hosting a small server (Node with SQLite and file storage, or Cloudflare), plus backups and sign-in setup. This is a recommendation, not a decision yet.
2. **Content model.** Events, sessions and venues become separate linked content types instead of text typed into pages. An event has many sessions. Each session points to a shared venue record, so a venue's address is typed once. Fixed categories (event type, status) become dropdowns. Elementor's repeated blocks (speaker lists, schedules, partner logos) will be sorted into: its own content type, ordinary page text, a site setting, or dropped. I record this in a content-candidate register. Separately, I will check whether a ready-made events plugin from the EmDash registry (Eventual) covers your needs before we build custom event types.
3. **French and English.** Each language version of a page or event is its own record, linked to its translation. There are no duplicated "title_en" style fields. Each language can be published independently. French stays at the root URL with English under /en/ (assuming French is your default; please confirm). Before any bulk import I test a small sample and check that each imported record is really tagged with the right language, because French-looking text does not prove the record says French. A mismatch stops the import. I would also check which translation plugin you use (likely Polylang), since its translation links must be mapped explicitly and are not guaranteed to import.
4. **Elementor.** Content and media come across, but Elementor's layouts, widgets and Theme Builder templates do not convert automatically. The pages are rebuilt in Baseline's own design system, using your current site as the visual reference. You choose how much of the current look to keep: refine, significant overhaul, or replace. If you want to keep the current design as a reference, Elementor can export a Website Template kit. That is optional, and you can skip it.
5. **The three volunteers.** They would edit in the CMS forms and live view instead of Elementor. This is a real change in how they work. I would define their roles and review/publish steps, rehearse their typical tasks (add an event, add sessions, edit in French then English) before launch, and write the editor handoff guide.
6. **Everything else on the site that is not content.** Forms (contact, registration), search, popups, newsletter and event registration or ticketing, embedded maps and calendars, and SEO plugin data. Each gets classified and replaced deliberately. If registrations have capacity limits or need an inbox, that is a different, stateful kind of form from a simple contact form. Any payment, file upload or external system is documented separately.
7. **Addresses and search ranking.** Every old URL is inventoried and either kept or given a 301 redirect, and then checked automatically.
8. **Launch.** Content freeze, final sync, DNS switch, rollback plan, and keeping your existing mail DNS working. Moving the code and moving the content are separate steps, and DNS is a third.

**What I need from you (small first group)**

1. **Access.** Is someone able to log into the WordPress dashboard and install a plugin? The first-party EmDash Exporter plugin is installed from its official release ZIP. Its migration key must be passed to me privately, not by chat or email. Fallback is Tools > Export > All content (an XML file). This is what lets me give a real, evidence-based audit.
2. **Who edits and how.** Are the three volunteers comfortable with a new editor? Do you want a review step before publishing?
3. **Languages.** Which is the default language, and are all pages translated or only some?
4. **Design.** Keep, refine or replace the current look? Do you want an Elementor template kit export as reference (optional)?
5. **Hosting and budget.** Where should the site run and who looks after it afterwards (backups, sign-in recovery)? Do you have a target date?
6. **Release scope.** Is the aim a local, reviewable preview first, with deploy and DNS handled as separate approvals?

I can run the read-only parts without your involvement. I will not import, deploy, change DNS or contact any plugin or hosting vendor until you say so.

### Plan behind the response (for selection, nothing authorized beyond this audit)

**Track and profile.** Standard track (migration, two locales, relations, volunteer roles). Recommended profile: emdash. Alternatives to present once: static + Sveltia (cheaper to host, but no relational events, no live canvas, and edits go through Git); static (developer-only edits). Record the choice and rationale in AGENTS.md or an adopted PROJECT.md.

**Phase 0 - Public-only evidence (read-only, allowed now).** Probe the URL with `migration:wordpress probe` (after confirming that script exists in the installed site; if not, treat as needing reviewed additive adoption and continue with manual steps). Inspect the rendered site at desktop and mobile: route inventory, language switcher and URL pattern, event list and detail pages, venue pages, forms, popups, plugins visible in markup. Output: preliminary route inventory and a first content-candidate register (audit/content-candidate-register.md, linked from AGENTS.md). Limits: no private/draft content, no postmeta, no builder data, no plugin settings visible from a public URL.

**Phase 1 - Owner decisions (asked in chat, grouped as above).** Access, editors, languages, design stance, hosting and ownership, release scope.

**Phase 2 - Source capture and assessment (needs owner access).** Install the EmDash Exporter 1.2.0 or later, migration key via a private channel, keep WordPress and media available throughout. `migration:wordpress capture` into an ignored backup directory, then `assess` (with the Elementor kit or `--kit-decision skipped`). Review recovered copy, unsupported widgets, dynamic tags and source exclusions. Record theme, builders, language plugin and version, translatable post types and taxonomies, menus, per-language slugs. Existing backups of the WordPress site stay in place; a capture is not a full backup.

**Phase 3 - Language preflight.** Set native default and supported locales with `prefixDefaultLocale: false`. Trial a small representative export in a disposable destination. Read the imported record by ID with no locale filter and run `migration:check-locale` (or the manual equivalent if absent). Stop on any mismatch, repair in the trial, do not reset a populated destination or add parallel language fields.

**Phase 4 - Content model (emdash-content-modeling, wordpress-to-emdash-content).** Collections: events, sessions (non-routable, child of events), venues/locations (shared master data), people if speakers/organizers recur, pages, news if present. Relations via translation groups so links resolve per language. Select fields for fixed categories. Editor-facing labels in the volunteers' working language (French if so confirmed), slugs in ASCII English. Pruning of legacy scratch fields after hydration. Check the Eventual plugin first; use a bespoke plugin only if requirements prove it necessary. Consider LinguaDash only if volunteers need translation dashboards. Assess blocks (editable page sections) per the audit guidance only where the volunteers demonstrably need to add or reorder sections; missing evidence is reported as missing, not assumed.

**Phase 5 - Design (site-art-direction, astro-site-design, impeccable).** Decide refine versus overhaul. For an overhaul, compare two or three concepts (default HTML/browser; present Brilliant, OpenPencil, Penpot once if a canvas is wanted). Save the Art Direction Record in AGENTS.md and pass `check:art-direction --require-record` before any site-specific visual work. Calibrate on /_styleguide, record in audit/component-calibration.md. Rebuild event list/detail, venue and page archetypes, then a critique pass.

**Phase 6 - Import and rebuild.** Import via the native wizard at /_emdash/admin/import/wordpress, then media copy and URL rewrite. `media:prepare` for images. Replace forms by tier. Extract sessions and venues from whatever source shape they take (custom post type, ACF repeater, builder section or plugin table) with an idempotent mapping, preserving source IDs. Build navigation, redirects, SEO.

**Phase 7 - Verification and editor acceptance.** `npm run doctor`, `verify`, `build`, `audit:html`, `migration:verify --scope full` with a URL inventory, content count reconciliation by type, locale and status. Rehearse the volunteers' real tasks including save, reload, publish, in both languages. Report only checks actually run.

**Phase 8 - Release (needs explicit authorization for each).** Content freeze and delta reconciliation (docs/migration-cutover.md), recovery point and backups, editor handoff (docs/editor-handoff.md), deploy preview, content transfer, sign-in setup, DNS cutover, rollback triggers, `site:register`. Include in the plan: verified changes committed, pushed to the agreed repository and branch, deployed to the agreed target, live acceptance. Release destination and authority are an open item to settle at plan selection; this audit request alone is not deploy or DNS permission, and release authority would not cover content imports, production writes or messages.

**Decisions needed from the owner (summary):** platform profile; default language and translation scope; keep/refine/replace design; hosting and who maintains it; volunteer roles and review flow; whether to supply WordPress dashboard access and the optional Elementor kit; release scope.

**Risks and caveats to state honestly:** public-URL audit cannot see unpublished content, plugin data, or builder structure; Elementor layouts and plugin behavior are rebuilt, not converted; event registration or payment features, if any, need separate treatment; WordPress statuses such as pending, private and scheduled may import as drafts and need review; translation links from Polylang are not assumed to import; re-running import is not synchronization.
