## Answer

**Mechanism: a container query (row 2 of the "Choose the mechanism" table in astro-site-design/references/responsive-architecture.md).**

Why not the other two rows:
- Intrinsic layout (row 1) cannot do it alone. The card has two distinct layouts (image beside text, or image above text) and has to switch between them on the width of its slot.
- A media query (row 3) is the wrong tool. The same card sits in a grid cell, a narrow sidebar and a full-width band, and the viewport width says nothing about which slot it is in. At 1440px the sidebar card is still narrow and the feature card is wide.
- Row 2 is the case the skill describes: two layouts, with inline space that changes independently of the viewport (sidebar, grid cell and full-width feature).

Rules from the reference that shape the CSS:
- Query an ancestor, never the card itself. The slot wrapper is the container, and the card's descendants respond to it.
- Put the container on the slot, not on the whole grid. On the shop page each grid `<li>` is the container, so each card switches at its own width and not the grid's.
- Name the container (`card-slot`), because containers can nest (the band sits inside page layout wrappers).
- Keep the narrow layout (image above text) outside `@container` and enhance at `min-width`. Without container support, or with no container, the card is still readable.
- Use `minmax(0, 1fr)` on the text track so long titles cannot push the track wider than its slot.
- Do not use fixed heights, and do not use the `:has(> &)` trick to make the card's parent a container.
- Keep the CSS in the global stylesheet's named components layer (AGENTS.md: "Keep CSS in named base or components layers"), not in a scoped `<style>` block, because Tailwind v4 component styles are a separate context. Use the existing spacing and type tokens (`--spacing-grid`, `--spacing-content`) and not one-off values.

Wrapper markup. The caller or structural component owns the wrapper, so the contract is visible. The component renders the card, and each placement supplies a slot wrapper:

```astro
<!-- Shop: semantic list, each <li> is the slot -->
<ul class="product-grid" role="list">
  {products.map((p) => (
    <li class="product-slot"><ProductCard {...p} /></li>
  ))}
</ul>

<!-- Article sidebar -->
<aside aria-label="Related products">
  <div class="product-slot"><ProductCard {...product} /></div>
</aside>

<!-- Homepage feature band -->
<Section>
  <div class="product-slot"><ProductCard {...featured} /></div>
</Section>
```

CSS, in the components layer of `src/styles/global.css`:

```css
@layer components {
  /* Grid uses intrinsic columns (row 1); each item is its own query container. */
  .product-grid {
    display: grid;
    grid-template-columns: repeat(auto-fit, minmax(min(100%, 16rem), 1fr));
    gap: var(--spacing-grid);
  }

  .product-slot {
    container: product-slot / inline-size;
    min-inline-size: 0;           /* a containment box must not collapse or overflow its track */
  }

  /* Narrow default: image above text. No query needed. */
  .product-card {
    display: grid;
    gap: var(--spacing-content);
    align-content: start;
  }
  .product-card__media img { inline-size: 100%; block-size: auto; }
  .product-card__body { min-inline-size: 0; overflow-wrap: anywhere; }

  /* Enough room: image beside text. Threshold to be measured, not assumed. */
  @container product-slot (min-width: 36rem) {
    .product-card {
      grid-template-columns: minmax(10rem, 2fr) minmax(0, 3fr);
      align-items: start;
    }
  }
}
```

Notes on the choices:
- `36rem` is a placeholder. The reference says an example value is not a universal breakpoint. I would set it at the width where the real card (longest expected title, price, button) stops fitting side by side, by resizing the slot in the browser.
- The shop grid: three columns on desktop keeps each cell narrow, so cards stack vertically. If the shop grid ever drops to one wide column on a tablet, the card goes horizontal there without any extra rule.
- The sidebar stays below the threshold, so its card is always stacked. The feature band exceeds it, so its card is always side by side.
- `inline-size` containment means the wrapper no longer sizes to its content. I would inspect it in the real layout, because a shrink-wrapped wrapper such as a flex or inline-block parent can collapse.
- The image goes through `ResponsiveImage` (or native Astro `Image`/`Picture`) with accurate `sizes` for each placement. The wide band and narrow stacked card need different `sizes`, so the component takes a prop or uses a container-aware default. The image's reserved space uses an `aspect-ratio`, so a missing or unusual ratio does not shift the layout.
- The component stays presentational. It holds no queries, widgets or storage (the astro-site-design "Platform presentation boundary").
- DOM order stays image first, then text, in both modes. The layout rearranges visually with grid only, so there is no source-order mismatch for focus or reading order.

**What I would check before calling it done** (from the reference's "Review with unpredictable content" list and the skill's verification loop):
1. Render all three real placements (shop grid, article sidebar, homepage band) in the browser and confirm each shows the intended layout. The sidebar is the narrowest real placement and must be tested there, not only at phone and desktop presets.
2. Widths just below and just above the container threshold, found by resizing the slot. Check intermediate widths, plus 375px, 768px and 1440px, and a case wider than the content maximum.
3. Zero horizontal overflow, clipped text, awkward single-word heading wraps, and sensible outer gutters at those widths.
4. Stress content: very long titles, unbroken strings or URLs, a missing image, odd image ratios, more and fewer cards, and translated (French-length) strings. Check the grid's tracks do not exceed their slot (`minmax(0, 1fr)`).
5. Disable the `@container` rule and confirm the stacked fallback is still readable (the narrow-default-outside-the-query rule).
6. Confirm the container is on the slot (`li` or wrapper) and not on the grid, so cards in one grid can switch independently. Confirm no wrapper collapsed under `inline-size` containment.
7. 400% browser zoom (reflow without clipping or page scroll), 200% text resizing and increased text and paragraph spacing.
8. Keyboard and focus: visible focus rings, the card link target size, and focus order matching the visual order in both layouts. Meaningful images have alt text. Run the contrast check on text over the surfaces used in the band and sidebar. Manual checks, not only automated ones, per the skill's WCAG 2.2 AA default.
9. Images: the `sizes` attribute is accurate per placement, the above-the-fold band image uses `loading="eager"`/priority where relevant, and there is no layout shift.
10. Project checks per package.json scripts (on this EmDash foundation: `npm run doctor`, `verify:fast`, `verify`, `build`, `audit:html` against the fresh build). Inspect the final result in the browser on the built artifact. Also confirm that a content change to a product shows up in all three instances (shared-instance behavior), and that CSS is token-based with no IDs or `!important`.
11. Report only what I actually ran and any acceptance limits (for example, if a browser or build was not available).
