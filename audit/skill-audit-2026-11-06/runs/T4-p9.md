## Plan

Classification: a scoped day-2 spacing change on a launched static site. This is site work, not Baseline maintainer work. It is no new-site track (no Express/Standard). Start at the earliest affected stage, which is implementation and verification. Do not rerun discovery or art direction.

1. Orient (read only).
   - AGENTS.md routes "tokens, layout, components, day-2 visual changes" to docs/site-working-rules.md, docs/design-framework.md and docs/native-composition.md. Read them before editing.
   - The new-site-workflow router (SKILL.md) sends "spacing on an existing site" to references/site-maintenance.md. Read that, plus astro-site-design/SKILL.md for implementation.
   - Do not load art-direction canvas skills (Brilliant/OpenPencil/Penpot/OpenDesign) or site-art-direction. There is no concept pass and no redesign. Do not load impeccable unless a rendered critique is wanted. The change is bounded, so a before/after inspection is enough.
   - Skip all EmDash/CMS skills. This is a static profile.
   - Read the site's own generated AGENTS.md and baseline.config.json (profile receipt). Read the saved `## Art Direction Record`, especially Token Physics / Spatial Density. Also read package.json scripts. Static sites often lack some Baseline commands (`design:tokens`, `check:art-direction`, `verify`). For a missing command, use the site's own equivalent or do the check manually and report it as manual. Do not install tooling.
   - Check git status and the current progress/handoff notes.

2. Turn the request into an observable result.
   - Target: on phones, the gap between the class cards on the Classes page is smaller, by a modest amount ("a bit", for example about 20-25% tighter).
   - Preserve: desktop and tablet spacing, card internals (padding, radius), copy, navigation, and every other page's grids. The owner said everything else is fine, so there is no wider redesign and no art-direction rewrite.
   - Ask no questions. The only open choice is the exact amount, so use a labelled working assumption of about 0.75x. Mention it in the reply so the owner can ask for more or less.

3. Find the actual owner of the gap (inspect the source before editing).
   - Open src/pages/ for the Classes route and see how the class cards are composed: `<Section>` > `<Container>` > `<Grid>` > `<Card>`.
   - Check whether the gap comes from the Grid's grid gap (`--layout-grid-gap` / `--spacing-grid`), a `gap` prop or a `gap-*` utility, flow or `space-y` margins (the double-ownership case to avoid), Card margins, or a Section/Container stack gap.
   - Read src/styles/global.css, the shell policy (`SiteShell spacingPolicy`, which should be automatic-v2), and the Card and Grid components. Search the consumers of Card and Grid.
   - Also check whether the cards stack in one column on the phone. Grid gap tightens the space between stacked cards, but only if the Classes grid, not the Card's own padding or Section padding, is the source of the "too far apart" feeling.
   - Also check whether the same Grid or Card is used on other routes. The gap relationship should be changed only where the owner asked.

4. Pick the smallest scope (hierarchy in site-maintenance.md / design-framework section 8).
   - Preferred: change this one instance, the Classes page Grid. Use the `gap` prop, e.g. `gap="calc(var(--layout-grid-gap) * 0.75)"`, or a local layered alias. If the cards live in a named region, use a contextual `:where(.classes-region)` alias in `@layer components`.
   - Do not touch `@theme` `--spacing-*` scales, the root `--layout-grid-gap` alias (it would change every grid on the site), a lane preset or `--space-scale`, or shared Card/Grid defaults. Nobody asked for those.
   - To make the change phone-only, use a fluid expression, not breakpoint soup or arbitrary pixel values. The tokens are already fluid (`--spacing-grid` is 20px at 320 and 36px at 1280), so a multiplier tightens narrow widths in proportion. If the owner's request really needs phone-only (desktop untouched), use a single deliberate layout media query or container query scoped to the Classes grid, and say so. Avoid `!important`. Keep all CSS in named layers with `:where()` for contextual defaults.
   - Do not add margins on top of the gap. Do not add flow margins or `space-y` to the gapped Grid, because each relationship has one owner.
   - Art direction gate: this preserves the accepted visual system (Spatial Density) and is a bounded instance tweak. Check that the 0.75x gap does not contradict the saved Token Physics. If core physics would shift (it should not), align the Art Direction Record. Otherwise leave the record unchanged. Run the art-direction check if the site has it. If the change counts as visual source, a record should already exist from launch.

5. Preview and apply.
   - Where the site has `design:tokens` and the change is token or alias based, preview with `npm run design:tokens -- --set "--root:--layout-grid-gap=calc(var(--spacing-grid) * 0.75)" --json`, review it, then `--write`. Only do this if a site-wide alias were the right scope, which it is not here. For a one-instance prop or regional alias, edit the Astro or CSS source directly.
   - Make the edit. Keep diffs minimal. No unrelated refactors, no content or navigation changes, no new documents.
   - On a static site the change goes straight into Git-owned source. Note that code changes do not touch content files.

6. Verify (match acceptance to the change).
   - Run the site's installed checks from package.json: `npm run verify` (lint, art direction, token audits, typecheck, tests) if present, then `npm run build`. If any check is missing, use an equivalent or report a manual check.
   - Rendered check in a browser on the built or dev output: the Classes page at 390x844 (the owner's phone case), plus 375, an intermediate width (about 768) and desktop (1440). Confirm the gap is measurably tighter at phone widths (measure the computed grid gap before and after), cards do not touch, nothing overflows horizontally or clips, and the intermediate and wide layouts match the "before" (unchanged unless the multiplier deliberately applies everywhere).
   - Confirm the reference compositions are unchanged: other pages and grids, copy, navigation, and Card internals. Check one other page that uses Grid or Card to prove it is unaffected.
   - If a shared component default was changed anyway, test every consumer. The plan avoids this.
   - Report only checks actually run. Say what was manual and what remains unverified (for example, real-device phone rendering).
   - Keep a short requirement-to-evidence record for handoff: requested result, route and viewport, change, observed evidence, status.

7. Release.
   - Use the existing release scope. The site is launched, so find out whether the owner or earlier instructions authorize commit, push and deploy. If so, commit with a clear message, push to the named branch and run the site's normal deploy, then check the live Classes page on a phone-width viewport. If no authority is established, stop after local verification and state the next action precisely. Do not guess a deploy target.

8. Reply to the owner in plain language (the site's French-first copy is untouched; the owner emails in English, so reply in English). Say what changed (the card spacing on phones, on the Classes page only), the amount, and offer to adjust it. No extra changes.
