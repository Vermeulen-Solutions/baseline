## Plan

Classification: scoped day-2 maintenance on a launched static site, which is a visual change. It is not a new build or redesign, so I would not replay Stages 1-4, the concept pass, the design-surface choice (Brilliant/OpenPencil/Penpot), spacing-choice prompts or discovery. The accepted art direction stays as is. AGENTS.md says "A local component adjustment for one website is still site work", and new-site-workflow says "Scoped changes start at the earliest affected stage and reuse established decisions". The profile is static: skip every EmDash/CMS skill and command. Content, copy, navigation and the other pages must not change.

1. Orient and load.
   - Read the site's own AGENTS.md. It is the generated static one, not the starter root one I have. Confirm the `## Art Direction Record` is present, in particular Token Physics / Spatial Density, and the site's installed commands.
   - Read `baseline.config.json` to confirm the profile is static or static-sveltia. Read `package.json` scripts. Only run Baseline-named commands (`verify`, `build`, `check:dev-tools`, `design:tokens`, `check:art-direction`, `test:design`) if the site actually has them. Otherwise use the site's own equivalents and report the check as manual.
   - Read the adopted PROJECT.md and the handoff if present. Missing optional docs do not block work.
   - Docs read before editing, per the AGENTS.md routing table row "Tokens, layout, components... or day-2 visual changes": `docs/site-working-rules.md` (Day-2 client changes section), `docs/design-framework.md` (section 8, contextual spacing maintenance, and the Section/Container/Grid ownership table) and `docs/native-composition.md`.
   - Skills: `new-site-workflow` (the scoped-maintenance loop, with `references/site-maintenance.md` for spacing and shared components) and `astro-site-design` for implementation and verification. I would load `impeccable` only for a bounded critique if the result looks off. I would not load `site-art-direction`, any design-surface skill, any EmDash skill, `wordpress-to-emdash-content`, `references/design-iteration.md` or media-preparation (no images are involved).

2. Art Direction gate.
   - This is visual work, but a small spacing tweak that stays within the saved Art Direction Record needs no new record or concept pass. Verify the record exists and passes `npm run check:art-direction -- --require-record` if that command exists.
   - Do not add `audit/design-gate-exceptions.json` entries; never exempt client pages.
   - If the tweak would change the record's core Spatial Density physics, align the record. For a one-region tightening it should not.

3. Establish the observable result and what must be preserved.
   - Result: on phone widths, the Classes page class cards sit closer together.
   - Preserved: desktop and tablet gaps on that page, other pages' grids (Home, Teachers, etc.), card padding and content, copy, navigation, links and accessibility behavior.
   - Resolve ambiguity myself. The owner said "a bit", so choose a modest reduction, for example about 20-25% on the gap. Prefer deciding and reporting over asking, since nothing consequential is missing.

4. Trace the affected surfaces. Find what actually owns the card gap on mobile.
   - Open `src/pages/classes.astro` (or equivalent) and look at how the class cards are composed: `Section` > `Container` > `Grid` > `Card`. Check whether the gap comes from Grid's grid gap (`--layout-grid-gap` / `--spacing-grid`), Container's content gap, Section's container gap, per-card margins, or flow margins double-counting a gap.
   - Check what else consumes the same owner. If the class Grid is also used for other cards, a root alias or token change would leak. Read `src/styles/global.css` for the `--layout-*` aliases, and `Grid.astro` and `Card.astro`. Search the consumers of Grid and of any shared class used here.
   - "Too far apart" on phones can also mean the vertical gap in a stacked single column, a Card margin or padding, or the Section/Container stack gap. Confirm with a rendered measurement at about 375-390px rather than guessing.

5. Choose the smallest scope, following the hierarchy in design-framework section 8 and site-maintenance:
   - First choice: a primitive `gap` prop on this page's Grid, for example `<Grid gap="calc(var(--spacing-grid) * 0.75)">`, or a `gap-*` utility. This is one instance, so other pages are untouched.
   - If the tightening should apply only on narrow screens and the fluid token does not already express that, do not add media-query breakpoint soup. Use the fluid token with a coefficient. Fluid `--spacing-grid` already shrinks on phones, so a fixed multiple scales down across widths. If the owner wants desktop unchanged, a layered regional alias scoped to the Classes region (`@layer components { :where(.class-cards) { --layout-grid-gap: ... } }`) with a deliberate container or media rule is the fallback. Record a concrete reason for it.
   - Not allowed: global `--spacing-*` or `--space-scale` changes, a new lane preset, root `--layout-grid-gap` changes (all grids would move), arbitrary pixel values like `gap-[13px]`, `!important`, adding flow margins on top of a gap, or editing Card defaults when only this page is requested.
   - If the gap really comes from a shared Card or Grid default and the owner would want it everywhere, that is a different, larger change. Report it instead of broadening scope.
   - CSS stays in the named `@layer base` or `@layer components`, contextual defaults use `:where()`, and tokens remain the sole configuration store.

6. Preview and apply.
   - If the change is a token or alias edit, preview first: `npm run design:tokens -- --set "--root:--layout-grid-gap=..." --json` (or the regional form), review the diff, then re-run with `--write`. Skip `--write-calibration` unless `audit/component-calibration.md` is maintained and the token source changed.
   - If it is a prop or utility on the page, edit just that route file.
   - Work on a branch if the site uses branches. Do not commit or push without an authorization that covers it.

7. Verify, matching the acceptance to the change.
   - Run the site's `verify`, or its equivalents (lint, typecheck, token and art-direction checks), and `build`. Say if any command is missing.
   - Use rendered browser inspection of `/classes` at narrow (375/390), intermediate (768) and wide (1440) widths. Confirm that the mobile gap is visibly smaller by the intended amount and that there is no overflow, clipping or awkward wrapping. Confirm that card padding, content and focus rings (`.clickable-parent` / `.focus-parent`) are unchanged.
   - Check the preserved set: wide and tablet layouts of `/classes`, and one or two other pages that share Grid or Card (Home, Teachers). They should be pixel-identical, which shows the change did not leak.
   - Use a fixed built artifact for the final review. A build or typecheck alone does not prove the rendered result. Record actual checks run and anything left manual.

8. Release and handoff.
   - Short completion record: requested result (mobile gap on Classes) / route and viewports / change made (owner, prop or alias and value) / evidence observed / status.
   - Release: this is a small change on an already-launched static site. Establish the agreed target. Commit, push and deploy (rebuild of `dist/`) only if that authority already exists in the owner's or project's decisions; otherwise leave a reviewable local result and name the one missing action. Report the actual commit, branch and deployed URL only if they were observed. No CMS or registry steps apply to static.
   - Reply to the owner in plain language (in the language the user uses): what changed, on which page, and that desktop and the other pages are unchanged.
