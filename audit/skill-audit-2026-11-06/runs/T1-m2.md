## Plan

### 0. Orientation and decisions made up front

- This root has no baseline.config.json, so it is the Baseline generator and EmDash starter. It is not the site. It is also not an authorized place to build the yoga site in place.
- Intent: this is site work (a complete new site), not Baseline maintenance. CONTRIBUTING.md is not needed.
- Track: Express, per new-site-workflow branch 4. It is greenfield, 5 routes (at most 6), one locale (French), at most 3 collections, with no migration, roles, integrations, auth or payments. Express keeps every gate. It only consolidates decisions into up to three checkpoints. I would say once that it moves to Standard if any of these appear: a booking or payment system, a second language, or a migration from an existing site.
- Profile: recommend `static`. Reason: the developer maintains the content and the owner emails changes, so there is no non-technical editor who needs a browser CMS. Static means typed Markdown, Astro static output, a cheap host, and a rebuild to publish. I would ask the owner one plain question: "Do you ever want to edit the site yourself in a browser, or is emailing changes fine?" If the owner wants browser editing, the fallback is `static-sveltia` (needs a GitHub repo and an OAuth proxy or PAT). EmDash is not warranted. Profile and track are separate choices. I would record the profile as a labelled assumption until the owner answers.
- Language: French only, one locale. Default locale fr, no prefix. This is an Express-compatible single locale. The owner's working language is a separate record, and I would ask for it. Voice must be settled: "je" versus the studio name, and *vous* versus *tu*. Typographic French spacing (before `:`, `;`, `?`, `!`) applies throughout. The assistant talks to the user in English, while the site stays French-first. I would add a French `lang` setting and French metadata.
- Project setup: from this Baseline checkout run `npm.cmd run init:profile -- --profile static --out <new empty dir>`. I would not prune this repo in place. Then work only in the generated folder, using its generated AGENTS.md and its own `package.json` scripts. On Windows PowerShell use `npm.cmd` and `npx.cmd`. First `npm.cmd install` creates the lockfile, and `npm.cmd ci` is used after that. Before running any command I check that the generated site has it. The EmDash-only commands (`doctor`, `audit:html`, `site:register`, `db:*`, registry and screenshot baselines) are skipped. No CMS dependencies are added to satisfy a check.

### 2. Checkpoint A: Stages 1–3 (brief, platform, content and routes)

Work:
- Stage 1 (core discovery). Reuse what was supplied. Write a short synthesis in AGENTS.md (the established home): priority visitor, offer, primary action, lead message, strongest evidence, biggest risk, missing material with owners. Keep an evidence inventory with a claim → source → permitted use ledger. Teacher credentials and testimonials must be supplied and permitted. Nothing is invented, and unsupported proof sections are omitted.
- Stage 2. Record the profile rationale: static, editing owner is the developer, rebuild publishes, static host with `dist/` and a real 404 (no SPA rewrite), `SITE_URL` to set, and the form or mail decision for contact.
- Stage 3. Route inventory: `/`, classes, timetable, about, contact. Define typed Zod collections in `src/content.config.ts` with Markdown in `src/content/`. Likely models: a classes collection (one template, so one archetype), the timetable as file-owned structured data or a single entry (not a CMS collection), and plain pages for home, about and contact. This stays within 3 collections and about 4 archetypes. Write a compact page brief per archetype. Draft real French copy at real length, marked draft with its owner. Choose the representative route by journey priority. Likely the home page, or the timetable if it is the key task. Classify every repeated element: classes, timetable slots, teacher bio, FAQ. Run `media:prepare` on the logo and photos. The logo goes through as an SVG `preserve` with a reason, the photos through the photo preset. Staging goes under `.baseline/backups/`, originals stay outside Git, and `alt` text is written in French.
- Gate: a brief, synthesis, evidence inventory with gaps and owners; known runtime and locale model; every archetype has a source, representation, route, container model and owner. Deferred items are marked explicitly.

What I would ask the owner in chat (one to three related questions at a time, with a recommendation, skipping anything already answered):
1. Purpose and audience: who is the ideal student (beginners, a local studio crowd, online), and what should a visitor do first (book a trial, see times, email you)?
2. Operation: "Is emailing me changes fine, or do you want to edit in a browser?" This is the profile question. Add: how fast must a timetable change go live? Should visitors book or pay on the site, or just contact you? This is the Standard-escalation check.
3. Contact: where should enquiries go? A mailto, an external form or a booking service. I would not simulate a working submission, so form delivery is recorded as an external-service decision.
4. Content and voice: which text, bios, class descriptions, prices and the timetable exist and who supplies the rest? Do you speak as "je" or as the studio? Use *vous* or *tu*? What is your language for me to write to you in? Which claims or testimonials may be published?
5. Assets: confirm the logo is the master (preserve, do not redesign) and which photos may be used and credited.

Checkpoint A handoff, stated in chat: the profile and hosting, collections and routes, the Layout spacing explanation (shared responsive spacing, balanced density by default; ask about compact or spacious only if it affects a visual decision), and the recommended visual direction in plain language. Continue without an extra approval stop when work is authorized, and label assumptions as assumptions.

### 3. Checkpoint B: Stages 4–4.5 (art direction, design surface, calibration)

Design surface (the concept checkpoint for a new site): no canvas or design tool was mentioned and none is settled. So the default is HTML/browser concepts. I would state once, in one short sentence, that an editable canvas is also possible: Brilliant (the recommended editable option), OpenPencil (local) and Penpot (shared cloud review), with OpenDesign optional. I would not require an answer, and I would continue with HTML. I would ask the single reference question: "Are you short on visual references or inspiration?" If yes, offer the prompt libraries once (and run `npm run design:prompt-check -- <file>` on any selected prompt, adapting it with `external-prompt-adaptation.md`). If no, do not repeat the offer. I would ask for 2–3 sites the owner likes, and what they dislike. If the answer is only an adjective ("calm", "modern"), I would ask for a feeling or an example first.

Concept pass: 2–3 structurally distinct directions, not colour skins, for the representative route. They live in `audit/visual-concepts/<round>/direction-a.html`, `b`, `c` plus one `index.html` comparison page. They use real copy shapes, the real logo and the real photos, and render at 1440×900 and 390×844 with a tablet width (check 375, 768 and 1440). Include the reference shortlist, the concept quality gate table, a motion toggle and reduced-motion view, and a review shell. Each direction is labelled with its structural idea. The review text is written in the owner's working language, with French site copy beside it. Verify headless, name one review surface (exact file and refresh step), and then ask which direction to develop. HTML concepts under `audit/visual-concepts/` are an exempt scope under the gate.

Lane: pick a primary lane from the aesthetic-lanes reference or Custom / existing brand with a rationale. For a yoga studio, Editorial Paper or Custom (organic, photography-led) is likely, and Technical Systems and Luminous Futurism are unlikely. This is recommended, not decided in advance. Hero strategy for a physical-practice brand is prepared editorial photography. Set the narrative metaphor, 4-voice typography with French-capable fonts (check accents and weights are served), surfaces, density, and 2–3 site-specific anti-patterns.

Gate before ANY site-specific visual implementation (route inventory and content modelling may precede it):
1. `npm.cmd run design:tokens -- --init-client --lane <lane>` (or `--seed-accent <hex>`). Optionally `npm.cmd run design:tokens -- --lane <lane> --write-record` to scaffold the record.
2. Save one complete `## Art Direction Record` in the site's AGENTS.md: Aesthetic Lane, Narrative Metaphor, Typography Pairing, Token Physics (Canvas, Action/Accent, Borders, Spatial Density) and 2–3 semicolon-separated Site Anti-Patterns. A commit is not required.
3. Refine tokens in `src/styles/global.css`, then run `npm.cmd run design:tokens` and `npm.cmd run test:design` (if the generated site has it) for contrast, fluid clamp bounds and required tokens.
4. `npm.cmd run check:art-direction -- --require-record` must pass.
5. Stage 4.5: run `npm.cmd run dev`, open the printed `/_styleguide/` path (with trailing slash), calibrate typography, colour, buttons, Container, Card, ResponsiveImage and flow spacing at narrow and wide widths. Save `audit/component-calibration.md` (scaffold with `npm.cmd run design:tokens -- --write-calibration`) with actual rendered evidence, keyboard/motion checks and ready/deferred patterns. A generated table is not browser evidence.

Checkpoint B handoff: report the saved record and which choices were approved versus assumed, the actual gate command and result, the contrast, token and specimen checks actually run and their limits, then continue.

What I would ask at B: which direction (A/B/C, or a combination), whether the typography is open or fixed (if the logo fixes a typeface), and any density preference. Only ask what changes the work.

### 4. Checkpoint C: Stages 5–6 (build, critique, verification)

Stage 5: build the shell and one representative page per archetype first (home, a class, timetable, then the plain pages). Write a section-by-section pacing blueprint before each page's markup, with no two adjacent sections sharing the same 3-column card geometry (or a recorded exception), and use the shared primitives (`Section`, `Container`, `Grid`, `Card`, `ResponsiveImage`) and shared tokens, not one-off CSS. Hero images get `loading="eager" fetchpriority="high"`. JavaScript only if an interaction needs it (a timetable filter, for example). No third-party tracking. Use the file-owned Base layout, native Markdown rendering and native images. Navigation lives in the site config. Work out the French-language owner tasks ("change a class time", "add a class") and rehearse them. Then load `impeccable` for a bounded critique of the representative routes, fix findings in shared tokens or components, then complete the remaining routes.

Stage 6: finish all five routes and states (a 404, empty and long-content cases, focus, forms). Final Impeccable critique/audit across the full set, fix cross-route findings in shared styles. Review the pages against their briefs (can a visitor see the offer, the fit and the next step? are claims supported? does the contact action reach the promised destination?).

Commands, run in the generated static site (checked against its `package.json` first):
- During edits: `npm.cmd run verify:fast` if present.
- Final: `npm.cmd run verify`, `npm.cmd run build`, `npm.cmd run check:dev-tools`. Confirm that `dist/` has no server adapter or database and excludes `/_styleguide`. Never deploy fixture output.
- `npm.cmd run audit:page` if present, and `check:native-images`.
- Not run for static: `doctor`, `audit:html` (EmDash), `site:register`, visual-regression baselines, CMS registry. Where an EmDash-only check is replaced, record browser evidence directly instead.
- Browser acceptance on a fixed built artifact via `npm.cmd run preview`, with zero horizontal overflow, clipped text or orphan single-word heading wraps at 375, 768 and 1440 (plus 390×844 and an intermediate width), keyboard and focus paths, reduced motion, alt text, French metadata, and a missing-route HTTP 404. Use a headless browser first and fall back to an available alternative, never bypassing a permission denial. Listen for `pageerror` and `console.error` if any client script exists. Contrast is checked on rendered pixels where it is uncertain.
- Reconcile a completion register (requested result → route → evidence → status).

Checkpoint C handoff in chat: routes rendered, checks actually run, browser findings addressed, assumptions, the preview URL, and pending items kept separate from "verified local build". Pending items are deployment, DNS, TLS and live form delivery, which are Stage 7 and outside scope. The delivery default is a verified local build. Stage 7 only runs if deployment is authorized, so I would ask nothing about it now beyond naming the remaining launch tasks (host choice, `SITE_URL`, contact destination, domain).

What I would ask at C: only whether the owner wants to review the preview, plus any still-missing content (for example real prices or a testimonial with permission). I would not ask "ready to continue?".

### 5. After handoff (day 2)

Owner emails changes, and I apply them as scoped changes starting at the earliest affected stage. Content edits touch the Markdown and the schema together, with no new track. New images go through `media:prepare`. Spacing or component changes follow `site-maintenance.md`, with the Art Direction Record preserved. Each change is re-verified with `verify`, `build` and a browser check of the affected routes. A renamed or removed public URL gets a 301 redirect, and a rebuild is needed to publish.
