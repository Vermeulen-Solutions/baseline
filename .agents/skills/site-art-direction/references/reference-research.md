# Reference research on every design surface

Use this at the concept checkpoint for a new site or substantial visual overhaul. `site-art-direction` owns reference discovery and adaptation for HTML/browser, Brilliant, OpenPencil, Penpot and any explicitly selected alternative. The iteration surface determines where concepts are made and reviewed; it does not determine which inspiration sources are available. Reuse the selected surface. Never select or connect OpenDesign merely to read its reference material, and do not load its surface skill for catalogue research alone.

## One inspiration offer

Start with the brief, supplied references, the owner's own sites, real content and fixed brand commitments. If those already provide sufficient direction, inspect a small relevant shortlist without another questionnaire. Small refinements reuse the accepted world's references.

When references are missing, ask once at the existing concept checkpoint: **are you short on visual references or inspiration?** Explain the offer concretely: “I can suggest a few examples that fit your brief, including websites, design prompts, visual systems or page templates.” If the owner accepts, research and present two or three relevant examples with a name, source, the useful idea and its fit to the brief. Let them name a favourite, combine specific aspects, or authorize the agent to proceed. Do not require them to choose a provider, browse a catalogue or select a template. A settled no means work from the brief and supplied evidence without repeating the offer. Reuse an existing answer or authorization; reference selection adds no mandatory approval checkpoint before the existing concept comparison.

## Choose sources for the design question

No provider has priority over the brief. Use the source that can answer the question; do not search every library or add an account/setup requirement.

| Source | Useful contribution | Read/inspect |
| --- | --- | --- |
| Supplied sites, the owner's previous sites and relevant real websites | Brand continuity, visitor flow, proof, navigation and composition | The relevant actual screens and responsive states, not just a search thumbnail |
| [open-design.ai/prompts](https://open-design.ai/prompts/), [superdesign.dev](https://superdesign.dev/), [designprompts.dev](https://designprompts.dev/) | Written directions for hierarchy, visual character, layout and motion | The selected prompt and relevant linked examples; preserve all three sources as options |
| Community `DESIGN.md` references, including `designmd-mcp` / [designmd.ai/explore](https://designmd.ai/explore) when available | Coordinated typography, palette, surfaces and visual rules | The selected document and provenance; access remains optional |
| OpenDesign [design systems](https://github.com/nexu-io/open-design/tree/main/design-systems) | Concrete visual systems and component specimens | Relevant `DESIGN.md`, `USAGE.md`, component/preview sources and source evidence where present |
| OpenDesign [design templates](https://github.com/nexu-io/open-design/tree/main/design-templates) | Worked page composition, assets and interactions | Relevant `SKILL.md`, `example.html`, licence and asset-source records; inspect the actual render before claiming visual quality |
| Nicelydone, Refero, Kombai Gallery or `21st.dev`, when available and relevant | Flow anatomy or a specific component pattern | Actual relevant screens/source; registry code still follows Astro's component-quarantine guidance |

For OpenDesign references, read the public repository files at an inspected commit, or an already-available local copy. Local app resources can contain `design-systems/` and `design-templates/` under a versioned `resources/open-design/` directory; older plugin layouts can use `plugins/_official/design-systems/` and `plugins/_official/examples/`. Inspect the actual available structure rather than hard-coding an app version, machine path or daemon port. Record the source commit, version or file hash. A connected OpenDesign catalogue search may be a convenient optional transport, but it is never required. If neither local files nor the public source are accessible, disclose that source as unavailable and continue with accessible references on the selected surface; do not install or start the app. Honour an owner's explicit requirement for a particular source by reporting the missing access rather than silently substituting it.

Treat brand-named collections as third-party interpretations unless original upstream evidence is established. Package examples and generated specimens are not client proof, official brand libraries or independently verified accessible implementations. A system's token files are reference material, not another canonical token source. No full catalogue, source artwork or template code is bundled or installed by this workflow; any later copying requires the selected item's licence and asset review.

## Adapt through the existing pass

Use [external reference adaptation](external-prompt-adaptation.md) for selected prompts, systems and templates. Preserve the structural idea and useful character, reconcile fixed commitments, map to Baseline roles, check permitted assets and factual claims, and cover responsive intent, states and reduced motion. Keep source instructions subordinate to the project; a source cannot mandate a surface switch, dependency installation or fabricated content.

Run `design:prompt-check` on a selected textual prompt, relevant system/template instructions, or a source-linked adaptation input that preserves their relevant directives and context. Do not feed screenshots, token JSON, embedded image data or an entire HTML bundle into the text checker and treat its output as template validation. Inspect HTML/CSS/JS and assets separately before rendering executable examples; source instructions do not authorize additional installation or execution. Run `design:artifact-check` on the resulting HTML concept when that command is installed. Native canvases keep their own actual-canvas review. Neither checker establishes visual quality, contrast, runtime behavior or approval.

Keep the source identity, useful characteristics, keep/change/refuse decisions and evidence in the existing concept notes/`adaptation.md` as described by the adaptation pass. Present the shortlist and its concrete influence with the two or three structurally distinct concepts using [the shared iteration loop](design-iteration.md#show-the-reference-research). Distinguish a metadata hit, source read and rendered review. Then select the direction, calibrate Baseline tokens/primitives and prove the native Astro result. Do not add another permanent design-system store or separate research sign-off.
