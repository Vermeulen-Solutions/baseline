# Design iteration and surface choice

Read at the new-site or significant-redesign concept checkpoint. This is the shared decision and iteration loop for [site-art-direction](../SKILL.md), HTML/browser, Brilliant, OpenPencil, Penpot and optional OpenDesign. Keep the existing detailed five-point recipes and brief-led exceptions; choosing a tool does not replace them.

## Recommend a surface once

For new sites and substantial visual overhauls, reuse a settled surface and working connection first. When the owner wants a dedicated editable design canvas for prototyping and has not chosen a tool, recommend **Brilliant** for native concept work. When no canvas is requested and no preference is established, recommend **HTML/browser concepts**. Explicitly present **Brilliant**, **OpenPencil** and **Penpot** at the same checkpoint, without waiting for the owner to ask about alternatives: HTML provides browser renders and agent-led file edits; Brilliant and OpenPencil provide editable local canvases; Penpot provides shared cloud review. OpenDesign remains optional when its catalogue, lint or existing project is useful. An established choice takes precedence over this recommendation; do not move an existing project or require a new connection merely to follow it. Small refinements stay in their accepted surface/composition; do not restart discovery for a local CSS adjustment.

An older installed site may receive this guidance before adopting the Brilliant adapter and onboarding guide. Do not assume missing files are installed: use the vendor's documented MCP only for bounded exploration, and prepare deliberate, reviewed adoption of the optional files before relying on the Baseline workflow. Ordinary updates preserve installed skill membership.

**Harness-neutral contract.** Whatever the surface, it must satisfy "The owner's review surface" below: one named artifact the owner opens, a review shell, and a check of that exact artifact before any claim. A harness-native canvas (in Claude: the Design artifact type) is another explicit alternative when it meets that contract; its availability does not silently override a settled choice. Use the documented owner-view limitation for an authenticated canvas that cannot be checked headlessly. Record the chosen surface in the existing context home so later sessions and other harnesses reuse it.

A useful single checkpoint is: “We can compare three directions side by side in browser concepts. If you want an editable design canvas, I recommend Brilliant for native prototyping; OpenPencil is another local choice, and Penpot suits shared cloud review. Do you have a preference?” If the owner has already asked for a canvas but has not chosen one, lead with: “I recommend Brilliant for the editable prototype. We can keep the directions and revisions in one named project; OpenPencil and Penpot are also available choices.” Present the relevant offer once when unresolved; do not make a tool-selection answer a mandatory stop when a default is already authorized. Prefer an already working, user-preferred canvas over making the user install another. Keep explicitly preferred **Pencil**, **Google Stitch**, **Claude Design** and `designmd-mcp` references available; inspect actual access and agree any fallback. Do not silently switch to code when a chosen canvas is unavailable.

This recommendation is based on the exercised native workflow, including the [native capability trial](https://github.com/Vermeulen-Solutions/baseline/blob/311ec6a/audit/brilliant-native-capabilities-2026-11-06.md), rather than a claim of faithful HTML round trips or measured superiority over other tools. Build native components/layout for prototyping; after selection, implement and accept the real Astro route. A browser-specific uncertainty can still justify an early bounded browser spike.

Surface and agent continuity are independent. The same agent can design and implement on every path. Ask about another model/session only when the user wants that arrangement; never automatically launch one. Setup is only the missing connection step, not a repeated questionnaire or permission to install software, provision accounts or change global configuration outside the user's scope.

Requests for motion, illustration, charts, 3D or other capabilities use [capability routing](capability-routing.md) on the selected surface. Choose guidance for the requested outcome and actual runtime, rather than changing surfaces to reach a particular skill. Inspect and test a targeted catalogue source when installed guidance has a gap; preserve the same browser/native acceptance boundary.

## Comparing directions in HTML

Surface choice and direction choice are separate. HTML concepts retain the same two-or-three-direction exploration and owner selection as canvas boards; a file-first default is not permission to present one unchosen direction or three colour skins of one layout.

1. Put each structurally distinct direction in its own file, for example `audit/visual-concepts/<round>/direction-a.html`, `direction-b.html` and `direction-c.html`. Use the same representative content, assets and comparison widths. Keep the current site and supplied references available beside them.
2. Provide one `index.html` comparison page with labelled A/B/C previews side by side at equal display scale, plus a link to open each complete direction at full size. Previews may be static captures linked to live files or independently scrollable frames with explicit viewport sizes. State the real render width: shrinking a 1440px screenshot to a thumbnail does not prove mobile reflow. On a narrow review screen, stack previews or allow horizontal comparison without squeezing the concepts into misleading widths.
3. Include desktop/mobile comparison (`1440×900`, `390×844`) and the existing tablet/device controls, motion/reduced-motion review and quality-gate table. Render each direction itself at 390/768/1440 and inspect the comparison entry and full-size links. Check page/console errors and controls when the shell uses JavaScript. Screenshots are summaries, not substitutes for full-page inspection.
4. Label each direction's structural idea, fixed commitments, meaningful differences and honest gaps, then ask which direction to develop. Selection may combine specific features deliberately; record the resulting direction and superseded alternatives before the Astro proof. Iteration after selection changes that direction in focused batches rather than regenerating all three.

When installed, `npm run design:watch -- --dir audit/visual-concepts/<round>` opens changed top-level HTML files. It is a file opener, not a live-reload server, and CSS/image edits alone do not trigger it. For a stable review tab, serve the concept folder with the site's available preview server and document refresh behavior; a manual refresh is acceptable when stated. Do not add a daemon, service or dependency just to compare concepts. Run `design:prompt-check` explicitly when importing a library prompt; an archived prompt's presence must not automatically fail the whole concept directory.

## Show the reference research

For a new direction or substantial overhaul, inspect a small shortlist of references relevant to the brief before presenting concepts. When OpenDesign is selected, follow its Stage 4A catalog research: search bundled design systems/examples and read the relevant parts of shortlisted `DESIGN.md` files or layout sources. Other surfaces can use available local references or suitable external sources; an external library account or exhaustive survey is not required. Preserve fixed brand commitments when interpreting inspiration.

At the concept checkpoint, ask one direct question before presenting concepts: **are you short on visual references or inspiration?** If the answer is yes, offer the prompt libraries — [open-design.ai/prompts](https://open-design.ai/prompts/), [superdesign.dev](https://superdesign.dev/), [designprompts.dev](https://designprompts.dev/) — and say plainly what they are: complete visual systems written for another product, useful as a brief and never as a specification. If the owner picks one, run `npm run design:prompt-check -- <file>` and adapt it with [external prompt adaptation](external-prompt-adaptation.md): keep structure, pacing and devices, map colours onto roles, carry type character with the site stacks, and refuse invented proof. If the answer is no, build the shortlist from the brief, the owner's own sites and supplied references; do not repeat the offer in the same session.

At the first concept presentation, show the shortlist directly in chat and beside the comparison or in its linked existing concept notes. For each reference, identify its name and source link/path, what was actually inspected, the useful idea (such as navigation hierarchy, section pacing, image treatment or typography), which concept it informed, and what was deliberately left behind to respect this site's brief. A compact table or a few sentences is enough. This makes the reason for a proposal reviewable rather than simply listing famous brands or tools.

Distinguish a catalog search hit from a source actually read, and a source read from a rendered example actually reviewed. Disclose partial reads or unavailable previews; do not claim a full-file or visual review from metadata alone. If no outside reference contributes, explain the source/brand evidence used instead. Keep this in the current presentation and existing concept record, without adding a separate report or approval checkpoint. Small refinements within an accepted direction reuse its references unless the change needs new research.

## A short loop with concrete review

1. **Frame one useful slice.** Reuse the brief, accepted brand, source CSS/component APIs and real content. Pick a representative page plus the state or second archetype that exposes the largest uncertainty. State fixed/changeable commitments and the design decision to resolve. Do not recreate the entire content model, every route or a complete component library in the canvas first.
2. **Explore and compare.** For a materially different direction, make two or three compact concepts showing composition, hierarchy, surface/type character and mobile intent. Directions must differ in **structure and idea** (hero concept, how proof is shown, section composition), not only in palette and font on one shared page skeleton; three colour skins of one layout are one direction. When typography is open, show it as its own quick step: a specimen of three or four pairings on the chosen surface with the real headline, intro, buttons and a content row, so the owner can pick type separately from layout. Include the reference shortlist and its concrete influence as described above. For refinement, edit the selected concept directly. Use `1440×900` and `390×844` comparison samples with the original fluid token expressions beside computed canvas values. Keep source content/URLs, supported states and reading order truthful.
   **Concept quality gate (before the owner sees a concept).** Put each concept side by side with the current site, with every owner-supplied reference **and with the owner's own earlier sites** (a site they already like is the strongest reference), and fill this fixed table in the presentation. Every row is required; "not applicable" needs a reason. Do not choose your own rows: a skipped row is how a concept that only decorates components gets presented as an improvement.

   | Row | Current site | Each concept | Pass when |
   | --- | --- | --- | --- |
   | Hero idea | | | a specific visual idea tied to this brand |
   | Real proof | | | the first proof matches what the visitor is buying, and is real |
   | Ground, depth and atmosphere | | | the page ground itself has light, texture or depth at the references' level; a flat single-colour ground with boxed sections is named as such |
   | Imagery | | | real photography/work, used at a size and crop that carries the feeling |
   | Motion | | | adopted motion is visible in the review (clip or toggle) and stills under reduced motion |
   | Section variety | | | no run of identical section skeletons or identical boxes |
   | Typography | | | pairing chosen or fixed, with the reason |
   | Recorded invariants | | | respects the Art Direction Record's borders and anti-patterns and the site's layout conventions (content width, uncropped galleries, required states); a violation is named, not hidden |
   | Distinct from the owner's other sites | | | no signature motif, ground or layout device lifted from the owner's other sites (a sibling club site's stripes, a studio site's glow); shared craft level, not shared devices |
   | Source quality per slot | | | every image slot lists the CMS field it reads and its source width; a slot never repeats a photo shown elsewhere on the page, and its source is at least the rendered width at 2× (a full-bleed band needs a large original) |

   The bullets below expand the rows:
   - **Hero idea:** is there a specific visual idea tied to this brand (not a generic headline over a gradient)?
   - **Real proof:** does the first proof the visitor meets match what they are buying (a website studio shows websites, a shop shows products), and is it real work, not a stand-in? Name the visitor persona from the brief and say what they see first.
   - **Craft level:** depth, imagery, motion and section variety at least at the level of the references, scaled to the brief (a "less flashy" request lowers excess, not craft).
   - **Section variety:** no run of sections sharing the same eyebrow → large heading → side intro skeleton or the same row/card pattern.
   - **Honest gap:** say plainly where the concept still falls short of the references.
   - **Seams at full size:** look at every overlap, gap and split ground at 100% (crop the screenshot): a ground that changes colour behind gaps between photos reads as broken stitching even when the full-page view looks fine.
   Placeholder or stand-in visuals (a logo in an empty box, initials, lorem imagery) block a direction review: replace them with real material or a clearly labelled illustration first. A concept that is not clearly better than the current site is not ready to present.
   **Shared changes need a sitewide sweep before approval.** When a concept changes a shared ground, token, surface or component (not only the sample pages), apply it to every page family at three widths before the owner approves, and list the affected families and any regressions in the review shell. A two-route sample hides failures such as default buttons vanishing on a new ground. When the tooling checkout is available, run `audit:ui` for this sweep and again after building: it hovers every element with a `:hover` rule, so a hover border or glow around unpadded content is caught. Hover effects that suggest a link (lift, glow, edge colour) belong only on clickable elements.
3. **Iterate in focused batches.** Present the render, explain the meaningful difference and recommend the next change. Apply the user's feedback as a small coherent batch, commonly one to three changes; re-read affected geometry/text and inspect the affected render. Reuse verified nodes, variables and components; avoid repeatedly exporting every board, re-reading the whole API overview or rebuilding a library for a local edit. Recheck target identity after reconnect/navigation and inspect committed state before retrying an uncertain write. Broaden the review when shared tokens, fonts or component changes can affect other boards.
4. **Select the direction.** Compare against the brief and the five-point rubric: 3-tier surfaces, 4-voice typography, grid rhythm/asymmetry, tactile actions and adopted motion/polish. Also run a persuasion check per brief persona (for example "referred club treasurer on a phone", "stranger from search"): what do they see first, what proof reassures them, and where is the action? Fix a proof/offer mismatch here, before build, rather than after a rendered critique. Show enough page context to judge pacing as well as close-up details. Ask for the meaningful choice before broad implementation unless that choice is already authorized. Record selected board/file identity and dated evidence, approval versus assumption and unresolved states in the existing context home. Same-agent work needs only a compact decision record, not a duplicate brief plus handoff package.
5. **Prove it in Astro, then roll out.** Save/check the Art Direction Record, translate selected relationships through actual native tokens/components and calibrate `/_styleguide`. Build one representative real route, compare with the selected design, fix browser-specific differences and check intermediate reflow, long content, keyboard/focus, destinations and adopted motion/reduced-motion behavior before broad rollout. Use an early bounded browser feasibility spike only when an interaction or responsive constraint could invalidate the concept; do not maintain a duplicate full Astro site during every canvas edit. Complete route acceptance, installed verification and agreed commit/push/applicable deployment/live checks.

When implementation reveals a material composition change, update the affected canvas/reference and direction decision as needed. Avoid automatic whole-file two-way synchronization, a second permanent token store or a full re-approval of unaffected choices. Preserve real CMS/file bindings. For another agent/session use the portable brief/handoff in `penpot-site-design`, carrying identifiers, selected versus draft state, source expressions, mapping, responsive/states intent and remaining questions without credentials or hidden `storage` dependencies.

For a selected change to shared design values, follow [token-handoff.md](token-handoff.md): map the intended semantic scope and original fluid expressions, preview the existing CLI operation, inspect a bounded CSS diff, then apply and prove the relationship on native primitives and a representative route. Inspect font-source preflight and actual rendered faces separately; a canvas export is not production acceptance.

For an authorized feedback batch, retain the small chain feedback → confirmed target → bounded change → inspected result → remaining status in the existing notes. Distinguish a correction completed in the canvas from one implemented and verified on its real route. Reuse the selected surface's comment/identity rules; a resolved thread does not establish user approval. `new-site-workflow/references/delivery-evidence.md`, when installed, connects this loop to shared components, content ownership and browser evidence without adding a second tracker.

## Refining a built site

When the site is already built and the owner wants a refinement (not a new direction), there is no canvas concept to "edit directly". Use this recipe:

1. **Diagnose with the owner first, or from the site.** Ask what bothers them in their own words before offering options (see `discovery-and-content.md`); "sleeker" can mean quieter or livelier. When the owner only wants a polish and the site already records its direction, derive the diagnosis from the rendered site and the owner's own sites instead, and confirm it in one paragraph. Offer opposite directions when you do offer options.
2. **Concepts as overlays on real routes.** Write each concept as a CSS (and, if needed, small JS) layer injected into the real rendered routes, so photos, CMS text and states stay real. From a Baseline checkout (the site needs no new dependency), `npm run capture:routes -- --base <dev server> --routes /,/contact --css concept-a.css --click "[data-pause]" --out <dir>` (one `--out` per variant) captures full pages plus viewport frames while scrolling (fixed layers only render truthfully in viewport frames), and `--compare` reports where captures differ. Motion clips for the review: `npm run record:motion -- --css concept-a.css --speed 4 --out hero-4x.gif`, labelled with the speed. Keep overlays in `audit/` as review material, not shipped code.
3. **Review shell with a current-versus-concept switcher**, the fixed gate table above, and an honest-gaps paragraph. When type is a fixed brand commitment, say "typography step skipped: fixed commitment" instead of running a specimen.
4. **Build in shared tokens and components**, run the sitewide sweep, then the two-agent critique, and show the owner a final before/after of the built result. Before spawning the critique, commit (or otherwise freeze) the rendered source and make only documentation edits until both assessments return, so they judge the same build. Seed `.impeccable/critique/ignore.md` from the motifs the Art Direction Record declares on purpose (for example a striped ground), and treat a contrast finding averaged over a gradient as unverified until rendered pixels are sampled.

## The owner's review surface

Verification only counts for the artifact the owner actually opens. In every hand-off:

- **Name one review surface** (app, project, exact file or URL, and the refresh step such as Ctrl+R) and check that exact artifact before claiming anything works. If a tool or editor auto-opens a different file, close it or tell the owner which one is current.
- **Never leave an unbuildable template where a viewer can open it.** A source file with placeholders that a build step replaces (inlined images, fonts) gets a non-viewable extension such as `.src.html.tpl`, not `.html`.
- **Ship a review shell with every round,** not a bare page: how to look (scroll inside frames, what to hover), what is real versus illustrative, a desktop/tablet/mobile switcher, specific feedback questions, and a motion toggle. Explain that visitors (and the owner's own machine) may ask for reduced motion, which freezes animation by design; the toggle lets the owner see both versions.
- **Write it in the owner's working language** (recorded in discovery), which can differ from the site's locales. Show site copy in its locales, with the owner-language version beside it when approval is needed.
- **Do your own checks headless** (Playwright or the canvas tool's export API) and leave the owner's browser panes and windows alone unless they ask to watch. Embed fonts and assets in concept files, because some canvas previews do not load remote stylesheets that their exports do.
- **For checks that outlive one turn** (background sub-agents, critiques), run the dev server as a persistent background process, confirm it answers before spawning reviewers, and stop it afterwards; an app-managed preview may be stopped between turns. Pick a port no sibling session uses (another site's dev server may hold 4321), record the server's PID, stop it by PID after checking its command line, and confirm the port is free: on Windows, stopping the wrapper shell can leave `node astro dev` running and holding files open. On Windows, start it with PowerShell `Start-Process node -ArgumentList 'node_modules/astro/bin/astro.mjs','dev','--port','4417' -PassThru` to get the real PID, and check with `netstat -ano | findstr :4417`; Git Bash `ps` does not list Windows-native node processes, so a running server can look dead. Stop the dev server before release steps that rename files (skill apply, asset retention).
- **The agreed surface overrides tool defaults.** Harness nudges to open a built-in preview pane, and Impeccable's preference for the harness browser, do not override the owner's rule. Critique assessments run headless (Playwright supports the mutable script injection Impeccable's overlay needs).

### Checking a Claude Design canvas

A private claude.ai canvas cannot be rendered headlessly without the owner's sign-in, and the Design type's own instructions discourage verification; the owner's request for a checked review overrides that. Check everything upstream of the upload and say what remains:

1. Verify every render, overlay and motion clip locally (headless, at the review widths) before uploading it.
2. After publishing, read back the published `.dc.html` and `canvas.json` files and compare them with what you wrote, and list the artifact's assets to confirm every `/_blob/` the artboards reference exists with the expected size.
3. State plainly that the canvas render itself is accepted through the owner's view, and ask the owner to leave at least one comment on the canvas, then read it with `ArtifactComments`, so the comment loop is exercised rather than replaced by chat.

## Efficiency and honest evidence

A canvas handoff needs one obvious current review entry, with previous versions clearly historical. Verify the owner's actual opening path in the selected surface: rendered alternatives, desktop/mobile comparison and complete-page inspection. State refresh/reopen steps in chat. An export, file listing or API registration does not prove desktop usability. Keep evidence in the existing direction record; no second mandatory handoff file. Future behavior must be assessed from an observed review, not a structural test of these instructions.

For native rollout, include the reported failure viewport and a width beyond the content maximum when viewport-derived spacing is used. Check full-width and constrained-parent placements, local-language expansion, reading measure, coherent headline phrases and actions that fit. Zero document overflow alone is not visual acceptance. Use representative archetypes/risk-based widths rather than imposing an exhaustive client-specific matrix on every site.

A design canvas can make direct manipulation and discussion easier, while HTML retains real CSS and browser behavior. Neither establishes a measured speed or token-savings advantage. The 2026-10-26 trial exercised OpenPencil, Penpot and Astro authoring/recovery, not a controlled token benchmark; Brilliant was not included. Tool/API latency, model ability, asset/font support and later translation can change total delivery time. If efficiency is material, compare the same brief, model, starting assets, three-direction slice, feedback batch and final Astro acceptance. Record setup and discovery, authoring, screenshots/reads, retries, owner interventions and translation separately. Report actual input/output/cached tokens and image accounting when the harness exposes them; otherwise mark them unavailable. MCP call counts and payload bytes are useful operational measurements, not model tokens. Distinguish cold setup from an already connected session, and report task-quality failures alongside any cost result.
