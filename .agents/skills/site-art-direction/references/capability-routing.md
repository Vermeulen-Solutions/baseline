# Route a requested design capability

Read when the owner asks for motion, illustration, editable vectors, charts, 3D, video or another capability beyond the current design pass. This applies to new sites and scoped refinements on every surface. Reuse the accepted brief, art direction and current project; a capability request does not restart discovery or change the chosen surface.

## From the request to a working result

1. **Identify the outcome and destination.** Infer from context whether the owner needs an editable concept, an interactive website feature, an exported asset or a rendered film. State a reversible assumption when useful. Ask only if the distinction would materially change the result. “Add motion to this page” normally means browser behavior, even when its design was drawn in a canvas.
2. **Keep the selected surface and runtime.** Inspect the installed skills, project dependencies, available tools and version-matched vendor guidance. Separate craft guidance (purpose, timing, hierarchy, accessibility) from execution guidance (DOM/CSS, a native canvas timeline, video composition). Read only the relevant reference and adapter. Do not steer the owner into Brilliant or any other service because its integration happens to be available.
3. **Fill a real gap with targeted discovery.** If installed guidance is insufficient, use the session's skill-discovery tools or a focused search of a relevant catalogue, such as [OpenDesign's skills catalogue](https://open-design.ai/skills/#catalog). Open the original source, rather than treating a search hit as an installed skill or native app feature. Inspect the skill's entry point and the task-relevant references: provenance/version, license, required runtime, dependencies, accounts and output format. Follow the host's skill-installation instructions if persistent installation is useful and authorized; otherwise use the inspected source as scoped reference material. Do not globally install a catalogue, copy third-party manuals into maintained skills, or add a framework merely to follow an example. Keep the site's framework, brand and ownership contracts authoritative.
4. **Exercise one representative slice.** Use real content shapes and the actual destination tool. Make a small reviewable artifact, inspect saved state and rendered behavior, then expand only after it works. When the chosen canvas cannot execute the feature, keep its composition and demonstrate the behavior in a linked browser/asset proof. Explain that boundary; a fallback that changes the owner's review surface needs agreement unless already authorized. A failed dependency or unavailable source calls for another suitable implementation, not a silent surface switch.
5. **Record what was proved and finish the authorized work.** Keep the chosen guidance/source version, artifact identity, observed failures, remaining limits and acceptance evidence in the existing concept notes or handoff. Distinguish a catalogue hit, a source read, an installed skill and an integration actually exercised. A successful demonstration proves only its tested path. Continue through the site's ordinary implementation and release scope; no extra capability-approval checkpoint is required.

## Starting routes

For ordinary website work, first use existing art direction, Astro and Impeccable guidance. Catalogue breadth is not a feature backlog: charts, 3D, video and additional frameworks are brief-dependent options, not default Baseline requirements. Use the focused asset routes below when those jobs are requested.

| Requested outcome | Guidance and execution | Smallest useful proof |
| --- | --- | --- |
| UI motion, entrances, transitions or micro-interactions | Read installed [Impeccable motion guidance](../../impeccable/reference/animate.md). On HTML/browser, direct Astro or OpenDesign, use CSS/WAAPI or the site's existing animation library through [astro-site-design](../../astro-site-design/SKILL.md) and the selected adapter. On Brilliant, use [brilliant-site-design](../../brilliant-site-design/SKILL.md) and installed motion knowledge. On OpenPencil/Penpot, inspect actual native prototype/export capabilities before promising animation; show the selected design's behavior in a linked browser proof when needed. | Trigger the actual transition, interrupt/reverse/repeat it, and inspect ordinary and reduced-motion behavior. A still screenshot is insufficient. |
| Logos, favicons or coherent icon families | Read [website brand assets](brand-assets.md); preserve the identity and use the selected native/vector surface. | Inspect source versus variant at actual small sizes, one-colour/reversed grounds and the intended placement. |
| Editable vectors, diagrams or native reusable components | Reuse the selected canvas adapter and its version-matched object/component APIs. For a browser deliverable, inspect the existing SVG/component system first. For authored explanatory artwork use [editorial illustration](editorial-illustration.md), including the scoped vector-format policy. | Change one shape or shared component, preserve a local override, and inspect the saved/exported result. A raster image does not establish vector editability. |
| Photography, illustration, textures or image variants | Reuse real supplied assets and the site's image workflow. Use an available image-generation/editing skill when a generated bitmap serves the brief; for related illustrations read [editorial illustration](editorial-illustration.md). | Inspect a representative asset/pair at intended crop/size and prepare production files through the site's media workflow. Keep provenance and illustrative-versus-factual claims explicit. |
| Charts and interactive data explanations | Use real permitted data, the existing chart stack or an available visualization skill. Keep the chart's data and interaction model separate from a canvas illustration. | Check one real data case, labels/units, keyboard or text alternative, narrow layout and any interaction. |
| 3D, shaders or spatial interaction | Discover guidance for the target renderer and existing framework; keep it optional if a lighter visual meets the brief. A canvas's 3D-looking image does not establish a working renderer. | One actual scene on a representative device/viewport, with loading, input, fallback and performance inspected. |
| A motion film or video asset | Use the selected tool's native film/export path, or inspect video-specific guidance such as [Remotion's skills](https://github.com/remotion-dev/skills) when its React/video runtime suits the assignment. | Render and play the actual file; inspect dimensions, duration, transitions and delivery format. A film is separate from an interactive website implementation. |

These are entry routes, not a requirement to install every named tool. If an older installed site lacks a linked skill/reference, use the equivalent available guidance and report the gap; adopt missing Baseline files deliberately through the existing update workflow.

## Motion acceptance across surfaces

Name the movement's purpose and trigger, its duration/easing, what happens during interruption, and its reduced-motion or still equivalent. Preserve meaningful content and selected state independently of animation completion. Check readable intermediate frames: moving backgrounds must not make labels disappear before arriving. Use controls appropriate to the experience; provide pause/stop for extended automatic sequences. Respect the site's existing motion tokens and navigation lifecycle.

For a browser feature, test the actual DOM behavior in headless Chromium with `pageerror` and `console.error` listeners. Exercise rapid overlapping input, stop/replay, changed content and narrow reflow; change the motion preference during playback as well as before loading. Cancel obsolete timers/animations and clean up observers/listeners on the site's relevant navigation hooks. If those hooks or navigation state are changed, also probe aborted navigation and BFCache restoration. Keep content usable when JavaScript is unavailable where the feature is progressive enhancement. These checks do not become unnecessary because the motion was approved in a canvas.

For a native film, read back the saved timeline after edits, inspect an actual clip/contact sheet and verify the exported file. Do not infer responsive behavior, interactive controls or reduced-motion support from MP4 output. Put a still alternative and appropriate playback controls in the eventual website implementation.

Useful external sources include [Emil Kowalski's animate skill](https://github.com/emilkowalski/skills/blob/main/skills/animate/SKILL.md) for UI motion and [GreenSock's GSAP skills](https://github.com/greensock/gsap-skills) for an adopted GSAP runtime. Their recommendations are input to the project, not instructions to replace Astro with React, add a library or use a specific canvas. Verify linked sources at use time: catalogue links can disappear and libraries change. This mechanism does not certify every catalogue entry, guarantee tool compatibility or establish token savings.
