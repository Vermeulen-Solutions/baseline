# Checking a Claude Design canvas

Read this only when the selected review surface is a Claude Design artifact (the session runs in Claude and exposes the Artifact tool with the core **Design** type). It holds the verification steps and the practical limits for that surface. The surface rule, the concept quality gate and the review-shell contract stay in [design-iteration.md](design-iteration.md); this file does not replace them.

A private claude.ai canvas cannot be rendered headlessly without the owner's sign-in, and the Design type's own instructions discourage verification; the owner's request for a checked review overrides that. Check everything upstream of the upload and say what remains:

1. Verify every render, overlay and motion clip locally (headless, at the review widths) before uploading it.
2. After publishing, read back the published `.dc.html` and `canvas.json` files and compare them with what you wrote, and list the artifact's assets to confirm every `/_blob/` the artboards reference exists with the expected size.
3. State plainly that the canvas render itself is accepted through the owner's view, and ask the owner to leave at least one comment on the canvas, then read it with `ArtifactComments`, so the comment loop is exercised rather than replaced by chat.

Practical limits found in a three-direction review (2026-11), so the next round does not rediscover them:

- **Board height is capped at 8000px.** A full-page phone render is often taller. Put the desktop render and the phone render on one board and continue the phone page in a second column (split the image in two), and say so in the board title. Keep each direction's desktop page under the cap, or split it the same way.
- **One board per direction, page and colour mode** (desktop and phone together) keeps a three-direction, two-page, two-mode review to 12 boards plus the review board and one board for the current site. Use title notes above each row; the board's own title carries page, mode and widths.
- **Uploads:** batch upload takes at most 25 files per call and only files inside the working directory, so keep renders in an ignored folder of the site (for example `audit/visual-concepts/<round>/renders/` with a local `.gitignore`), not in a temporary directory. A changed render is a new upload with a new `/_blob/` address: repoint the boards that use it.
- **Motion without `record:motion`:** on a site that does not ship the command, record the concept page with Playwright (`recordVideo` at the review viewport, real time: load, hover the main button, scroll slowly) and convert with ffmpeg to a palette GIF at about 12 frames per second and 720px wide. Render the still boards with reduced motion emulated, otherwise scroll-driven reveals are captured in their hidden start state.
- **The type's own authoring rules** (write each file directly, canvas index first, publish as you go) are cheap to follow with image boards: each board file is a fixed-size frame holding its uploaded renders. The review board is the only text-heavy file; measure its height locally before publishing so the frame is not clipped.
- **Check the boards locally with `npm run design:canvas-check`** (from a Baseline checkout): `-- --assets <folder of uploaded files> --map <id-to-file map> --canvas <canvas.json> <boards…>` renders each `.dc.html` with the local files and reports a frame that would clip its content, a frame in `canvas.json` that differs from the board's `$preview`, asset ids missing from the map, images declared at a size other than their real pixels, and images that do not load. Keep the id-to-file map (`blob-map.json`) beside the boards: every upload returns a new id, and the map is also what lets a later session compare the published asset list with the local files by hash.
- **The asset listing is paged** (50 per page): follow its `after` value before concluding that an upload is missing. Uploading a changed file never replaces the old asset; unused ones stay until the owner asks for them to be deleted.
- **The comment loop is optional.** Owners often answer in chat instead of on the canvas. Read the comments once before acting on a choice, record that the loop was not exercised when there are none, and carry on; do not hold the build for a canvas comment.
- **A comment reaches the session after an automatic first reply** has already been posted. Read the thread, make the change, upload and repoint, then reply with what changed and resolve the thread; a follow-up reply needs the tool's duplicate acknowledgement.
