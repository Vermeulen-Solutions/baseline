# Decisions, questions, audits and release

Read this when a stage needs a user decision, when a handoff is due, when the request is an audit, or when release scope (commit, push, deploy) is unsettled. The router in `SKILL.md` keeps the summary rules; this file keeps the full policy.

## Decision and question policy

Use supplied evidence and prior answers before asking. Treat the handoff prompts in the stage references as adaptable examples, not mandatory scripts or permission requests. When work is already authorized, report the outcome and continue. Ask only unresolved questions whose answers change the work; combine related decisions and use plain language with a recommendation. Express has **up to three consolidated checkpoints**, not three mandatory stops. Do not ask “ready to build?” repeatedly or require users to choose implementation details the agent can derive.

Put specific questions for the user directly in chat when they become relevant. A question recorded only at the end of a report, checklist or handoff has not been asked. Keep the artifact as supporting evidence and a durable decision record. Ask in small groups, distinguish decisions needed now from later launch tasks, and say when no answer is currently needed. Use the visitor/editor outcome in everyday language; if a technical term is necessary, give a short plain-language explanation beside it and recommend an option. For example, ask where the finished website should run and who will maintain it before asking the user to choose a runtime or hosting product. Once answered, update the fact's established home and retire the stale question from active handoffs rather than asking it again.

Each handoff reports the completed scope, observed evidence, unresolved decisions and next authorized action. Label working assumptions explicitly; a saved record or passing check does not establish user approval. If the user requested only a stage, stop at that scope. For a complete build, continue through local verification; deployment, content transfer, DNS changes and external submissions require authorization covering those actions. Reuse existing authorization rather than asking again at each stage.

When delegation is authorized and independent work would help, use [parallel-delivery.md](parallel-delivery.md). Keep a single writer for shared files, instances and canvases; settle shared contracts before dependent route implementation and freeze writers before release verification. Another agent is optional, not a workflow checkpoint.

At a major transition, after resolving a blocker, and in the final reply, state the workflow position and next concrete action directly in chat. Technical activity updates and report links do not replace this. Use the existing tracker for the current checkpoint; retire superseded holds when the user's answer changes the scope. Do not add a mandatory status document or make the owner ask what comes next. If nothing needs their answer, continue the next authorized work rather than ending with “shall I continue?”.

For a migration release, distinguish code deployed, owner able to sign in, content/media transferred, and publication verified. Report only the milestones actually observed. For example: “The preview code is deployed; content transfer is next. Please create your own passkey at this protected setup link; I can then transfer the reviewed content.” After that step, say what completed and perform the authorized transfer/acceptance without requesting deployment approval again. A reachable setup page does not prove working sign-in, and a Git push does not transfer CMS data. Respect the owner's review-before-deployment decision when it remains active; do not repeat it after they completed review and authorized release.

When evaluating Baseline's workflow in a real project, retain brief notes as friction occurs: the intended step, what actually happened, evidence, user/operator effort, workaround and a specific proposed improvement. Use an existing tracker or one focused project-local retrospective; do not duplicate the brief or impose a log on unrelated small changes. At the agreed phase end, consolidate what worked, where the workflow caused confusion or avoidable work, and prioritized improvements with acceptance criteria. Distinguish observed limitations from assumptions, proposals from shipped fixes, and pilot results from full migration acceptance. Keep identifiable client evidence private and use sanitized reproductions for upstream work. A request for a workflow review does not authorize implementing every recommendation.

Discover the following in small groups, omitting known answers:

1. **Purpose and visitor:** Who is the site for, what should visitors do, and what must that journey accomplish? Which pages/content are essential?
2. **Content and identity:** New build or migration? Which content, logo, imagery and brand/source references are authoritative and available to use, what is missing, who supplies it, and which languages must launch?
3. **Operation and constraints:** Who edits and maintains it? Is browser editing or immediate publication needed? Are there required forms, bookings, services, hosting/cost constraints or a target date?

Ask conditional details when relevant: preserve/refine/overhaul and URL redirects for a migration; form destination, recovery, integration/data owner and handling requirements for enquiries; roles and review/publishing workflow for editors; translation ownership for multiple locales; actual measurement needs before analytics; existing SEO/search/social requirements; approved privacy/legal copy when the site collects personal data or its jurisdiction requires it. Do not invent policy copy or request secrets in chat; use the project's supported secret storage. Keep deployment, CMS data transfer and DNS changes separate, with the existing authorization rules.

## Audit requests and release completion

Across design, content/schema, dependency, configuration and workflow audits, an unqualified request to audit normally asks for evidence and an actionable follow-up plan before implementation. Lead with the recommended next actions and consequential user decisions; keep the detailed report as supporting evidence when useful. Respect an explicit report-only request. Do not mistake an audit request for permission to apply all findings in one pass.

For an existing EmDash site's content-model or redesign audit, assess opportunities for editable page sections alongside the automated technical findings. Inspect the current schemas, stored content, templates and editor workflow using `emdash-content-modeling`'s composition decision tree. Recommend blocks where a demonstrated need to add, remove or reorder predefined sections would benefit editors; duplicated markup alone is insufficient. If editing needs are unknown, identify the missing evidence rather than asserting a benefit. Report the routes that would benefit, the concrete editorial benefit, proposed block types, preservation of existing content/design/URLs, migration effort and editor/public acceptance; retain fixed templates or existing compositions where they already meet the need. This qualitative audit recommendation does not itself authorize a conversion; carry selected work into the existing migration and implementation workflow.

Recommend a coherent sequence with the problem/impact, proposed changes, preserved boundaries, tradeoffs, dependencies and acceptance evidence. Offer two or three alternatives that differ in outcome or cost where the user's choice matters, rather than a catalogue of every possible improvement. If only diagnosis was authorized, present the plan for selection before implementation. If the user already selected the work or asked to audit and implement within defined bounds, reuse that authorization and continue once consequential open decisions are resolved; do not manufacture a new approval checkpoint.

Include release completion in the proposed implementation plan: verified changes committed, pushed to the agreed repository/branch and deployed to the agreed target where applicable, followed by live acceptance. Establish the release destination and whether these actions are authorized during planning, using existing decisions first. A standalone audit or approval of a local implementation is not blanket deployment permission. Resolve missing release scope at plan selection, or request only the still-missing final action after preparing a reviewable result. Once release is authorized, carry it through without waiting for separate commit/push/deploy prompts. Report actual commit, remote branch, deployed version/URL and observed acceptance; do not call a local diff the released result.

Match the endpoint to the work. An explicitly local-only task ends locally; a template/library/docs change may require commit and push with no site deployment. State that applicability rather than deploying an unrelated site. Release authority does not imply permission for content imports, production data writes, messages or DNS cutover.

## Brownfield site audit and modernization (`Audit -> Propose Follow-Up -> Execute -> Re-Audit`)

When auditing an existing EmDash site to adopt newer starter standards or design-system practices, **never treat a diagnostic report or a single primitive-backport pass as the end of the workflow**:

Apply the common audit/decision policy above. The plan is the primary handoff; implementation awaits selection unless already authorized. Include verification and the applicable commit/push/deploy phase in that plan, with known targets and any genuinely missing authority.
1. **Run Read-Only Diagnosis**: Execute `npm run audit:site -- --root <site-path> [--runtime node-sqlite|cloudflare-d1-r2] [--db-snapshot <file>|--d1-dump <file.sql>] --out <private-report-dir>`.
2. **Present Findings & Propose a Phased Follow-Up Plan**: Always synthesize the report's `Recommended follow-up plan` into concrete, user-selectable tracks rather than stopping after printing the table:
   - **Track 1 — Skills & Provenance Sync**: Stage, review, and apply `sync:site-skills` and `sync:emdash-skills` on a feature branch; record intentional drift under `overrides` in `.emdash/site-skills.json`.
   - **Track 2 — Design-System Primitives, Card Accessibility & Token Engine**: Backport `global.css` rhythm/token architecture (`interpolate-size`, consolidated `.flow` with duplicate-margin guard, `.content-grid` subgrid, `[data-surface]`, 4-voice typography `--font-mono`/`--font-accent`, 3-tier surfaces `--color-elevated`/`--surface-glass`, `.bento-grid`/`.ui-specimen`, tactile `.btn--secondary`/`.btn--ghost`, `.clickable-parent`/`.focus-parent`, tokenized `@theme` `clamp()` scales), semantic `<article>` Card primitives with `transitionName` morphing and CMS edit forwarding, `SiteShell.astro` choreography (`data-surface-toggle`, `data-sticky-header`, `data-vt-loading`), `/_styleguide`, and `scripts/design-system.mjs` (`npm run design:tokens`). See [site-maintenance.md](site-maintenance.md) for the early-Baseline visual upgrade playbook.
   - **Track 3 — Route Template Adoption, Visual Redesign & `/_styleguide` Calibration**: Inspect actual routes in `src/pages/` and live rendered pages against the **5-Point Visual Self-Critique Rubric** and the **Early-Baseline & Legacy Pattern → Modern Baseline Upgrade Matrix** in `astro-site-design/references/migration-visual-audit.md` — opting long-form editorial templates into `<Container breakout>` (`.content-grid`), applying `data-surface="dark|muted|brand"` and 3-tier surfaces, upgrading uniform card rows or flat heroes with 4-voice typography and asymmetric layouts (`.bento-grid`, `.grid-hairline`, `<Sidebar>`, `.ui-specimen`), and saving `audit/component-calibration.md`.
   - **Track 4 — Framework, Adapter & Node Policy Alignment**: Evaluate lockfile versions (`astro`, `emdash`, `@astrojs/*`), `engines.node`, and apply `npm run audit:modernize -- --recipe schema-budget-prebuild@1` when the site lacks the prebuild schema-budget check.
   - **Track 5 — Live Browser, Visual & Editor Verification**: Run the site's test suites, `typecheck`, and `build`, verify `/_styleguide` and key public/editor routes across viewports, and propose branch merge/PR when verified.
3. **Iterate with Explicit Follow-Up Proposals**: After completing any approved track and re-running `audit:site`, always present the before/after delta **and immediately propose the remaining follow-up tracks** so the user can choose what to execute next or explicitly defer.
