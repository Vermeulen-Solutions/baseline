# Stages 4–4.5: art direction and component calibration

Read this when Stage 4 begins (Standard track) or at Express Checkpoint B. The art-direction gate in this file blocks site-specific visual implementation; calibration on `/_styleguide` is a required stage, not an optional review.

## Stage 4: set the art direction

Reference research is a shared `site-art-direction` step, independent of the iteration surface. Use [reference research](../../site-art-direction/references/reference-research.md) for the one inspiration offer, a brief-led shortlist across supplied sites, prompt libraries, community systems and OpenDesign systems/templates, and the existing adaptation pass. HTML/browser and Brilliant access the same local/public sources; catalogue reading never requires the OpenDesign app or its surface skill. Reuse the owner's supplied references and settled answers before asking anything new.

Use `site-art-direction` and its [shared iteration loop](../../site-art-direction/references/design-iteration.md): recommend Brilliant for a requested editable prototyping canvas when no tool is settled; default to HTML/browser when no canvas is requested; name Brilliant/OpenPencil/Penpot choices once when unresolved, compare two or three structurally distinct concepts side by side, select the direction, then prove it in Astro before broad rollout. Preserve a selected surface, including optional OpenDesign. For Penpot load `penpot-site-design`; for OpenPencil load `openpencil-site-design` alongside its official version-matched skill/API; for OpenDesign load `opendesign-site-design`. For Brilliant load `brilliant-site-design`, preserving source expressions and its documented export/undo limits. The same agent can complete the flow. Only when changing agents/sessions, save a portable brief/handoff with target IDs, approval evidence, source token expressions, native component mapping, responsive/states intent and open questions; never include a credential or depend on hidden MCP storage. HTML concepts under `audit/visual-concepts/` use the same review/selection criteria. Neither concept files nor canvas boards replace the Stage 4.5 styleguide or real-route browser acceptance.

Use `site-art-direction` with the brief, source audit, content model, real assets, and relevant references. Select a primary lane from `site-art-direction/references/aesthetic-lanes.md`, or Custom / existing brand with a rationale when those lanes do not fit. Define the narrative metaphor, 4-voice typography hierarchy (display, inline `.font-accent` contrast voice, reading body, and `.eyebrow-telemetry` monospace coordinates), 3-tier surface and border physics, hero visual specimen strategy (live-coded `.ui-specimen` console vs interactive capability stage vs prepared editorial photography), signature header archetype, spatial density, section pacing rhythm, and explicit anti-patterns. These are concrete defaults for new or replacement visual work. When a fixed brief or accepted existing direction requires an exception, record that specific exception and its visual rationale; do not silently omit the design checks or replace the examples with generic styling advice.

### Layout spacing choice (Standard and Express)

During the design handoff, explain briefly. Express uses the shared defaults in [express-track.md](express-track.md); Standard asks once when the spacing approach is unresolved and the brief or user calls for a tightly specified composition. Reuse existing answers:

> **Layout spacing:** Sections, content groups, and grids get consistent spacing that adapts to screen size. Shared settings keep changes consistent across the site, while individual layouts can have their own spacing. Article text uses flow spacing between headings, paragraphs, lists, and media.
>
> **Which approach suits this site?**
> 1. **Shared spacing defaults (recommended):** Calibrate the site's overall density, then use the layout components' defaults with deliberate local exceptions.
> 2. **Custom layout spacing:** Plan explicit spacing for the affected layouts, useful when matching a tightly specified composition. Shared tokens still keep those values maintainable.

For Standard, include any needed choice in the Stage 3 → Stage 4 handoff; for Express, include the explanation and recommended shared default in Checkpoint A's design handoff. Do not paste the two-choice question into Express unless the brief/user makes the architecture a real decision. Bundle any answer with visual direction, without a separate blocking approval. If the user has authorized autonomous design, state the recommended working assumption and proceed. Do not replay this prompt for scoped maintenance or existing-site updates.

Record the selected approach, density, intended exceptions and whether the choice was approved or assumed in `AGENTS.md`; record actual calibrated values/evidence in `audit/component-calibration.md`. Use neutral terms: **layout spacing**, **spacing tokens**, **stack/grid gaps**, **fluid spacing**, and **flow spacing**. These describe the architecture, not a named CSS feature or external product. Do not introduce product comparisons or a settings panel.

Both choices use the current `SiteShell` policy (`automatic-v2` is an internal compatibility identifier). A custom choice uses contextual aliases, explicit primitive gap/padding controls and `layout="custom"` where the caller owns display/gap. Do not switch a new site to `legacy`, disable editorial boundaries, remove gutters, or scatter arbitrary values to implement that choice. Verify the chosen relationship owners on `/_styleguide` before broad page assembly; see `docs/design-framework.md`.

Do not start broad visual implementation from the starter's neutral defaults. First record the approved direction or explicitly labeled working assumption in `AGENTS.md` following the mandatory Art Direction Record schema and canonical gate in `AGENTS.md` (you can scaffold a structurally valid record directly via `npm run design:tokens -- --lane <lane> --write-record` and refine its prose for the client brief); use a linked project document when the direction needs substantial visual references or component detail.

For any existing-site redesign, including an earlier Baseline site or a builder migration, distinguish refinement, significant overhaul within the brand, and replacement of the visual world. State which identity elements and compositions are fixed versus open to change; reuse an explicit user choice. For a significant overhaul or a different visual premise (new lane, metaphor or hero strategy), run the visual concept pass in `site-art-direction` before broad implementation: develop two or three concepts for a representative archetype using real content shapes and known assets, compare them against the brief and source identity, and resolve the direction decision. Concepts pass the **concept quality gate** in `design-iteration.md` (side-by-side with the current site and owner references; real proof matching the offer; structural, not token-skin, differences; no stand-in visuals) before the owner reviews them. Record which previous visual decisions are superseded, and update the superseded documents in the same step: replace or archive `DESIGN.md` and rewrite superseded `PRODUCT.md` paragraphs rather than appending below them, so later tools (for example Impeccable, which loads both) do not judge the new design against the old one. Reuse the single surface choice in `site-art-direction`'s `references/design-iteration.md`, including HTML/browser, Brilliant, OpenPencil, Penpot, optional OpenDesign and explicitly preferred named alternatives; do not repeat a settled checkpoint or silently skip an unresolved choice because implementation is generally authorized. Embed the narrative metaphor in generation prompts and treat concepts as references rather than exact implementation specifications.

## Stage 4.5: calibrate components before page assembly

Open the **Component calibration** path printed by `npm run dev` on Astro's local
origin. It respects base/slash policy: generated static sites default to
`/_styleguide/`, including the slash; their slashless URL returns 404. Release
previews intentionally omit it. Use the documented fixture build/serve commands
only when a separate specimen artifact is needed, not to recover a missing slash.

For URL/screenshot migrations or external component sourcing (such as `21st.dev MCP`), follow `astro-site-design/references/component-quarantine.md` after Stage 4 and its art-direction gate. Inspect representative source elements or candidate registry blueprints, then calibrate relevant tokens, states, and production primitives on `/_styleguide` before creating client page templates or bespoke sections — including `<Container width="reading|content|wide">` versus `<Container breakout>` (`.content-grid` with `.content--feature|wide|full|full-safe`), `<Card>` (`--card-*` custom properties, concentric radius math, and `.clickable-parent`/`.focus-parent` accessibility), and flow spacing (`.flow`). When sourcing external React/Tailwind components (e.g., from `21st.dev`), transmute them through the quarantine checklist: strip unnecessary React/Framer Motion runtime down to zero-JS Astro markup, replace hardcoded palette classes with semantic tokens, bind fluid typography/spacing steps, and wire EmDash live edit proxies only on the `emdash` profile. For greenfield work, review the relevant primitive baseline against the brief and record inapplicable source comparisons.

Save `audit/component-calibration.md` (you can scaffold or refresh the verified `## Token Calibration` table and SHA-256 digest via `npm run design:tokens -- --write-calibration`) with evidence, actual component APIs, supported surfaces/states, asset provenance, narrow/wide and keyboard/motion checks, unresolved gaps and ready/deferred decisions. Resolve gaps in components the representative pages will reuse before broad assembly. Keep normal-build route exclusion and synthetic fixtures intact. Page findings may reopen calibration; this is not a permanent component freeze. Use written handoffs between passes; fork/archive chats only when the user requests it.

**Gate:** the calibration record identifies which patterns are ready for representative pages and why; relevant checks pass. No source cloning, un-quarantined React/palette bloat, invented APIs, fake CMS edit identities, or specimen-only CSS repairs.

**Stage 4.5 handoff:**
Report the checked components, viewports, surfaces/states and unresolved limitations from `audit/component-calibration.md`. A saved token table alone does not establish rendered acceptance. When the calibration gate passes, continue to the shell and the representative page archetypes that best exercise the actual route/content model. Use an established page priority; otherwise explain the selection and proceed without requiring the user to choose an implementation order.
