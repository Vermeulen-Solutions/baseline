# Stages 5–7: build, verify and launch

Read this when Stage 5 begins (Standard track) or at Express Checkpoint C, and again for Stage 6 verification and Stage 7 cutover. Stage 7 runs only within authorization that covers deployment, content transfer or DNS.

## Stage 5: implement representative pages

Read [delivery-evidence.md](delivery-evidence.md) when representative work affects reuse, repeated content, owner editing or public-page loading. Show a compact route/component/data-owner/editing map, verify the loops that render repeated content and actual component render sites, and rehearse the owner's representative tasks before broad rollout. Source structure supports inspection; saved/public readbacks establish behavior. Keep these observations with existing route/calibration notes and preserve each profile's editing boundary.

Use the page brief's section argument and actual draft copy to inform the pacing blueprint below. When visitor intent or available evidence calls for a different order or proof treatment, record the concrete exception and retain the useful native composition recipes; never invent evidence to fill a prescribed section.

Before writing a representative page's markup, outline its **section-by-section pacing blueprint** so no two adjacent sections repeat the same 3-column card grid (for example: Asymmetric Hero with live-coded `.ui-specimen` or framed focal media → `.grid-hairline` proof/metrics ledger or `<LogoTicker>` → `<Sidebar>` sticky narrative + bento/capability matrix → `<Section data-surface="dark" class="surface-spotlight">` showcase band → native `<Disclosure>` FAQ). Use Baseline's 4-voice typography helpers (`.eyebrow-telemetry` and `.tabular-nums` on real metadata, `.font-accent` only where the brand has that voice; no kicker labels or decorative section indices), 3-tier surface utilities (`.surface-elevated`, `.surface-glass`, `.surface-spotlight`), and architectural grids (`.grid-hairline`, `.bg-grid-blueprint`, `.frame-crosshair`). For a preserved composition or a comparison layout that needs uniform rows, record the concrete exception rather than treating the pacing checklist as optional. The example sequence is one option, not a template for every page: vary it by content, and run the generic-fingerprint check in `astro-site-design`. Use real content; do not invent factual metadata or controls to populate a specimen.

Before adding incoming images, use the installed `media:prepare` workflow in
`docs/media-preparation.md`; inspect eligible stored copies before static asset
integration or EmDash upload/readback. Keep full-size originals outside the
library and Git. Use this for greenfield content as well as later maintenance.

**Static branch:** use the file-owned Base layout around shared `SiteShell.astro`, native `ResponsiveImage` metadata, Markdown RichText and static routes. Shared `Card` attribute bags need no edit proxies. Do not use CMS queries, cache hints or `Base content` bindings. Verify common styleguide specimens identically to EmDash; CMS-only specimens are inapplicable. The remaining CMS implementation instructions apply only to EmDash.

When references are screenshots/mockups or interaction recipes, route through `astro-site-design/references/visual-mockup-workflow.md`. Keep measured facts, responsive assumptions and editorial ownership explicit. `AGENTS.md` is the project instruction bridge; harness-specific rules are not universal enforcement.

Use `astro-site-design` for the design system, Astro components, responsive behavior, accessibility, and browser review. Use `building-emdash-site` alongside it for EmDash queries, cache hints, media, Portable Text, menus, and editor integration.

**SSR & Edge Performance Checklist (EmDash & Cloudflare Workers):**
- **Parallelize independent queries:** Always wrap independent `getSiteSettingsWithCacheHint`, `getMenuWithCacheHint`, `getEmDashCollection`, and `getEmDashEntry` calls in `Promise.all(...)` inside `Base.astro` and route templates; never await independent queries sequentially.
- **Scope relational hydration & avoid N+1 waterfalls:** Pass an explicit `references` filter to `getEmDashEntry(collection, slug, { locale, references: { ... } })` when a directory or schedule page only needs specific relations (cutting D1/SQLite query counts by 50–70%), and never run per-item `getEmDashCollection` queries when the inverse relation is already loaded on the parent entry.
- **Zero-R2-download SSR image dimensions & quality-80 WebP:** Preserve `{ width, height }` from CMS media JSON objects (`rememberImageDimensions()` in `src/lib/photo-gallery.ts` / `src/lib/image-source.ts`) so `imageSource()` never downloads raw files from R2 during SSR. Use `quality: 80` WebP in `ResponsiveImage.astro` and `loading="eager"` on primary card grids.
- **Immutable image caching (`1 year`):** Ensure `src/middleware.ts` and `src/lib/cloudflare-cache-provider.mjs` serve `200` `GET`/`HEAD` responses for `/_image` and `/_emdash/api/media/file/*` with `Cache-Control: public, max-age=31536000, immutable` (and `caches.default` on Workers), overriding EmDash's default `max-age=0, must-revalidate`.
- **1-hour public HTML edge caching (`PUBLIC_CACHE_SECONDS = 3600`):** On low/medium-frequency sites, use a 1-hour (`3600s`) public HTML cache budget with `src/lib/cloudflare-cache-provider.mjs` (`caches.default` for anonymous GETs + `Cloudflare-CDN-Cache-Control: no-store` so `*.workers.dev` never serves cached anonymous HTML to cookie-bearing admin sessions). When using Eventual or public feed plugins, validate feed splits/tags and cap HTML `maxAge` by the next upcoming event start/end boundary (`Math.min(PUBLIC_CACHE_SECONDS, boundaryCap)`) rather than clamping HTML caching to a 15-second plugin feed TTL.
- **Silky 250ms GPU View Transitions & hover image pre-decoding:** Use native `250ms` root View Transitions, `600ms` slow-network threshold for `data-vt-loading`, and 20ms link-hover HTML + `img.decode()` pre-warming (`SiteShell.astro` / `public-navigation.ts`) with strict CMS editor native navigation guards (`keepEditorNative()`).

Calibrate tokens in `src/styles/global.css` using `npm run design:tokens` (`scripts/design-system.mjs`) and inspect live updates via Vite HMR on `/_styleguide` and representative routes. Verify WCAG AA perceptual contrast across default and `[data-surface="dark"]` contexts, fluid `clamp()` bounds, and actual font faces/weights with `npm run design:tokens` and `npm run test:design`. If `@perkyzz/emvb` was enabled in Stage 2 for visual landing pages, wire `resolveEmVBPage(Astro)` and `<EmVBPage />` in `src/pages/[slug].astro` and sync EmVB site styles with the project's OKLCH palette via `@perkyzz/emvb-mcp`.

Build the shell and one representative page from each archetype that has its own template or section sequence before expanding across every route. Feed implementation findings back to the content model or art direction when real content exposes a weak assumption; update the site record when a decision changes.

For EmDash pages selected for blocks composition in Stage 3, create the site-specific sections as part of the authorized implementation: define the block types and collection field, build the Astro renderers using the calibrated design/primitives, add the canonical typed component map, and render representative stored compositions on the actual server-rendered routes. A fresh site's seed reproduces these definitions/content; an existing site's schema/content changes use its authorized native migration workflow. Single-version types can render directly; introduce exhaustive version dispatch when multiple versions are retained. Verify editor add/edit/reorder/remove, save and reload, plus the resulting public composition after authorized publication; report unavailable editor acceptance explicitly. Defining a schema or showing a hardcoded mockup alone does not finish the selected blocks feature.

Once representative pages render, load `impeccable` for a bounded visual critique of those routes. Use its critique and audit guidance to identify hierarchy, typography, spacing, responsive, accessibility, and interaction issues, then fix shared tokens or components before multiplying the pattern across the route inventory. Treat the critique as implementation evidence alongside the brief and source audit; it does not replace those inputs or authorize changing preserved content facts.

**Gate:** representative pages work with real content at mobile, intermediate, and wide viewports, and establish reusable patterns for the remaining routes. The main visual findings from the Impeccable pass are resolved or recorded.

**Stage 5 handoff:**
Report which representative routes render, the browser/Impeccable findings addressed, and any remaining content or interaction gaps. Offer the preview for inspection while continuing the remaining authorized routes and Stage 6 checks. Pause for a user review only when requested or when a consequential unresolved decision prevents further work.

## Stage 6: complete and verify

**All profiles:** run `npm run verify`, `npm run build` and `npm run check:dev-tools`, inspect routes, responsive images, focus and 404 behavior. Static builds must contain no server adapter/database and exclude `/_styleguide`; never deploy fixture output. Sveltia also needs real-account auth/upload/save/rebuild/logout checks before editorial handoff; a local build does not prove those. Existing Windows screenshot baselines and CMS registry commands are EmDash-only; static projects record browser evidence directly.

Finish the route inventory, content states, interactions, metadata, and accessibility behavior. Check that every primitive the route inventory names is actually built. When site search was chosen, run `npm run search:index` after the build (EmDash: from an explicit `audit:html` snapshot) and complete the browser acceptance in `astro-site-design/references/shipped-primitives.md`; configured search without a built index is not done. Follow the visual review and repair passes in `astro-site-design`, and run one final Impeccable critique or audit when the full route set is available. Fix findings that recur on two or more routes in shared styles or components, then stop once the review is coherent. Run the repository's requested checks and build. Verify public and editor modes for CMS-rendered content.

Review representative rendered content against its page brief using [discovery-and-content.md](discovery-and-content.md#review-the-representative-result): audience/offer clarity, priority question coverage, supported claims, and an action that delivers the promised next step. Keep concrete observations beside existing acceptance evidence; agent review does not prove user understanding or post-launch performance.

Use [delivery-evidence.md](delivery-evidence.md) to reconcile the structure/owner-task map with actual loop/component, font/asset and applicable public-page performance evidence. Report source-only or unobserved items honestly. Optional browser tooling remains local-only and does not introduce a universal score or replace editor/publication acceptance.

Use `astro-site-design/references/rollout-verification.md` for browser availability, valid capture evidence and route coverage. If a native browser fails, discover supported built-in or connector alternatives before declaring browser acceptance unavailable; an actual permission/policy denial must not be bypassed. Before ending a multi-deliverable request, reconcile its completion register using [the maintenance closeout guidance](site-maintenance.md#reconcile-completion-before-handoff). Continue required, authorized work while it is possible; an attempted check or saved checklist is not a completed acceptance step.

Use `emdash-site-setup` again for deployment and site transfer. Treat deployment of code and transfer of CMS data as separate operations.

**Gate:** every required route and distinct state is accounted for; visual, content, responsive, accessibility, and editor-mode findings that affect a visitor task, a brief criterion or accessibility are resolved or explicitly documented. For EmDash migrations with the installed command, run `npm run migration:verify -- --scope full --manifest audit/url-inventory.json` to verify HTTP statuses, 301 redirect chains without loops, SEO tags, link/image integrity, and content inventory reconciliation (`docs/migration-acceptance.md`). On all profiles with the updated portable tools, generate an acceptance manifest with `migration:wordpress acceptance` and run the installed `migration:verify`; full scope keeps missing content/editor/design evidence unverified. Static migrations follow `docs/wordpress-migration.md` and their installed checks; older sites need reviewed additive adoption before invoking absent commands.

On EmDash, before declaring a new-site workflow complete, use `npm run site:register` with the actual stable site/repository/runtime/owner and starter version metadata. Follow `docs/site-registry.md`: submit a reviewed private registry change within existing authorization, or retain the ignored pending-registration artifact and record its reason when central access or submission authorization is unavailable. Reuse the same site ID for renames; do not publish private client details in the starter or invent a stable release for an unreleased checkout.

**Stage 6 handoff:**
Report actual route coverage, automated results, browser/editor acceptance and pending checks. Distinguish a verified local build from deployment and launch acceptance; avoid blanket claims of full verification when required evidence is missing.

Use the selected profile and hosting decision for any Stage 7 preparation: static `dist/` and build/404 configuration; Node startup, persistence and reverse proxy configuration; or Workers bindings, preview and cutover configuration. Complete authorized local preparation before requesting any missing external-action authorization, and identify the concrete deployment/content-transfer/DNS action it would cover. If deployment is already authorized, continue without asking again. If the requested scope ends at a local build, deliver that result with remaining launch work recorded.

## Stage 7: production cutover, email & forms

**Static branch:** deploy verified `dist/`, configure canonical URLs, TLS and 404 status, verify rebuild-on-commit and rollback to the last successful build. For Sveltia verify admin assets, OAuth origins/callbacks or PAT access and fresh sign-in, upload, draft behavior and publication with real accounts. Record static deployment ownership, browser evidence and source/asset backup policy in project notes. Do not run EmDash registry, database backup or CMS cutover commands. Only use external form/mail services required by the brief; preserve existing mail DNS. The remaining cutover instructions are EmDash-only.

For migrations, follow `docs/migration-cutover.md` to enforce the pre-cutover content freeze (`T_freeze`), reconcile late source edits/deletions/slug shifts, and establish rollback triggers. For Node.js targets, acquire a consistent SQLite backup via `.backup` or `VACUUM INTO` paired with media and `.env` secrets per `docs/node-backup-restore.md` (naive copying during active WAL is prohibited). Complete the `docs/editor-handoff.md` guide covering editor roles and the peripheral integrations checklist.

Use `emdash-production-cutover` when moving a Cloudflare Workers site from preview/`workers.dev` to its production custom domain. Establish and test admin recovery before changing the authentication origin, configure the canonical hostname and alias redirects, and verify fresh production login. Preserve working email providers and form integrations; configure Cloudflare Email Sending or replace forms only when requested or required by established site requirements.

**Gate:** complete applicable setup/cutover checks within existing authorization using repository configuration and supported tools. First launch and domain changes require valid TLS/aliases, fresh mode-specific login, preserved corporate mail and applicable form delivery. Use the site's normal deployment and supported migration mode. Added/pending core migrations or data-changing actions need a database recovery point before startup/deploy; on D1, record a Time Travel bookmark using existing Wrangler access. Reuse existing media/key recovery versions when unchanged. Do not require a new API token, managed migration pipeline or fresh full backup bundle merely for a version upgrade or ordinary redeploy. Use docs/cloudflare-backup-restore.md for actual migration/recovery operations and docs/edge-cache-lifecycle.md for affected cache behavior. Run publish/purge/provider/cron acceptance when launching the site or changing those surfaces. Node targets use their applicable recovery runbook. Leave unobserved checks pending; request only consequential missing access/inputs or actions unavailable to the agent.

**Stage 7 handoff:**
State whether the result is prepared configuration, a preview deployment or an observed production launch. Report only the TLS/domain, profile-specific login/publication, mail/form and recovery checks actually performed; retain missing evidence as pending. For EmDash, finalize the required registry record or pending-registration artifact within the existing submission authorization. Static profiles record ownership and acceptance in project notes. Record backup/restore ownership and any agreed follow-up; do not start ongoing monitoring without a request.
