# Inspectable implementation and owner tasks

Use during representative implementation and delivery, or when a scoped change affects repeated content, reuse, editing or loading behavior. Reuse route notes, calibration and the execution register; this reference does not add a mandatory document, tool or checkpoint. Source observations, browser observations and owner acceptance are distinct evidence.

## Show what was built

For the representative journey, give the operator a compact map: **route → template/components → repeated data source or field owner → editing location → observed result**. Point to actual source/entry/field identities and describe unresolved relationships. Do not copy full schemas, component APIs or inventories into another registry. The optional installed `baseline:inspect -- --structure --json` can supply bounded source observations; ordinary source review remains complete when it is unavailable. Imported code, literal field hints and source loops do not establish runtime use or successful editing.

Choose content ownership and presentation reuse independently. A service can be a collection record rendered through a shared service-card component; one-off hero copy can still belong to an editable page field. Repeated presentation alone does not establish an entity's independent lifecycle, and component props do not make embedded copy editor-owned. Use Stage 3's existing content model and the selected profile's actual editing needs; this distinction adds no new table or checkpoint.

Use semantic components where the same content/interaction contract recurs and a shared change should remain consistent, such as a service card, result row or section introduction. Expose only meaningful variants; preserve natural text, image, heading and action ownership. A component defined but unused is not reuse. Do not force unrelated one-off sections into a page-sized component or a universal configuration object.

Render repeated data through the selected profile's real collection/query or owned data array and a native loop, passing each item's values into its component. Avoid manually copied cards for independently managed records. Fixed illustrative content does not automatically need a CMS collection, and two similar visual boxes alone do not justify extracting a component. Preserve semantic list structure, item ordering, stable destinations, meaningful image alternatives and field edit identity.

## Verify loops and components, beyond source shape

Choose a small representative record and two intended instances in an authorized local/disposable surface. Record the initial item identities/order and meaningful text/media, not just a total count.

- Add or change one record through the actual content owner. Save/reload and perform the profile's publication/rebuild step. Confirm the intended list changes once without a template edit, unrelated items remain, and the new destination/content is correct. Include an empty or missing-value state when the change makes that state relevant.
- For a repeated component, identify its actual import/render sites. Apply an authorized bounded shared change and inspect the intended instances at narrow and wide placements. Confirm existing copy, destinations and edit ownership remain intact. Do not require a cosmetic change merely to test an untouched component; use the current requested change or an isolated synthetic rehearsal.
- Keep query, loop and component observations separate from runtime conclusions. A `.map()` expression over a hardcoded demo array is not proof of CMS ownership; matching screenshots of two copied cards are not proof of a shared component.

Restore synthetic test content or retain it only in its owned disposable fixture. Do not create public sample reviews, customer identities or factual claims to populate a real page. Existing CMS data requires the site's supported write/recovery scope; a seed edit is not a migration.

When authorized work is delegated, use [parallel-delivery.md](parallel-delivery.md) for bounded ownership and dependency-aware handoffs. Same-agent delivery remains complete. For a selected canvas change that affects tokens, use [the token handoff recipe](../../site-art-direction/references/token-handoff.md) when installed before broad component rollout.

## Rehearse the owner's actual tasks early

Derive a few tasks from established editing needs on the representative route before broad rollout. Use visitor/editor language, for example “change the displayed service price”, “add another service” or “replace this photograph and description”. Section add/remove/reorder is a task only when the agreed model supports it; do not introduce a page builder to satisfy an invented requirement.

| [specific owner task] | [file or collection/entry/field, actual editing surface] | [where the value appears and what must remain unchanged] | [save/reload/publication/rebuild/readback observations, or pending owner step] |

Use file edit → validation/build/public render for static, actual browser edit → Git/rebuild/public render for a Git-backed editor, and registered field → save/reload/draft/publish/public render for the relational CMS. Verify supported structured-editor paths for images, references, repeaters or non-inline fields. Owner ability to use the interface is a separate observation from an agent/API successfully writing data. Record which was tested; do not substitute an annotation or source-only task map for a completed round trip.

Keep this map with existing acceptance notes, then use it for the owner handoff. Record developer-owned areas and unresolved access/publication tasks. Reuse established decisions and authorization instead of asking for a new approval for every save.

## Read actual fonts, assets and public-page costs

During calibration and representative browser review, inspect rendered text after fonts/styles settle, including relevant weights and non-ASCII content. Source font declarations and readiness alone do not prove the intended face rendered. Compare actual rendered faces where browser tooling exposes them, CSS family/weight, failed requests and the visible result. Record intentional fallback and canvas-only substitutions. Repair missing files/configuration before multiplying a mismatched template.

For media, follow the installed preparation/upload workflow, then inspect the actual selected asset, dimensions, crop/fit, caption/alternative and ownership. A successful upload is not proof that the route uses that stored file. Keep originals outside the content library/Git and do not add another asset manifest when an existing preparation/readback receipt owns the fact.

When loading behavior matters or a representative release review is in scope, use the installed optional `audit:page` command and `docs/page-performance.md`, or equivalent supported browser evidence. Record the production build/route, viewport, browser, cache/network/CPU conditions, resource costs, loading/layout-shift observations and failures. A development-server sample is development evidence. External-resource blocking and unavailable metrics limit interpretation. Compare like conditions and investigate material regressions; no universal score or mandatory new analytics/monitoring follows from this guidance. Set budgets only from actual site requirements and preserve approved exceptions. Local browser runs stay outside automated CI and production builds.

## Close the visual feedback loop

Within authorized review work, translate each meaningful comment or chat request into **feedback → confirmed target → bounded change → inspected result → remaining status**. Reuse an existing tracker/decision note. Confirm the document/route and affected component/token/content owner before writing; broaden verification when a shared change affects sibling pages. Apply a small coherent batch, then inspect the relevant saved render or actual browser result.

Distinguish addressed in concept, implemented, browser-verified and owner-approved where those differ. A resolved comment is not approval or native-route acceptance. Reacquire targets after reconnect/reopen and inspect current state before retrying uncertain writes. Use supported comment APIs when available, with the selected design skill's permission/identity rules; chat and a small before/after comparison remain complete alternatives. Do not add a messaging service, duplicate full-site canvas or mandatory reviewer to perform a local correction.
