# Astro site design and implementation

Treat optional `DESIGN.md` proposals as reference material and reconcile them with `AGENTS.md` and shipped CSS. Validate implemented tokens with `npm run design:tokens` and inspect the rendered result; preserve fluid expressions and contextual aliases when translating external values. No exchange schema or validator is required. If a handoff needs a specific validator/exporter, select and install it separately; use `docs/design-interchange.md` for further guidance when available. External tool markup still needs the selected profile's content ownership and native image integration. On a site without these commands, check `package.json` `scripts` first and follow the command-availability rule in `new-site-workflow` (Start here): use the site's own equivalent or a reported manual check, and never install Baseline tooling just to match a command name. An incomplete token set reports a `Contract gap`; see `site-art-direction/references/token-handoff.md`.

Build maintainable, accessible Astro pages and components. When a source site or visual reference exists, inspect its actual rendered appearance before implementation; do not substitute a vague textual approximation for visual review.

When the Art Direction Record says `Motion Tier: impression`, build the smoothed scroll, the Interlude page transitions and the pinned scene from [impression motion](references/impression-motion.md) before anything else in this paragraph: they are required on that tier, they may use scripts, and `audit:composition` checks them. For other requested motion, imagery, charts, 3D or other specialist behavior, use [capability routing](../site-art-direction/references/capability-routing.md). For effects borrowed from distinctive sites (springs, hover lifts, word reveals, rolling numbers, command palettes, link previews, textures, sound), read [interaction techniques](references/interaction-techniques.md) for the technique under each and the fallback it needs. Keep the selected surface and existing runtime; for UI motion read installed Impeccable `reference/animate.md`, then implement and review the mechanics with [interaction motion](references/interaction-motion.md) through CSS/WAAPI or the site's adopted library. Inspect actual interaction, interruption and reduced-motion behavior in the browser; a canvas film does not prove website behavior.

For asset-specific work follow site-art-direction's [brand assets](../site-art-direction/references/brand-assets.md) or [editorial illustration](../site-art-direction/references/editorial-illustration.md) reference. For reader announcement/focus acceptance use [bounded screen-reader checks](references/screen-reader-checks.md); semantic/keyboard checks alone do not establish actual reader output.

## Platform presentation boundary

For repeated content and reusable presentation, follow `new-site-workflow/references/delivery-evidence.md` when installed: trace actual query/data ownership, loop output and component render sites, then verify the relevant content change and shared instance behavior. Keep file-owned static content separate from CMS collections/editing. Existing route notes can hold the compact map; no new registry or blanket component extraction is required.

Read `baseline.config.json` first. `static` and `static-sveltia` use native Content Collections, `getStaticPaths()` and Markdown `render()`; skip `building-emdash-site` and all CMS binding/modeling specialists. Existing EmDash API/editor/cache instructions below apply only to `emdash`. Localized static routes follow the project's file/URL model rather than assuming CMS translation groups.

Use shared `src/layouts/SiteShell.astro` for document metadata, global styles, skip link and landmarks. A site whose public pages are dark by default passes `darkReaderLock` to it, so the Dark Reader extension does not recolour its light text to near-black. Platform `Base.astro` wrappers supply file-owned settings/navigation or EmDash contributions. Keep queries, widgets and storage out of shared primitives. `Card.astro` accepts ordinary HTML attribute bags; pass edit annotations only from an EmDash caller.

`ResponsiveImage.astro` accepts native Astro ImageMetadata (from `src/assets`) or a resolved URL with dimensions and uses Astro image processing. Do not add a storage endpoint to static sites. Native EmDash image fields must be passed whole to `Image` from `emdash/ui`; `url`/`src` may be absent on their provider/reference values. Baseline's `EmDashImage.astro` resolves already-known URLs for presentation, not arbitrary native field objects. Verify a CMS-saved image reference through actual rendering; do not treat upload success as proof. Where installed, `PhotoGallery fit="contain"` preserves full image frames; its omitted/cover default retains existing cropped previews. Static RichText wraps native Markdown in `.flow` plus `data-editorial-content`; Portable Text is a platform extension. `flow={false}` relinquishes both defaults, wrapperless unless attributes require a plain wrapper.

**Framed photographs take the shape of the photograph.** A fixed-height frame with `object-fit: cover` hid the top 27% of group photographs on tablets, where the faces were. The recipe that held for ten photographs between 1:1 and 3:2 at ten widths (at most 1% hidden on any side): set the frame's `aspect-ratio` from the stored image dimensions, clamped to the range the design allows; limit the frame by a maximum height and make it narrower rather than cropping when the limit is reached; and when one end of the frame is rounded, keep the radius well under half its height (about a quarter at most, never a `999px` pill end), so the corners of the photograph, and whoever stands there, stay in view.

```astro
---
// image: ImageMetadata or a stored field with width and height.
const ratio = Math.min(Math.max(image.width / image.height, 1), 1.5);
---
<figure class="photo-frame" style={`--ratio: ${ratio}`}>
  <ResponsiveImage src={image} alt={alt} />
</figure>
```

```css
@layer components {
  .photo-frame { --frame-max-h: 32rem; aspect-ratio: var(--ratio); inline-size: min(100%, calc(var(--frame-max-h) * var(--ratio))); overflow: hidden; }
  .photo-frame img { inline-size: 100%; block-size: 100%; object-fit: cover; }
}
```

Only the clamp crops, and only for photographs outside the allowed range. `audit:ui` reports `image-cover-cropped` when a frame hides more than 15% on one side; mark images that are meant to be cropped (backgrounds, textures) with `data-audit-crop-ok`.

For incoming imagery in a greenfield build or day-2 maintenance, follow the installed `docs/media-preparation.md` and `media:prepare` command before storing/uploading it. Inspect intended use and output quality, use eligible prepared copies, and keep full-size originals outside the library and Git. Static profiles add those copies to `src/assets/`; EmDash uses the selected instance and `media:upload` readback when installed. A prior WordPress migration is not required. Existing sites without these commands need the explicit adoption described in `docs/baseline-updates.md`; do not invent an installed capability.

Calibrate tokens, typography, layout, cards, ticker and native images on the same common `/_styleguide` on both foundations. EmDash adds Portable Text/storage specimens separately. Static editor-proxy checks explicitly report inapplicable; this is not an editor verification pass. Production builds must exclude the route and fixture artifacts must remain nondeployable. Generated static sites support manual browser acceptance, not the EmDash-specific screenshot/registry harness. Follow the generated README's actual commands.

## Inspect before implementing

For URL-to-Astro migrations, read [references/component-quarantine.md](references/component-quarantine.md). After content and art-direction gates, calibrate real production primitives on `/_styleguide` before broad page assembly. That reference defines open composition versus semantic composites, surface-aware action patterns, the `src/assets/`/CMS image boundary, safe zero-JS LogoTicker slots and written handoffs. Follow its recorded Stage 4.5 gate; preserve the default-production route guard.

For flat screenshots, visual mockups or external interaction recipes, read [references/visual-mockup-workflow.md](references/visual-mockup-workflow.md). It defines evidence metadata, semantic translation, contextual safeguards and clean-source verification without changing upstream skills.

For a WordPress migration or redesign of an existing site, first read [`references/migration-visual-audit.md`](references/migration-visual-audit.md). It defines the route inventory, source evidence, preserve/improve decisions, and final page-by-page QA required for that work.

1. Use available browser automation to inspect the source site before asking the user for screenshots. Capture each distinct page archetype and unique editorial page at consistent desktop and mobile sizes; capture full-page views so content below the fold is included. Sample repeated records with different layouts or fields. Inspect rendered screenshots and, when available, the DOM and computed styles. If the site requires authentication, blocks automated access, or a relevant page/state cannot be reached with available tools, ask only for the missing access or reference rather than inventing the design.
2. Record a compact visual and content inventory: route/page type, content hierarchy, layout, typography, colors, spacing, imagery/crops, repeated components, interaction states, and responsive changes. Record which recognizable elements to preserve and which specific problems to improve. Verify the meaning of functional assets from nearby copy, links, captions, and destinations; do not infer their purpose from appearance alone.
3. Before coding, establish the design direction. For WordPress migrations, default to improving the design unless faithful reproduction is requested. Treat the source as evidence of content, purpose, and identity, not a quality ceiling or pixel target. Write down the brand cues and functional details to retain, the design weaknesses to solve, and the intended improvements in hierarchy, typography, composition, imagery, navigation, and responsive behavior. Do not silently turn it into a different identity, remove distinctive motifs, or replace meaningful source imagery with generic decoration. Read the design-direction and comparison criteria in `references/migration-visual-audit.md`.

For WordPress sources built with Blocksy, Stackable, or Elementor, inspect the relevant theme/builder configuration as well as the rendered pages: global styles, headers/footers, archive/single templates, reusable sections, dynamic fields, responsive overrides, and interactions. A content export or screenshot alone may miss these. Use them to recover the design rules and behavior, then rebuild in Astro; do not copy generated builder markup or CSS. See the [WordPress content migration skill](https://github.com/Vermeulen-Solutions/baseline/blob/main/.agents/skills/wordpress-to-emdash-content/SKILL.md) (`.agents/skills/wordpress-to-emdash-content/SKILL.md` in EmDash sites) for a builder-specific inventory checklist.

Treat per-element IDs and generated builder styles as clues about the source, not as a styling API to port. If repeated items such as Stackable cards have individually assigned IDs, colors, spacing, or typography, compare several instances and determine which differences express real content or intentional variants and which are accidental drift. Model the repeated content as data and render it through one Astro component with shared tokens; add only a small number of named variants for deliberate differences. Use IDs only when identity is needed for anchors, labels, or ARIA relationships, not for visual styling. Do not reproduce each card as a hand-styled one-off.

## Implement clean Astro

For a multilingual site, use the locales and default locale agreed during setup. Astro owns locale-aware public routes; EmDash stores each translation as a separate entry in a linked translation group. Pass `Astro.currentLocale` to EmDash entry, collection, menu, and taxonomy queries. Build locale-aware links and a language switcher from available translations, and include canonical and hreflang metadata on every page that has a translation. Keep each locale's content, menus, and publication state intentional; don't assume fallback supplies collection listings or translates UI copy. Code that reads a value out of a text field (a time, a date, a price, a score) must read every locale's way of writing it: translated rows often write `19:30` where the default locale writes `19h30`, and a parser that knows one form silently drops the other locale's rows. Test such code against each locale's real rows, from production rather than an older local copy; print it back in the page's locale. Follow EmDash's [internationalization guide](https://docs.emdashcms.com/guides/internationalization/) and verify the default locale stays unprefixed so `/_emdash/admin` continues to work.

- Treat WordPress output as reference content and visual behavior, not markup to copy. Rebuild from semantic HTML, accessible controls, and focused Astro components; do not carry over Gutenberg/Elementor/Stackable wrapper trees, shortcodes, or theme-specific CSS as the new architecture.
- Identify repeated site-wide patterns and make reusable layouts/components for them. Use shared design tokens and component-level classes; avoid one-off inline styles and duplicated page CSS when a shared rule or component is appropriate.
- Inspect the project first and follow its existing styling conventions when they are sound. For a new site or a substantial visual rebuild, use the project's fluid token baseline: Tailwind CSS v4 with CSS-first `@theme` tokens, fluid type and spacing scales (including high-contrast `-to-` bridge steps), semantic spacing names, multi-layer OKLCH elevation shadows, and small semantic Astro layout components. Do not migrate a sound existing system just to standardize it. Do not add Tailwind v3 or the legacy `@astrojs/tailwind` integration to a new project; use Astro's documented Tailwind v4 / `@tailwindcss/vite` setup and verify it against the installed Astro version.
- Use a three-tier architecture: (1) CSS design tokens and base rules, (2) semantic Astro structural primitives, and (3) agent instructions/recipes that constrain composition to the first two tiers. Do not recreate a large combinatorial runtime utility framework.
- Define fluid scales mathematically rather than choosing unrelated `clamp()` values by eye. Choose minimum and maximum values and viewport bounds, calculate the linear interpolation, and encode the result as `clamp(min, calc(intercept + slope * 100vi), max)` tokens. `vi` is the default for viewport-wide fluid type and spacing; use `cqi` for a component that should respond to its containing layout only when an ancestor establishes an inline-size query container. Document bounds and keep the min/max legible at zoom and narrow widths. Prefer a small intentional scale with paired steps (for example, type and space steps) over a large list of near-duplicates.
- Choose responsive behavior by what controls the available space: use intrinsic CSS first, then a container query for a component whose placement changes its width, then a media query for viewport-level behavior. Keep user-preference media queries for motion, contrast, and similar settings. A breakpoint should reflect where content stops working; share a named breakpoint only when multiple parts of the site genuinely need the same threshold. Read `references/responsive-architecture.md` when designing responsive components or changing the site's responsive strategy.
- Centralize palette, font, content widths, type, spacing, breakpoints, radii, borders, shadows, layering, and motion values. Use semantic spacing tokens such as content, grid, and container gaps rather than unexplained one-off layout values. In Tailwind v4, map CSS tokens through the appropriate `@theme` namespaces when they should create utilities; retain regular CSS custom properties for semantic aliases and values that should not create utility APIs. Define color primitives in OKLCH where suitable, then define semantic roles such as surface, text, border, action, and status. Derived shade/alpha steps must still be checked for perceptual consistency, theme behavior, and text/control contrast; don't assume a generated shade is accessible.
- Avoid styling through IDs, long high-specificity selector chains, or escalating `!important` overrides. Let Tailwind utilities, shared component classes, tokens, and deliberate cascade layers express the design. Use `!important` only to contain an override for an external style that cannot be changed, and leave a brief explanation.
- Build semantic Astro primitives such as `Section`, `Container` (`width="reading|content|wide"` for standard sections, `breakout` / `.content-grid` for long-form editorial flows with wide callouts/media), and `Grid` when they encode repeated structure or responsive behavior; use `Card` (`<article class="card">` with `.clickable-parent` / `.focus-parent` on the heading link, `--card-*` custom properties, and concentric `--card-media-radius` math) when its content/link contract is consistent. Keep APIs small and explicit. Don't wrap every element or turn Astro into a client-rendered component system.
- **Blueprint section pacing before assembling routes:** For an organisation, a place or a maker (clubs, associations, schools, churches, workshops, local businesses), plan each page by weight and set each content type as the real object it is, following `site-art-direction/references/distinctive-direction.md`, and build the signature moments with the expressive layer (`MediaStage`, `IndexList`, `.display-fit`, `data-shape`, scroll reveals, `transitionStyle`; see [shipped primitives](references/shipped-primitives.md)). The conversion engine below is for software, product and campaign pages. For marketing, landing, or conversion surfaces, reuse the page brief and actual draft copy, then follow the strategic intake, conversion copywriting formulas (`"{Outcome} without {pain}"`), and default section build order in `references/landing-page-archetypes.md`. Record a concrete content-led exception when visitor intent or available evidence calls for a different order or proof treatment; never invent evidence to fill a section. Before writing a page template, write down its section-by-section structural sequence so no two consecutive sections share the same layout geometry (never stack consecutive 3-column card grids). Alternate across: (1) Asymmetric 7/5 or 6/6 Hero with a live-coded `.ui-specimen` or framed focal visual, (2) Exposed `1px` `.grid-hairline` metrics/proof ledger or `<LogoTicker>`, (3) Asymmetric `<Sidebar>` sticky narrative paired with a bento/ledger matrix, (4) High-contrast `<Section data-surface="dark" class="surface-spotlight">` showcase band, and (5) Native `<Disclosure>` FAQ + closing conversion band. These five are a menu, not a fixed order: take the sequence from the page brief's section argument, vary it between page archetypes, and leave out a block that has no real content behind it. The generic-fingerprint check below fails the same sequence repeated on every page.
- **Baseline utilities:** before writing typography roles, surfaces, actions, hero specimens, micro-islands, page transitions or Astro platform features, read [references/baseline-utilities.md](references/baseline-utilities.md) and use the existing utility for the visitor need. Two rules apply to every page: keep adjacent inline elements on one line or join them with `{' '}`, because Astro v7 `compressHTML: 'jsx'` strips the newline between them and words concatenate (`Engineered for <em class="font-accent">precision</em>`); and pass `loading="eager" fetchpriority="high"` to the above-the-fold hero `<ResponsiveImage>` (or `priority` on native `<Image />`/`<Picture />`), because it is usually the Largest Contentful Paint element.
- **Shipped interaction and navigation primitives:** before composing a route that needs site search, a table of contents, heading permalinks, tabs, copy buttons, callouts, numbered steps, a theme control or live announcements, read [references/shipped-primitives.md](references/shipped-primitives.md). These components ship on every profile but render only when a template uses them; build the ones the route inventory names instead of writing parallel versions.
- **Native browser features:** before writing client JavaScript for an overlay, dismissal, positioning, disclosure, tabs or toast, or before adding a UI dependency, read [references/shipped-primitives.md](references/shipped-primitives.md), then [references/native-platform.md](references/native-platform.md). The second holds the browser support policy: essential content, navigation, forms and focus need Widely available features or a tested fallback, because Baseline's automated browser checks run only in Chromium.
- Use the shipped spacing ownership in `docs/design-framework.md`: site-owned Base activates `automatic-v2`; shared SiteShell defaults legacy. Section owns padding (one fluid section step set once; with `sectionJoins="shared"` two sections on the same ground share one step and a ground change keeps both; named exceptions are `spacing="medium|content|none"`, never per-page numbers; contextual spacing is for content inside text only) and container gap, Container owns content gap, Grid owns grid gap, and the shell owns horizontal gutters once. Local modes reset; `spacing="none"` changes padding only. Choose `layout="custom"` for caller-owned display/gap and retain breakout's named grid. Root `--layout-*` aliases reuse existing scales and can be scoped regionally. Generic `.flow` spaces direct siblings; RichText/explicit `data-editorial-content` owns prose controls, bounded at `data-editorial-island` roots. Avoid duplicating a layout gap with flow/space-y margins. Check actual inline-editor select/type/save/reload when changing CMS renderer boundaries. For day-2 changes preview a narrow `design:tokens --set` request, review its diff, write explicitly and verify the saved source plus affected rendered compositions. Do not create a second token store or spacing settings panel.
- Keep utilities and semantic CSS complementary: Tailwind utilities are useful for clear local composition; component classes and Astro primitives own repeated patterns and complex responsive behavior. For macro layout, prefer structural components and named contextual tokens over default-scale guesses such as `gap-7`, arbitrary values such as `p-[22px]`, or duplicated ad hoc media queries. Do not ban every fixed value: a documented local exception is better than distorting a component API. Use breakpoint variants/media queries for real discrete behavior changes, not to patch around a missing fluid token. With Tailwind v4, component `<style>` blocks are separate style contexts; prefer shared CSS variables or classes from the global stylesheet rather than assuming `@theme` values or `@apply` are automatically available there. If using Tailwind directives in a component style, follow the current `@reference` guidance.
- Include accessible interaction tokens and behavior alongside visual tokens: visible focus styles, hover/active/disabled states, reduced-motion handling, adequate target sizes, and sufficient text and non-text contrast. Honor semantic HTML and keyboard behavior; design tokens do not replace accessible markup or testing.
- Treat WCAG 2.2 AA as the default implementation target unless the project names another standard. Accessibility is a design and content requirement, not a final color-check pass: check landmarks/headings, link and control names, keyboard operation/focus, form labels/errors/status, alternatives for meaningful imagery, contrast, zoom/reflow, motion preferences, and pointer targets. Do not claim conformance based only on automated checks; include manual keyboard and responsive checks.
- Keep HTML semantic and responsive, keyboard-accessible, and readable. Use Astro for mostly static rendering and add client-side JavaScript only for interactions that need it. Every control works without JavaScript; one that cannot (a map, a live configurator) says so in text and offers the plain alternative.
- Prefer relationship-aware layout over builder spacing hacks: use `gap` for sibling layout, padding for space inside a section or container, and flow spacing for editorial text. Do not create empty spacer elements or use `min-height` as a substitute for content spacing; use minimum heights only for an intentional composition such as a viewport-filling hero, and make it tolerate longer content. Keep text as HTML rather than baking essential copy into images.
- Do not add intrusive patterns just because a source builder makes them easy: avoid unsolicited popups, autoplaying media, decorative single-item sliders, scroll hijacking, and infinite-scroll-only listings. Prefer visible content, pagination, or user-triggered controls. Preserve or add these patterns only for a clear user need, with keyboard operation, reduced-motion support, and a usable non-JavaScript or content fallback.
- Connect EmDash data to presentation through well-defined queries and components. Keep event/plugin data fetching and presentation logic separate; a registry sandboxed plugin's API response is data, not a rendered visitor-facing calendar.

## Styling architecture defaults

- In new builds, keep global tokens, reset/base rules, and rich-text flow rules in a small set of global CSS files. Keep repeated page structures in Astro components and page-specific layout in named component classes; use scoped `<style>` blocks for genuinely local exceptions, not as the only home for a design system.
- Keep a project's design values site-specific. This skill defines the architecture and naming discipline, not one fixed brand palette, font pairing, or set of numeric token values. Derive scales from the visual reference and intended content density, then verify them at narrow and wide viewports.
- Do not use Tailwind's default vocabulary (`bg-indigo-500`, `text-4xl`, `rounded-xl`, `shadow-2xl`, numeric `p-7`/`gap-6`, arbitrary `p-[37px]`) where a Baseline token exists; `npm run check:css` lists them as advisory token guardrails, and new client sites start with a strict theme (`design:tokens --init-client`) in which those defaults do not compile.
- Treat spacing and type tokens as the default API, not a ban on every fixed value. Fixed values remain appropriate for borders, icons, control hit areas, compact UI details, and deliberate exceptions. Explain repeated exceptions by giving them a named token or component rule.
- Put project-specific deviations and naming decisions in that site's `AGENTS.md`. Do not create a shared package or framework preset just to share a short token file between sites.
- Snippets in the `references/` documents are examples. Never copy them unchanged as a site theme: derive colors, type/space bounds, component variants, and content widths from the site's brief and inspected reference.
- When building a new token system, read `references/fluid-tokens.md`; when creating or reworking repeated layouts, read `references/astro-primitives.md`; when assembling conversion or marketing pages, read `references/landing-page-archetypes.md`; when rendering CMS rich text, read `references/emdash-content.md`. Load only the relevant reference for the current task.
- Read `references/accessibility.md` when adding a component pattern, interactive behavior, forms, navigation, media, or a validation checklist.

For a multi-page rollout, read [`references/rollout-verification.md`](references/rollout-verification.md) when planning acceptance. It covers task tracking, capture readiness, live enhancement checks, and honest verification scope.

## Implement and review in visual passes

For new sites and substantial visual overhauls, use `site-art-direction`'s [shared iteration loop](../site-art-direction/references/design-iteration.md): offer the design surface once as that reference sets out (HTML/browser concepts by default, Brilliant when an editable canvas is requested, OpenPencil and Penpot named, OpenDesign optional), reuse the user's choice, compare two or three structurally distinct directions side by side, resolve composition in focused batches, then prove one representative real route before rollout. Do not maintain a duplicate full Astro implementation during every concept edit; use an early bounded browser spike only for a material feasibility question. When Penpot is selected, use `penpot-site-design`; when OpenPencil is selected, use `openpencil-site-design` alongside its official version-matched upstream skill/API; when OpenDesign is selected, use `opendesign-site-design`. For Brilliant, use `brilliant-site-design` and verify fixed-width translation, semantic-role export and post-undo state before the Astro proof. Read approved file/page/board IDs and dated evidence, distinguish selected concepts from newer drafts, preserve source CSS expressions and content ownership, then translate through actual native component APIs. Same-agent work needs no duplicate packet. No concept export establishes browser behavior, CMS editability or release readiness.

Do not treat the first implementation as finished. For a new design, compare against the brief and chosen visual direction. For a migration, use the source screenshots to verify content, identity, and behavior, then judge whether the new design solves the documented weaknesses; matching weak source styling is not success. Use `references/migration-visual-audit.md` for that comparison.

1. Build the shared shell and representative page archetypes. Render them in the browser at desktop, mobile, and widths where layouts change. Inspect full pages, including lower sections and interaction states, before applying the design to every route.
2. Record concrete findings by route/component and viewport: missing content, wrong image or meaning, lost brand character, weak or generic composition, hierarchy, spacing, typography, contrast, overflow, and broken behavior. Use screenshots and Impeccable's `critique` command run as `new-site-workflow/references/impeccable-passes.md` sets out (not `detect` alone); a critique supplements the source/brief comparison. Prioritize shared token or component causes before page-specific tweaks. If the draft feels flatter, less distinctive, or harder to use than the source, revisit the design direction before expanding it.
3. Fix the findings as a batch, render again, and check that each material issue is resolved without regressing another page or width. Repeat this check for each newly built archetype. Once all routes are implemented, make a fresh full-page pass across every unique page and representative repeated records; fix and recheck any material findings from that pass.
4. **Apply the 5-Point Visual Self-Critique Rubric on every primary landing route before handoff:**
   - **3-Tier Surface Depth:** Verify Base Canvas (`--color-page`) → Primary Surface (`--color-surface`) → Elevated/Glass (`--color-elevated`, `.surface-elevated`, `.surface-glass`) with `1px` `--color-border` hairlines, and that each tier marks a real hierarchy step. When a long page needs a pacing change, use one purposeful rhythm breaker (`data-surface="dark"`, `.surface-spotlight`, `.surface-grain` or `.grid-hairline`) where the content changes register. A calm single-tone page passes this check; do not add a dark band to complete it.
   - **Typography Roles (4 available voices):** Verify optically tracked display headings (`--font-display`) and readable body/lead copy (`--font-body`, about `60ch–68ch` measure); these two are required. The accent and mono voices are available, not quotas. Use italic `.font-accent` only when the pairing has a genuine editorial voice, and in one of two ways: once, in the page heading, on the words the sentence turns on, or as the recorded way of setting every heading; not in some headings and not others. Use `.eyebrow-telemetry` / `.tabular-nums` for real metadata such as dates, times, prices, counts, versions and status. A small label above a heading is earned by such a fact; a label that only names its section, or a bare section index (`01`, `[01 // …]`), is not, unless the sequence itself carries information the visitor needs. A two-voice page is a valid result. Keep factual data truthful.
   - **Grid Rhythm & Asymmetry:** Verify no two consecutive sections repeat the same equal-width 3-column card geometry. Alternate with a 12-column `.bento-grid` (`8/4` or `7/5`), `1px` `.grid-hairline`, `<Sidebar>` or `.stack-cards` as the content warrants; an asymmetric split should follow a real difference in content weight. Record a specific comparison/brand exception where uniform rows must remain.
   - **Tactile Action Hierarchy:** Are primary/secondary actions distinct, accessible and functional? Use the relevant `.btn`, `.btn--secondary`, `.btn--ghost` and `.icon-nudge` patterns; verify keyboard focus and any `.clickable-parent` / `.focus-parent` card treatment.
   - **Signature & Content as Object:** Does the page have one moment only this subject would have (a full-width photograph of the real work or people, one fitted line, an index that previews, a dated programme)? Are lists set as the objects they are (a contents page, a fixtures list, a register) rather than a grid of equal cards? Run `npm run audit:composition -- --base <origin> --routes <route>` where installed and resolve its findings or record why they stay.
   - **Motion & Polish:** Exercise adopted `data-reveal`, `data-sticky-header`, `<Card transitionName>` morphing and FOUC-free `[data-surface-toggle]` behavior, including reduced motion and ordinary-navigation fallbacks. Choose motion and surface controls for a visitor need, not to complete a feature quota.

The rubric checks that each pattern is a reasoned choice, not that it is present. Then run the **generic-fingerprint check**: cover the logo and ask whether the page could be any generated site from this year. These patterns read as generated when they appear by default:

- a label above headings that only names the section (one that carries a date, a price or a count is earned);
- numbered section indices;
- an italic word in some headlines and not others (once in the page heading, or in every heading as the recorded treatment, is a choice);
- a floating glass navigation bar on a site whose recorded surfaces are not glass;
- the same bento → metric strip → dark spotlight band → FAQ sequence on every page;
- gradient text;
- a live-console hero for an offer that is not software;
- a kicker, a heading on one side and a lead on the other opening most sections;
- every list set as a grid of equal cards;
- photographs only in boxes, none at full width, on a site whose subject photographs well;
- a centred heading and button on a coloured band as the last section of every page.

Each one that remains needs a content reason in the page brief; otherwise remove it. Impeccable's craft floor (kicker labels, decorative section numbers, gradient text, decorative glass, monospace as a costume) applies on top of these recipes; when they disagree, the craft floor wins, and its own text says which items a brief can earn back.

Use these concrete defaults for new or replacement visual work. During refinement, a fixed brief or accepted existing identity can justify a specific exception: record the affected check, the constraint and the rendered evidence instead of quietly skipping it or replacing the recipe with generic advice. An audit's capability flags or expressive-usage count alone cannot establish visual quality. Use `references/rollout-verification.md` for browser fallback and capture readiness.

Across all five lenses, verify zero horizontal overflow, clipped text or awkward single-word heading wraps at `390px`, `768px` and `1440px` (the widths the concept comparison and visual baselines use), at `320px` for the narrowest phones, plus requested sizes such as `390x844` and `1440x900`. Inspect outer gutters, image meaning and reading order. Validate saved capture dimensions as well as live geometry. Evaluate every lens and document specific exceptions against the brief.

Keep a route checklist and resolve missing sections, broken assets, accidental content changes, and obvious layout defects before calling the work complete. Test intermediate widths and the narrowest placement of reusable components, not only phone and desktop presets. Stress representative templates with long headings, missing or unusually proportioned images, additional records, and translated text when applicable; check browser zoom/reflow and text-spacing overrides. For larger collections, inspect representative records visually and check every migrated URL for status, assets, and links. Run the project's checks and build, then check key interactions and accessibility in the browser. Stop when the brief's material design and functional criteria are met, rather than endlessly tuning cosmetic pixels. Do not claim visual fidelity without inspecting the rendered result.

Use current [EmDash theme-porting guidance](https://docs.emdashcms.com/themes/porting-wp-themes/) when implementing EmDash-backed routes, and consult the current Astro documentation for framework APIs.

For image delivery, verify the installed Astro image service and EmDash storage endpoint before custom infrastructure. Prefer native Image/Picture/getImage, accurate sizes and native-width limits. Configure runtime host services for fresh CMS uploads; do not introduce a manual rendition manifest by default. See docs/image-delivery.md in the starter.

## Engineering verification loop

Responsive acceptance includes the user's failed viewport, intermediate reflow and a case beyond the content maximum when the layout has one. Inspect copy width, heading groups, action wrapping, image crops and gutters alongside overflow. Check viewport-derived offsets inside a constrained native specimen and their full-width route. Preserve gallery frames and check regional contrast, not only loaded-image counts. Use real content in the selected languages; this is not a fixed heading-line-count rule.

After checks/builds that refresh compiler state, use a fixed built artifact in an owned process for final browser review. Preserve the review site's data and record artifact/revision, origin and runtime; stop only the owned process. Do not count an earlier browser pass against a changed build or call a stale dev import a product defect. Reuse existing isolated visual/SSR lifecycles rather than adding a competing preview service.

Run the verification sequence in the site's `AGENTS.md` (*Verify and hand off* on the EmDash foundation, *Verification and release* on generated static sites) before handoff; `new-site-workflow` holds the full sequence and its reasons. Check each command against `package.json` first, and do not add CMS tooling to satisfy an unavailable command.
