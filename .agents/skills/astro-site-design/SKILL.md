# Astro site design and implementation

Treat optional `DESIGN.md` proposals as reference material and reconcile them with `AGENTS.md` and shipped CSS. Validate implemented tokens with `npm run design:tokens` and inspect the rendered result; preserve fluid expressions and contextual aliases when translating external values. No exchange schema or validator is required. If a handoff needs a specific validator/exporter, select and install it separately; use `docs/design-interchange.md` for further guidance when available. External tool markup still needs the selected profile's content ownership and native image integration.

Build maintainable, accessible Astro pages and components. When a source site or visual reference exists, inspect its actual rendered appearance before implementation; do not substitute a vague textual approximation for visual review.

## Platform presentation boundary

Read `baseline.config.json` first. `static` and `static-sveltia` use native Content Collections, `getStaticPaths()` and Markdown `render()`; skip `building-emdash-site` and all CMS binding/modeling specialists. Existing EmDash API/editor/cache instructions below apply only to `emdash`. Localized static routes follow the project's file/URL model rather than assuming CMS translation groups.

Use shared `src/layouts/SiteShell.astro` for document metadata, global styles, skip link and landmarks. Platform `Base.astro` wrappers supply file-owned settings/navigation or EmDash contributions. Keep queries, widgets and storage out of shared primitives. `Card.astro` accepts ordinary HTML attribute bags; pass edit annotations only from an EmDash caller.

`ResponsiveImage.astro` accepts native Astro ImageMetadata (from `src/assets`) or a resolved URL with dimensions and uses Astro image processing. Do not add a storage endpoint to static sites. Native EmDash image fields must be passed whole to `Image` from `emdash/ui`; `url`/`src` may be absent on their provider/reference values. Baseline's `EmDashImage.astro` resolves already-known URLs for presentation, not arbitrary native field objects. Verify a CMS-saved image reference through actual rendering; do not treat upload success as proof. Where installed, `PhotoGallery fit="contain"` preserves full image frames; its omitted/cover default retains existing cropped previews. Static RichText wraps native Markdown in `.flow` plus `data-editorial-content`; Portable Text is a platform extension. `flow={false}` relinquishes both defaults, wrapperless unless attributes require a plain wrapper.

For incoming imagery in a greenfield build or day-2 maintenance, follow the installed `docs/media-preparation.md` and `media:prepare` command before storing/uploading it. Inspect intended use and output quality, use eligible prepared copies, and keep full-size originals outside the library and Git. Static profiles add those copies to `src/assets/`; EmDash uses the selected instance and `media:upload` readback when installed. A prior WordPress migration is not required. Existing sites without these commands need the explicit adoption described in `docs/baseline-updates.md`; do not invent an installed capability.

Calibrate tokens, typography, layout, cards, ticker and native images on the same common `/_styleguide` on both foundations. EmDash adds Portable Text/storage specimens separately. Static editor-proxy checks explicitly report inapplicable; this is not an editor verification pass. Production builds must exclude the route and fixture artifacts must remain nondeployable. Generated static sites support manual browser acceptance, not the EmDash-specific screenshot/registry harness. Follow the generated README's actual commands.

## Inspect before implementing

For URL-to-Astro migrations, read [references/component-quarantine.md](references/component-quarantine.md). After content and art-direction gates, calibrate real production primitives on `/_styleguide` before broad page assembly. That reference defines open composition versus semantic composites, surface-aware action patterns, the `src/assets/`/CMS image boundary, safe zero-JS LogoTicker slots and written handoffs. Follow its recorded Stage 4.5 gate; preserve the default-production route guard.

For flat screenshots, visual mockups or external interaction recipes, read [references/visual-mockup-workflow.md](references/visual-mockup-workflow.md). It defines evidence metadata, semantic translation, contextual safeguards and clean-source verification without changing upstream skills.

For a WordPress migration or redesign of an existing site, first read [`references/migration-visual-audit.md`](references/migration-visual-audit.md). It defines the route inventory, source evidence, preserve/improve decisions, and final page-by-page QA required for that work.

1. Use available browser automation to inspect the source site before asking the user for screenshots. Capture each distinct page archetype and unique editorial page at consistent desktop and mobile sizes; capture full-page views so content below the fold is included. Sample repeated records with different layouts or fields. Inspect rendered screenshots and, when available, the DOM and computed styles. If the site requires authentication, blocks automated access, or a relevant page/state cannot be reached with available tools, ask only for the missing access or reference rather than inventing the design.
2. Record a compact visual and content inventory: route/page type, content hierarchy, layout, typography, colors, spacing, imagery/crops, repeated components, interaction states, and responsive changes. Record which recognizable elements to preserve and which specific problems to improve. Verify the meaning of functional assets from nearby copy, links, captions, and destinations; do not infer their purpose from appearance alone.
3. Before coding, establish the design direction. For this user's WordPress migrations, default to improving the design unless faithful reproduction is requested. Treat the source as evidence of content, purpose, and identity, not a quality ceiling or pixel target. Write down the brand cues and functional details to retain, the design weaknesses to solve, and the intended improvements in hierarchy, typography, composition, imagery, navigation, and responsive behavior. Do not silently turn it into a different identity, remove distinctive motifs, or replace meaningful source imagery with generic decoration. Read the design-direction and comparison criteria in `references/migration-visual-audit.md`.

For WordPress sources built with Blocksy, Stackable, or Elementor, inspect the relevant theme/builder configuration as well as the rendered pages: global styles, headers/footers, archive/single templates, reusable sections, dynamic fields, responsive overrides, and interactions. A content export or screenshot alone may miss these. Use them to recover the design rules and behavior, then rebuild in Astro; do not copy generated builder markup or CSS. See the [WordPress content migration skill](../wordpress-to-emdash-content/SKILL.md) for a builder-specific inventory checklist.

Treat per-element IDs and generated builder styles as clues about the source, not as a styling API to port. If repeated items such as Stackable cards have individually assigned IDs, colors, spacing, or typography, compare several instances and determine which differences express real content or intentional variants and which are accidental drift. Model the repeated content as data and render it through one Astro component with shared tokens; add only a small number of named variants for deliberate differences. Use IDs only when identity is needed for anchors, labels, or ARIA relationships, not for visual styling. Do not reproduce each card as a hand-styled one-off.

## Implement clean Astro

For a multilingual site, use the locales and default locale agreed during setup. Astro owns locale-aware public routes; EmDash stores each translation as a separate entry in a linked translation group. Pass `Astro.currentLocale` to EmDash entry, collection, menu, and taxonomy queries. Build locale-aware links and a language switcher from available translations, and include canonical/hreflang metadata where appropriate. Keep each locale's content, menus, and publication state intentional; don't assume fallback supplies collection listings or translates UI copy. Follow EmDash's [internationalization guide](https://docs.emdashcms.com/guides/internationalization/) and verify the default locale stays unprefixed so `/_emdash/admin` continues to work.

- Treat WordPress output as reference content and visual behavior, not markup to copy. Rebuild from semantic HTML, accessible controls, and focused Astro components; do not carry over Gutenberg/Elementor/Stackable wrapper trees, shortcodes, or theme-specific CSS as the new architecture.
- Identify repeated site-wide patterns and make reusable layouts/components for them. Use shared design tokens and component-level classes; avoid one-off inline styles and duplicated page CSS when a shared rule or component is appropriate.
- Inspect the project first and follow its existing styling conventions when they are sound. For a new site or a substantial visual rebuild, use the project's fluid token baseline: Tailwind CSS v4 with CSS-first `@theme` tokens, fluid type and spacing scales (including high-contrast `-to-` bridge steps), semantic spacing names, multi-layer OKLCH elevation shadows, and small semantic Astro layout components. Do not migrate a sound existing system just to standardize it. Do not add Tailwind v3 or the legacy `@astrojs/tailwind` integration to a new project; use Astro's documented Tailwind v4 / `@tailwindcss/vite` setup and verify it against the installed Astro version.
- Use a three-tier architecture: (1) CSS design tokens and base rules, (2) semantic Astro structural primitives, and (3) agent instructions/recipes that constrain composition to the first two tiers. Do not recreate a large combinatorial runtime utility framework.
- Define fluid scales mathematically rather than choosing unrelated `clamp()` values by eye. Choose minimum and maximum values and viewport bounds, calculate the linear interpolation, and encode the result as `clamp(min, calc(intercept + slope * 100vi), max)` tokens. `vi` is the default for viewport-wide fluid type and spacing; use `cqi` for a component that should respond to its containing layout only when an ancestor establishes an inline-size query container. Document bounds and keep the min/max legible at zoom and narrow widths. Prefer a small intentional scale with paired steps (for example, type and space steps) over a large list of near-duplicates.
- Choose responsive behavior by what controls the available space: use intrinsic CSS first, then a container query for a component whose placement changes its width, then a media query for viewport-level behavior. Keep user-preference media queries for motion, contrast, and similar settings. A breakpoint should reflect where content stops working; share a named breakpoint only when multiple parts of the site genuinely need the same threshold. Read `references/responsive-architecture.md` when designing responsive components or changing the site's responsive strategy.
- Centralize palette, font, content widths, type, spacing, breakpoints, radii, borders, shadows, layering, and motion values. Use semantic spacing tokens such as content, grid, and container gaps rather than unexplained one-off layout values. In Tailwind v4, map CSS tokens through the appropriate `@theme` namespaces when they should create utilities; retain regular CSS custom properties for semantic aliases and values that should not create utility APIs. Define color primitives in OKLCH where suitable, then define semantic roles such as surface, text, border, action, and status. Derived shade/alpha steps must still be checked for perceptual consistency, theme behavior, and text/control contrast; don't assume a generated shade is accessible.
- Avoid styling through IDs, long high-specificity selector chains, or escalating `!important` overrides. Let Tailwind utilities, shared component classes, tokens, and deliberate cascade layers express the design. Use `!important` only to contain an override for an external style that cannot be changed, and leave a brief explanation.
- Build semantic Astro primitives such as `Section`, `Container` (`width="reading|content|wide"` for standard sections, `breakout` / `.content-grid` for long-form editorial flows with wide callouts/media), and `Grid` when they encode repeated structure or responsive behavior; use `Card` (`<article class="card">` with `.clickable-parent` / `.focus-parent` on the heading link, `--card-*` custom properties, and concentric `--card-media-radius` math) when its content/link contract is consistent. Keep APIs small and explicit. Don't wrap every element or turn Astro into a client-rendered component system.
- **Blueprint section pacing and conversion engine before assembling routes:** For marketing, landing, or conversion surfaces, follow the strategic intake, conversion copywriting formulas (`"{Outcome} without {pain}"`), and deterministic section build order in `references/landing-page-archetypes.md`. Before writing a page template, write down its section-by-section structural sequence so no two consecutive sections share the same layout geometry (never stack consecutive 3-column card grids). Alternate across: (1) Asymmetric 7/5 or 6/6 Hero with a live-coded `.ui-specimen` or framed focal visual, (2) Exposed `1px` `.grid-hairline` metrics/proof ledger or `<LogoTicker>`, (3) Asymmetric `<Sidebar>` sticky narrative paired with a bento/ledger matrix, (4) High-contrast `<Section data-surface="dark" class="surface-spotlight">` showcase band, and (5) Native `<Disclosure>` FAQ + closing conversion band.
- **Use Baseline's 4-voice typography, surface physics, and live-coded UI specimen utilities (`src/styles/global.css`):**
  - Pair `--font-display` headlines with `.eyebrow-telemetry` (`--font-mono` uppercase coordinate tags like `[01 // ARCHITECTURE]`), `.font-accent` (`--font-accent` inline italic serif contrast on 1–2 focal words inside `<h1>`/`<h2>`), `.prose-dropcap` for editorial essays/manifestos, and `.tabular-nums` on all metrics/counters. **Astro v7 `compressHTML: 'jsx'` whitespace rule:** Astro v7 strips newline whitespace between adjacent inline elements; always keep inline spans/tags on the same line (`Engineered for <em class="font-accent">precision</em>`) or insert an explicit `{' '}` so words never concatenate.
  - Layer 3-tier surfaces (`--color-page` canvas, `--color-surface` cards, `.surface-elevated` raised controls/headers, `.surface-glass` translucent bars, and `.surface-grain` zero-asset SVG paper/film texture) with `--surface-highlight` (`1px` top inner specular edge), `.bento-grid` (`.bento-span-4|5|6|7|8|12`, `.bento-row-2`), `.reel-snap` horizontal scroll-snap galleries, `.section-defer` (`content-visibility: auto`) on below-the-fold sections, native `<dialog>` `@starting-style` modals/drawers, and `.grid-hairline` / `.bg-grid-blueprint` / `.frame-crosshair` for architectural precision.
  - Style actions with explicit hierarchy using `.btn` (primary solid), `.btn--secondary` (elevated surface with `--color-border-strong`), and `.btn--ghost`, pairing trailing arrows (`→` / `↗`) with `.icon-nudge` for spring-eased hover choreography; mark sticky site headers with `data-sticky-header` so `SiteShell.astro` toggles `data-scrolled` glass condensation after `16px` of scroll; and always pass `loading="eager" fetchpriority="high"` to above-the-fold hero `<ResponsiveImage>` components (or `priority` on native `<Image />` / `<Picture />`) for optimal LCP.
  - For SaaS, developer tools, AI, fintech, and B2B sites, build the hero and flagship feature visuals as **live-coded HTML/SVG UI specimens** (`.ui-specimen` + `.ui-specimen__header` + `.badge-pill` + `.status-dot`) and pure-CSS telemetry histograms (`.viz-bars` + `.viz-bar` with `--bar-value`) rather than generic stock imagery. See `references/landing-page-archetypes.md` for copy-ready patterns.
  - **Zero-framework micro-islands & declarative shell choreography:** Use `.stack-cards` + `.stack-card` (`--stack-index`) for zero-JS sticky physical card stacking; `data-reveal` + `data-reveal-delay` for progressive-enhancement scroll reveals; `data-filter-root` / `data-filter-btn` / `data-filter-item` for instant client-side category filtering with `.animate-card-in` reflow replay; `<SiteShell surface="dark|light|system">` + `data-surface-toggle` (with `[data-surface-icon="light"]` and `[data-surface-icon="dark"]` children) for FOUC-free persisted Daylight/Dark surface switching (`baseline:surface`) that preserves 3-tier `--color-page` / `--color-surface` / `--color-elevated` depth in both modes; and `<script define:vars={{ ... }}>` bound on `astro:page-load` for interactive ROI/pricing calculators or DAG/console node inspectors with 0 KB of client framework runtime.
  - **Instant page transitions, shared-element morphing & Speculation Rules (`<ClientRouter fallback="swap" />`):** On `static` and `static-sveltia` sites (and public `emdash` routes that do not conflict with active inline Portable Text editing), slot `<ClientRouter fallback="swap" slot="head" />` from `astro:transitions` into `<SiteShell>` inside `Base.astro`. This enables 80ms hover and `touchstart`/`mousedown` prefetching (`prefetchAll: true`), `<head>` stylesheet deduplication, and `180ms var(--ease-smooth)` root View Transitions. Pass `transitionName={`post-${slug}`}` to `<Card>` on index pages and apply `.vt-morph` (`style={`--vt-name: post-${slug}-title`}`) on the detail route's `<h1>`/hero media to morph cards into full articles; use `transition:persist` on stateful header or media elements; and consider `experimental: { clientPrerender: true }` (Speculation Rules API) on static sites for 0ms background prerendering.
  - **Native Astro 5/6/7 fonts, SVG components, Server Islands & Form Actions:** Configure custom Google, Fontshare, Bunny, Fontsource, or local fonts via Astro's built-in `fonts` API (`fontProviders` in `astro.config.mjs` + `<Font cssVariable="--font-display" preload />` from `astro:assets`) for self-hosted `.woff2` files and metric-matched zero-CLS fallback `@font-face` generation; import `.svg` files from `src/assets/` directly as inline Astro components with `.svg-icon`; use `server:defer` Server Islands with `<div slot="fallback" class="skeleton-shimmer">` for personalized/dynamic blocks on cached EmDash SSR pages; and use `astro:actions` (`defineAction({ accept: 'form' })`) for progressive-enhancement validated forms.
- Use the shipped spacing ownership in `docs/design-framework.md`: site-owned Base activates `automatic-v2`; shared SiteShell defaults legacy. Section owns padding and container gap, Container owns content gap, Grid owns grid gap, and the shell owns horizontal gutters once. Local modes reset; `spacing="none"` changes padding only. Choose `layout="custom"` for caller-owned display/gap and retain breakout's named grid. Root `--layout-*` aliases reuse existing scales and can be scoped regionally. Generic `.flow` spaces direct siblings; RichText/explicit `data-editorial-content` owns prose controls, bounded at `data-editorial-island` roots. Avoid duplicating a layout gap with flow/space-y margins. Check actual inline-editor select/type/save/reload when changing CMS renderer boundaries. For day-2 changes preview a narrow `design:tokens --set` request, review its diff, write explicitly and verify the saved source plus affected rendered compositions. Do not create a second token store or spacing settings panel.
- Keep utilities and semantic CSS complementary: Tailwind utilities are useful for clear local composition; component classes and Astro primitives own repeated patterns and complex responsive behavior. For macro layout, prefer structural components and named contextual tokens over default-scale guesses such as `gap-7`, arbitrary values such as `p-[22px]`, or duplicated ad hoc media queries. Do not ban every fixed value: a documented local exception is better than distorting a component API. Use breakpoint variants/media queries for real discrete behavior changes, not to patch around a missing fluid token. With Tailwind v4, component `<style>` blocks are separate style contexts; prefer shared CSS variables or classes from the global stylesheet rather than assuming `@theme` values or `@apply` are automatically available there. If using Tailwind directives in a component style, follow the current `@reference` guidance.
- Include accessible interaction tokens and behavior alongside visual tokens: visible focus styles, hover/active/disabled states, reduced-motion handling, adequate target sizes, and sufficient text and non-text contrast. Honor semantic HTML and keyboard behavior; design tokens do not replace accessible markup or testing.
- Treat WCAG 2.2 AA as the default implementation target unless the project names another standard. Accessibility is a design and content requirement, not a final color-check pass: check landmarks/headings, link and control names, keyboard operation/focus, form labels/errors/status, alternatives for meaningful imagery, contrast, zoom/reflow, motion preferences, and pointer targets. Do not claim conformance based only on automated checks; include manual keyboard and responsive checks.
- Keep HTML semantic and responsive, keyboard-accessible, and readable. Use Astro for mostly static rendering and add client-side JavaScript only for interactions that need it. Preserve progressive enhancement where practical.
- Prefer relationship-aware layout over builder spacing hacks: use `gap` for sibling layout, padding for space inside a section or container, and flow spacing for editorial text. Do not create empty spacer elements or use `min-height` as a substitute for content spacing; use minimum heights only for an intentional composition such as a viewport-filling hero, and make it tolerate longer content. Keep text as HTML rather than baking essential copy into images.
- Do not add intrusive patterns just because a source builder makes them easy: avoid unsolicited popups, autoplaying media, decorative single-item sliders, scroll hijacking, and infinite-scroll-only listings. Prefer visible content, pagination, or user-triggered controls. Preserve or add these patterns only for a clear user need, with keyboard operation, reduced-motion support, and a usable non-JavaScript/content fallback as appropriate.
- Connect EmDash data to presentation through well-defined queries and components. Keep event/plugin data fetching and presentation logic separate; a registry sandboxed plugin's API response is data, not a rendered visitor-facing calendar.

## Styling architecture defaults

- In new builds, keep global tokens, reset/base rules, and rich-text flow rules in a small set of global CSS files. Keep repeated page structures in Astro components and page-specific layout in named component classes; use scoped `<style>` blocks for genuinely local exceptions, not as the only home for a design system.
- Keep a project's design values site-specific. This skill defines the architecture and naming discipline, not one fixed brand palette, font pairing, or set of numeric token values. Derive scales from the visual reference and intended content density, then verify them at narrow and wide viewports.
- Treat spacing and type tokens as the default API, not a ban on every fixed value. Fixed values remain appropriate for borders, icons, control hit areas, compact UI details, and deliberate exceptions. Explain repeated exceptions by giving them a named token or component rule.
- Record these conventions in this skill for cross-site behavior. Put project-specific deviations and naming decisions in that site's `AGENTS.md`. Add a shared package or starter preset only after multiple sites demonstrate that the same implementation is worth maintaining; do not create a framework package just to share a short token file.
- Keep the top-level skill focused on the decision rules and workflow. Put detailed interpolation examples, token naming recipes, Astro component contracts, and EmDash Portable Text examples in small, task-specific `references/` documents and tell the agent when to read them. Optional starter snippets can live beside those references as examples, but never copy them unchanged as a site theme: derive colors, type/space bounds, component variants, and content widths from the site's brief and inspected reference. Avoid loading every recipe into context for unrelated tasks.
- When building a new token system, read `references/fluid-tokens.md`; when creating or reworking repeated layouts, read `references/astro-primitives.md`; when assembling conversion or marketing pages, read `references/landing-page-archetypes.md`; when rendering CMS rich text, read `references/emdash-content.md`. Load only the relevant reference for the current task.
- Read `references/accessibility.md` when adding a component pattern, interactive behavior, forms, navigation, media, or a validation checklist.

For a multi-page rollout, read [`references/rollout-verification.md`](references/rollout-verification.md) when planning acceptance. It covers task tracking, capture readiness, live enhancement checks, and honest verification scope.

## Implement and review in visual passes

For new sites and substantial visual overhauls, use `site-art-direction`'s [canvas-led iteration loop](../site-art-direction/references/design-iteration.md): offer OpenPencil, OpenDesign, Penpot and direct Astro/browser, reuse the user's choice, resolve composition in focused batches, then prove one representative real route before rollout. Do not maintain a duplicate full Astro implementation during every canvas edit; use an early bounded browser spike only for a material feasibility question. When Penpot is selected, use `penpot-site-design`; when OpenPencil is selected, use `openpencil-site-design` alongside its official version-matched upstream skill/API; when OpenDesign is selected, use `opendesign-site-design`. Read approved file/page/board IDs and dated evidence, distinguish selected boards from newer drafts, preserve source CSS expressions and content ownership, then translate through actual native component APIs. Same-agent work needs no duplicate packet. No canvas export establishes browser behavior, CMS editability or release readiness.

Do not treat the first implementation as finished. For a new design, compare against the brief and chosen visual direction. For a migration, use the source screenshots to verify content, identity, and behavior, then judge whether the new design solves the documented weaknesses; matching weak source styling is not success. Use `references/migration-visual-audit.md` for that comparison.

1. Build the shared shell and representative page archetypes. Render them in the browser at desktop, mobile, and widths where layouts change. Inspect full pages, including lower sections and interaction states, before applying the design to every route.
2. Record concrete findings by route/component and viewport: missing content, wrong image or meaning, lost brand character, weak or generic composition, hierarchy, spacing, typography, contrast, overflow, and broken behavior. Use screenshots and a design critique tool such as Impeccable when available; a critique supplements the source/brief comparison. Prioritize shared token or component causes before page-specific tweaks. If the draft feels flatter, less distinctive, or harder to use than the source, revisit the design direction before expanding it.
3. Fix the findings as a batch, render again, and check that each material issue is resolved without regressing another page or width. Repeat this check for each newly built archetype. Once all routes are implemented, make a fresh full-page pass across every unique page and representative repeated records; fix and recheck any material findings from that pass.
4. **Apply the 5-Point Visual Self-Critique Rubric on every primary landing route before handoff:**
   - **3-Tier Surface Depth:** Verify Base Canvas (`--color-page`) → Primary Surface (`--color-surface`) → Elevated/Glass (`--color-elevated`, `.surface-elevated`, `.surface-glass`) with `1px` `--color-border` hairlines. On a new primary landing page, verify at least one high-contrast surface or structural rhythm breaker (`data-surface="dark"`, `.surface-spotlight`, `.surface-grain` or `.grid-hairline`) anchors the mid-page scroll.
   - **4-Voice Typography:** Verify optically tracked display headings (`--font-display`), readable body/lead copy (`--font-body`, about `60ch–68ch` measure), selective italic `.font-accent` contrast and `.eyebrow-telemetry` / `.tabular-nums` for labels or real metadata. On a new primary landing page, verify at least three distinct roles are visible above the fold: display headline, editorial accent or body lead, and mono metadata/badges. Keep factual data truthful.
   - **Grid Rhythm & Asymmetry:** Verify no two consecutive sections repeat the same equal-width 3-column card geometry. Alternate with a 12-column `.bento-grid` (`8/4` or `7/5`), `1px` `.grid-hairline`, `<Sidebar>` or `.stack-cards` as the content warrants. Record a specific comparison/brand exception where uniform rows must remain.
   - **Tactile Action Hierarchy:** Are primary/secondary actions distinct, accessible and functional? Use the relevant `.btn`, `.btn--secondary`, `.btn--ghost` and `.icon-nudge` patterns; verify keyboard focus and any `.clickable-parent` / `.focus-parent` card treatment.
   - **Motion & Polish:** Exercise adopted `data-reveal`, `data-sticky-header`, `<Card transitionName>` morphing and FOUC-free `[data-surface-toggle]` behavior, including reduced motion and ordinary-navigation fallbacks. Choose motion and surface controls for a visitor need, not to complete a feature quota.

Use these concrete defaults for new or replacement visual work. During refinement, a fixed brief or accepted existing identity can justify a specific exception: record the affected check, the constraint and the rendered evidence instead of quietly skipping it or replacing the recipe with generic advice. An audit's capability flags or expressive-usage count alone cannot establish visual quality. Use `references/rollout-verification.md` for browser fallback and capture readiness.

Across all five lenses, verify zero horizontal overflow, clipped text or awkward single-word heading wraps at `375px`, `768px` and `1440px`, plus requested sizes such as `390x844` and `1440x900`. Inspect outer gutters, image meaning and reading order. Validate saved capture dimensions as well as live geometry. Evaluate every lens and document specific exceptions against the brief.

Keep a route checklist and resolve missing sections, broken assets, accidental content changes, and obvious layout defects before calling the work complete. Test intermediate widths and the narrowest placement of reusable components, not only phone and desktop presets. Stress representative templates with long headings, missing or unusually proportioned images, additional records, and translated text when applicable; check browser zoom/reflow and text-spacing overrides. For larger collections, inspect representative records visually and check every migrated URL for status, assets, and links. Run the project's checks and build, then check key interactions and accessibility in the browser. Stop when the brief's material design and functional criteria are met, rather than endlessly tuning cosmetic pixels. Do not claim visual fidelity without inspecting the rendered result.

Use current [EmDash theme-porting guidance](https://docs.emdashcms.com/themes/porting-wp-themes/) when implementing EmDash-backed routes, and consult the current Astro documentation for framework APIs.

For image delivery, verify the installed Astro image service and EmDash storage endpoint before custom infrastructure. Prefer native Image/Picture/getImage, accurate sizes and native-width limits. Configure runtime host services for fresh CMS uploads; do not introduce a manual rendition manifest by default. See docs/image-delivery.md in the starter.

## Engineering verification loop

Responsive acceptance includes the user's failed viewport, intermediate reflow and a case beyond the content maximum where relevant. Inspect copy width, heading groups, action wrapping, image crops and gutters alongside overflow. Check viewport-derived offsets inside a constrained native specimen and their full-width route. Preserve gallery frames and check regional contrast, not only loaded-image counts. Use real content in the selected languages; this is not a fixed heading-line-count rule.

After checks/builds that refresh compiler state, use a fixed built artifact in an owned process for final browser review. Preserve the review site's data and record artifact/revision, origin and runtime; stop only the owned process. Do not count an earlier browser pass against a changed build or call a stale dev import a product defect. Reuse existing isolated visual/SSR lifecycles rather than adding a competing preview service.

For the EmDash foundation, preflight with `npm.cmd run doctor`, use
`npm.cmd run verify:fast` during edits, then run `npm.cmd run verify`,
`npm.cmd run build`, and `npm.cmd run audit:html` against that fresh build
before handoff. On Unix use `npm` in place of `npm.cmd`. Set up the local
Git pre-commit hook once with `npm.cmd run setup:hooks`; it runs doctor and
verify:fast and preserves existing hook managers. It supplements the final gate
and CI; Git hooks are local and can be bypassed. The HTML audit checks emitted
HTML or automatically captures linked public SSR responses from the local
production CMS. Missing published content or broken navigation fails the audit;
